## 4. 高优先级问题

### HIGH-001：Self-check 反射调用失败时静默降级为全 false — 假阴性不可诊断

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:628`

```csharp
catch (Exception ex) when (ex is IOException or InvalidOperationException 
    or MissingMethodException or TargetInvocationException 
    or FileNotFoundException or FileLoadException or BadImageFormatException)
{
    platform.AuditLog.Record("solidworks", "self-check", 
        "solidworks_skeleton_check_failed", ex.GetBaseException().Message);
    return new SolidWorksSkeletonSelfCheckResult(
        false, false, false, false, false, false, false, 
        false, false, false, false, false, false, false);
}
```

**问题**: 当 `workerMethod.Invoke()` 因方法签名变更抛出 `TargetInvocationException` 时，catch 返回全部 14 个字段为 `false` 的 `SolidWorksSkeletonSelfCheckResult`。审计日志虽然记录了错误，但 self-check 报告中**无法区分**：
1. SolidWorks 模块真的未启用（`module.yaml` 缺少配置）
2. Worker 类型正确加载但签名不匹配（代码 bug）
3. 反射调用过程中抛出了意外异常（运行时环境问题）

三种情况产生的 self-check JSON 输出完全一致（14 个 `false`）。

**风险**: 如果 Codex 未来修改了 `ISolidWorksWorker.ExecuteAsync` 的方法签名（例如增加参数），self-check 不会显式报错 — 它只是静默地报告 "SolidWorks 检查全部不通过"，而没有明确指出 **"自检本身的反射调用失败了"**。这种假阴性会误导排查方向。

**建议修复**: 在 SelfCheckReport 中新增 `SolidWorksSelfCheckError` 字符串字段，正常路径设为 `null`，异常路径写入 `ex.GetBaseException().Message`：
```csharp
return new SolidWorksSkeletonSelfCheckResult(
    false, false, false, false, false, false, false, 
    false, false, false, false, false, false, false)
{
    SelfCheckInfrastructureError = ex.GetBaseException().Message
};
```

**为什么重要**: 假阴性与假通过同等危险。如果自检基础设施损坏但没有暴露，开发者会花费大量时间排查"为什么模块未启用"，而真正的问题是自检代码本身需要更新。

**状态**: ⚠️ 上一轮 V0.9-B-fix 审查已提出，**至今未修复**。

### HIGH-002：PlaceholderWorker 回退路径中 CancellationToken 完全丢失

**位置**:
- `src/WorkerContracts/IWorker.cs:11-12` — 默认接口方法
- `src/PlatformCore/PlatformBootstrapper.cs:144` — PlaceholderWorker 回退
- `src/PlatformCore/WorkerRegistry/PlaceholderWorker.cs` — 不覆盖 CancellationToken 重载

**问题**: `IWorker` 的默认接口方法实现：

```csharp
Task<WorkerOutput> ExecuteAsync(WorkerInput input, CancellationToken cancellationToken) =>
    ExecuteAsync(input);  // ← token 直接丢弃
```

当 `PlatformBootstrapper.TryCreateWorker` 返回 `null`（例如 SolidWorksWorker.dll 未被编译或被移动），回退到 `PlaceholderWorker`。但 `PlaceholderWorker` **不覆盖** `ExecuteAsync(WorkerInput, CancellationToken)`，因此继承默认实现 — token 被丢弃。任何通过 WorkflowEngine 对 PlaceholderWorker 发起的超时取消都不会生效。

**风险**: 如果 WorkflowEngine 配置了步骤超时（例如 30s），当 PlaceholderWorker 因某种原因阻塞时：
- `CancellationToken` 不会被检查
- Workflow 步骤永久挂起
- 超时逻辑被绕过

**建议修复**: 在默认接口方法中至少检查 token：
```csharp
Task<WorkerOutput> ExecuteAsync(WorkerInput input, CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();
    return ExecuteAsync(input);
}
```
这样所有未覆盖的 `IWorker` 实现至少能在入口处响应取消。

**为什么重要**: 取消机制是 Workflow 可靠性的最后防线。回退路径丢失取消支持意味着在最需要超时保护的场景（外部依赖不可用时）反而最脆弱。

**状态**: ⚠️ 上一轮 V0.9-B-fix 审查已提出，**至今未修复**。

### HIGH-003（本轮新发现）：CandidateAssemblyPaths 中 `Directory.EnumerateFiles` 无子目录权限异常保护

**位置**: `src/PlatformCore/PlatformBootstrapper.cs:216-218`

```csharp
foreach (var path in Directory
    .EnumerateFiles(workerRoot, fileName, SearchOption.AllDirectories)
    .Where(path => path.Split(...).Contains("bin", ...))
    .OrderByDescending(File.GetLastWriteTimeUtc))
```

**问题**: `Directory.EnumerateFiles(workerRoot, ..., SearchOption.AllDirectories)` 在 `src/Workers` 子目录权限受限时会抛出 `UnauthorizedAccessException`，该异常在 `CandidateAssemblyPaths` 的 foreach 循环中出现，但 `CandidateAssemblyPaths` **没有 try-catch**。`CandidateAssemblies` 的 try-catch 只包裹 `Assembly.LoadFrom`。这会导致整个 `RegisterWorkers` → `CreateDefault` 调用崩溃。

**风险**: 在受限用户账户或某些 CI 环境中，`src/Workers` 子目录出现权限问题时，平台启动直接失败。

**建议修复**: 在 `CandidateAssemblyPaths` 中对 `EnumerateFiles` 增加 try-catch，或使用 .NET 7+ 的 `EnumerationOptions` 跳过不可访问目录：
```csharp
var options = new EnumerationOptions 
{ 
    RecurseSubdirectories = true, 
    IgnoreInaccessible = true 
};
foreach (var path in Directory.EnumerateFiles(workerRoot, fileName, options)...)
```

### MEDIUM-005（本轮新发现）：TryWriteJsonReport 对空目录名的 null-forgiving 假设

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:380`

```csharp
Directory.CreateDirectory(Path.GetDirectoryName(reportPath)!);
```

**问题**: `Path.GetDirectoryName` 对于仅文件名的路径（如 `"report.json"`）返回 `""`，对于根路径返回 `null`。`!` null-forgiving 操作符抑制了编译器警告，但如果传入意外格式的路径，`Directory.CreateDirectory("")` 或 `Directory.CreateDirectory(null)` 会抛出异常。

**风险**: 低 — 调用方始终使用已知的合成路径。但这是防御性代码中的防御性弱点。

**建议修复**: 显式检查并处理 null：
```csharp
var directory = Path.GetDirectoryName(reportPath);
if (!string.IsNullOrEmpty(directory))
{
    Directory.CreateDirectory(directory);
}
```

### MEDIUM-006（本轮新发现）：PlatformPathResolver.FindProjectRoot 回退到 `Directory.GetCurrentDirectory()` 可能导致静默误判

**位置**: `src/PlatformCore/PlatformPathResolver.cs:19`

```csharp
return Directory.GetCurrentDirectory();
```

**问题**: 当 `PlatformPathResolver.FindProjectRoot` 从 `AppContext.BaseDirectory` 向上遍历找不到 `.sln` 文件时，回退到 `Directory.GetCurrentDirectory()`。如果测试或运行时的工作目录不在项目根目录下，这个回退值会导致后续所有路径拼接错误——但不会产生显式错误，只会导致文件找不到或加载错误的工作集。

**风险**: 在 IDE 测试运行器、CI 代理或以不同工作目录启动的应用中，Fallback 返回错误根目录会导致运行时行为异常但无显式报错。

**建议修复**: 回退到抛异常并附带诊断信息，而非返回一个可能不正确的目录：
```csharp
throw new DirectoryNotFoundException(
    $"Could not locate project root from '{startDirectory ?? AppContext.BaseDirectory}'. " +
    "Ensure the working directory is within the AI_Mechanical_Engineering_Agent_Platform tree.");
```

## 7. 架构评估

- Skill → Worker → Validator → Reviewer → QualityGate 分层完整且清晰。

- Gateway → Worker 隔离在 `GatewayDoesNotDispatchSolidWorksWorker` 测试中得到验证。

### 接口稳定性: ✅ 良好

- `IWorker` 新增 CancellationToken 重载 — 默认实现委托给无参版本，所有已有 IWorker 实现行为不变。
- `SolidWorksArtifactValidator` 新增可选 `configuredOutputRoot` 构造参数 — 无参构造保持原有行为。
- `SolidWorksBuildPlanReviewer.ExtractDimensions` 返回类型从值元组变为可空元组 — 调用方已全部适配。
- `PlatformSelfCheckReport` 的 SolidWorks 14 个字段均有 `[JsonPropertyName]`，命名风格一致。

### 耦合风险: ✅ 低

- Skill / Validator / Reviewer / Worker 之间只通过 DomainSchemas 耦合。
- 无跨层引用。Worker 项目独立于 PlatformCore。
- `PlatformBootstrapper` 新增对 `System.Reflection` 的依赖为 .NET 标准库。
- `TryCreateWorker` / `CandidateAssemblies` / `CandidateAssemblyPaths` 均为 private static，不暴露给外部消费者。

### 扩展风险: ⚠️ 需注意

- 新增 Worker 时只需确保 Worker 项目被编译，Bootstrapper 的 `CandidateAssemblyPaths` 会自动发现。但依赖 `OrderByDescending(File.GetLastWriteTimeUtc)` 选择"最新"的 bin 目录，在同时存在 Debug 和 Release 构建时可能选择非预期版本。
- `CandidateAssemblyPaths` 隐式依赖 `src/Workers` 目录结构 — 如果组织结构变更需同步修改。

### Workflow 兼容性: ✅ 保持

- `SequentialWorkflowEngine` 的 retry delay (`await Task.Delay`) + `CancellationToken` 支持自 V0.8 以来保持稳定。
- `ChiefEngineerOrchestrator` 的 fallback 引擎已统一使用 `CreateDefaultRetryPolicy()`（已在 V0.7-fix 修复）。
- 本次修改不触及 WorkflowEngine、RetryPolicy、Orchestrator 核心逻辑。
