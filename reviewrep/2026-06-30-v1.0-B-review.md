## 4. 架构风险

### 架构风险 A-001：COM 对象通过 `SolidWorksSessionConnectionResult.Application` 泄漏 — 封装边界被破坏

**位置**:
- `src/Workers/SolidWorks/SolidWorksSessionManager.cs:21` — `object? Application = null`
- `src/Workers/SolidWorks/RealSolidWorksWorker.cs:165-170` — 将 `connection.Application` 传递给 `_plateBuilder`

**问题**: V1.0-A 中 `SolidWorksSessionManager` 是完全封装 COM 的黑盒 — 连接、版本查询、释放全部内部完成。V1.0-B 通过 `SolidWorksSessionConnectionResult.Application` 将原始 COM 对象暴露给消费者，打破了这层封装。

具体风险链：
1. `SolidWorksSessionManager.ConnectAsync` 返回 `SolidWorksSessionConnectionResult`，其中 `Application` 字段携带 COM 对象
2. `RealSolidWorksWorker` 取出 `connection.Application`，传递给 `_plateBuilder.BuildPlateBasicFourHolesAsync(connection.Application, ...)`
3. `finally` 块中调用 `_sessionManager.DisconnectAsync(CancellationToken.None)` 释放 COM 对象
4. 如果 `ISolidWorksPlateBuilder` 的实现缓存了 `application` 引用，则在 `DisconnectAsync` 之后，该引用变为悬挂 COM 引用（RCW 已释放，后续调用抛 `COMException`）

**当前风险评估**: 中等。当前的 `LateBoundSolidWorksPlateBuilder.BuildCore` 是同步方法，在 `finally` 之前完成，不会持有引用。但 `ISolidWorksPlateBuilder` 是公开接口，任何未来实现都可以存储 `application` 参数 — 接口契约没有禁止这一点。

**建议修复**: 将 `Application` 从 `SolidWorksSessionConnectionResult`（公开 record）中移除，改为在 `SolidWorksSessionManager` 内部提供一个受控的执行方法：
```csharp
// 方案：SessionManager 持有 Application，提供 ExecuteWithApplication 方法
public async Task<T> ExecuteWithApplicationAsync<T>(
    Func<object, CancellationToken, Task<T>> action,
    CancellationToken cancellationToken);
```
这样 COM 对象永远不会离开 `SessionManager` 的控制范围。

**重要性**: 如果 COM 对象被错误持有导致悬挂引用，不会造成数据损坏（文件已写入），但会造成：
- 误导性的 `COMException`（"COM object that has been separated from its underlying RCW"）
- 无法区分"真正的 COM 错误"和"生命周期管理错误"
- 在 SolidWorks 已崩溃但 RCW 仍被持有的场景下，阻塞线程池

### 架构风险 A-002：`SupportsRealBuild => false` 与 `SupportsPlateBasicFourHolesBuild => true` 共存 — API 语义冲突

**位置**:
- `src/Workers/SolidWorks/RealSolidWorksWorker.cs:38` — `public bool SupportsRealBuild => false;`
- `src/Workers/SolidWorks/RealSolidWorksWorker.cs:40` — `public bool SupportsPlateBasicFourHolesBuild => true;`

**问题**: 当前 `RealSolidWorksWorker` 可以执行 `RealBuildPlateBasic4Holes` 模式，该模式：
- 调用真实 SolidWorks COM API
- 创建真实 `.SLDPRT` 和 `.STEP` 文件
- 设置 `RealCadExecuted = true`
- 执行真实的建模命令（`ExtrudeBoss`、`CutExtrude` 等）

这与 `SupportsRealBuild => false` 的语义直接冲突 — 代码正在执行"真实构建"，但声明"不支持真实构建"。

self-check 报告中也存在同样的矛盾：
- `solidworks_real_build_not_implemented: true`（第 134 行）
- `solidworks_real_plate_build_implemented: true`（第 136 行）

两者同时为 `true`，阅读报告时会产生困惑。

**当前风险评估**: 低（不影响安全性）。`SupportsRealBuild` 不在任何安全门控路径中使用 — 三重安全开关独立工作。但这是一个技术债务，会误导未来的代码阅读者和 self-check 报告消费者。

**建议修复**: 两选一：
1. 将 `SupportsRealBuild` 重命名为 `SupportsGenericRealBuild`，明确语义（"通用真实构建" vs "特定模板构建"）
2. 当 `SupportsPlateBasicFourHolesBuild` 为 `true` 时，将 `SupportsRealBuild` 改为 `true`（语义上"plate 构建是真实构建的一种"）

推荐方案 1，因为它保持了"通用构建不支持"的安全声明，同时不产生矛盾。

### 架构风险 A-003：`LateBoundSolidWorksPlateBuilder.BuildCore` 使用 `.GetAwaiter().GetResult()` 进行同步-over-异步 — 线程池浪费

**位置**: `src/Workers/SolidWorks/SolidWorksPlateBuilder.cs:244` 和 `:292`

```csharp
SolidWorksPlateBuildReportWriter.WriteAsync(...).GetAwaiter().GetResult();
```

**问题**: `SolidWorksPlateBuildReportWriter.WriteAsync` 是异步方法（`async Task`），但 `BuildCore` 在 `Task.Run` 线程池线程上通过 `.GetAwaiter().GetResult()` 同步阻塞等待它。

当前不会死锁（线程池线程无 `SynchronizationContext`），但：
- 阻塞了一个线程池线程等待文件 I/O
- 如果线程池在负载下耗尽，新的 `Task.Run` 请求将排队
- 违反了"async all the way"原则

**建议修复**: 将 `BuildCore` 改为真正的异步方法，或使报告写入同步：
```csharp
// 方案 A: BuildCore 改为 async
private static async Task<SolidWorksPlateBuildResult> BuildCoreAsync(...)
{
    // ...
    await SolidWorksPlateBuildReportWriter.WriteAsync(...);
    // ...
}

// 方案 B: 提取同步写入方法
SolidWorksPlateBuildReportWriter.Write(reportPath, ...);  // 同步版本
```

## 5. 可靠性风险

### 可靠性风险 R-001：`RealSolidWorksWorker.ExecuteAsync` 中 DisconnectAsync 仍使用 `CancellationToken.None` — 无超时保护

**位置**: `src/Workers/SolidWorks/RealSolidWorksWorker.cs:189`（未变，与 V1.0-A 相同）

```csharp
await _sessionManager.DisconnectAsync(CancellationToken.None);
```

**问题**: 这是上一轮审查 MEDIUM-001 的同一问题，**未修复**。在真实构建完成后，`finally` 块中的 disconnect 仍然使用 `CancellationToken.None`。如果 COM 释放阻塞（例如 SolidWorks 正在弹出"是否保存更改？"对话框），此调用将永久挂起。由于它在 `finally` 块中，会阻塞整个 `ExecuteAsync` 的返回。

在 V1.0-B 中，这个风险更高了 — 真实构建执行后 SolidWorks 更可能处于需要清理的状态（打开了文档、修改了模型）。

**建议修复**: 使用 `ConnectTimeoutSeconds` 作为断开超时：
```csharp
using var disconnectCts = new CancellationTokenSource(
    TimeSpan.FromSeconds(options.ConnectTimeoutSeconds));
try
{
    await _sessionManager.DisconnectAsync(disconnectCts.Token);
}
catch (OperationCanceledException)
{
    logs.Add("solidworks_disconnect_timeout: COM release timed out.");
}
```

### 可靠性风险 R-002：`SolidWorksPlateBuildOutput.ResolveOutputDirectory` 时间戳碰撞风险

**位置**: `src/Workers/SolidWorks/SolidWorksPlateBuilder.cs:58-61`

```csharp
return Path.Combine(
    Path.GetDirectoryName(target) ?? fullRoot,
    $"plate_basic_4holes_{DateTimeOffset.UtcNow:yyyyMMdd_HHmmss_fff}");
```

**问题**: 如果两个真实构建在同一毫秒内启动，它们会获得相同的输出目录名。第二个构建会覆盖第一个的文件。

**风险**: 低概率 — 需要两个真实构建在 1ms 内同时启动，且通过所有安全开关。但这是确凿的竞态条件。

**建议修复**: 在时间戳后追加 GUID：
```csharp
$"plate_basic_4holes_{DateTimeOffset.UtcNow:yyyyMMdd_HHmmss_fff}_{Guid.NewGuid():N}"
```

### 可靠性风险 R-003：`SolidWorksArtifactValidator.IsUnderOutputSolidWorksRealSegment` 路径检查逻辑有缺陷

**位置**: `src/Modules/CADModeling/validators/SolidWorksArtifactValidator.cs:216-238`

```csharp
private static bool IsUnderOutputSolidWorksRealSegment(string fullPath)
{
    var directory = new FileInfo(fullPath).Directory;
    var sawReal = false;
    while (directory is not null)
    {
        if (!sawReal && directory.Name.Equals("real", StringComparison.OrdinalIgnoreCase))
        {
            sawReal = true;
        }

        if (sawReal &&
            directory.Name.Equals("solidworks", StringComparison.OrdinalIgnoreCase) &&
            directory.Parent?.Name.Equals("output", StringComparison.OrdinalIgnoreCase) == true)
        {
            return true;
        }

        directory = directory.Parent;
    }

    return false;
}
```

**问题**: 该方法在目录树中向上遍历，寻找 `output/solidworks/real` 路径段。逻辑要求先遇到 `real`，再遇到 `solidworks`（父目录为 `output`）。

但是，考虑路径 `D:\output\real\solidworks\myfile.SLDPRT`：
- 向上遍历：`solidworks` → 但此时 `sawReal` 还是 `false`（还没遇到 `real`）
- 继续：`real` → `sawReal = true`
- 继续：`output` → 但检查要求 `directory.Name == "solidworks"` 且 `directory.Parent?.Name == "output"` — 不匹配！
- 继续：`D:\` → 结束

所以这个路径会被**错误地拒绝**！虽然在实际使用中不太可能出现 `output/real/solidworks` 这样的目录结构，但算法的脆弱性是真实的。

**建议修复**: 使用更健壮的路径验证——规范化后检查是否在预期根目录下：
```csharp
var expectedRoot = Path.GetFullPath(Path.Combine(projectRoot, "output", "solidworks", "real"));
return normalizedPath.StartsWith(expectedRoot, StringComparison.OrdinalIgnoreCase);
```

### 可靠性风险 R-004：`SolidWorksPlateBuilder.ExitSketch` 和 `EnterSketch` 实现相同 — 依赖 SolidWorks API 隐式行为

**位置**: `src/Workers/SolidWorks/SolidWorksPlateBuilder.cs:316-320`

```csharp
private static void EnterSketch(object model) =>
    Invoke(GetProperty(model, "SketchManager"), "InsertSketch", true);

private static void ExitSketch(object model) =>
    Invoke(GetProperty(model, "SketchManager"), "InsertSketch", true);
```

**问题**: 两个方法有**完全相同**的实现（都调用 `InsertSketch(true)`）。这依赖于 SolidWorks API 的一个隐式行为：当 sketch 已打开时，再次调用 `InsertSketch(true)` 会关闭当前 sketch。

此行为：
- 不是 SolidWorks API 文档中明确保证的契约
- 在 SolidWorks 不同版本间可能变化
- 对不熟悉 SolidWorks API 的开发者来说非常困惑

**建议修复**: 最简方案 — 添加注释说明此行为。更好的方案 — 使用显式的退出方法（如果 API 支持），或在 ExitSketch 中添加校验（调用后验证不再处于 sketch 编辑模式）。
