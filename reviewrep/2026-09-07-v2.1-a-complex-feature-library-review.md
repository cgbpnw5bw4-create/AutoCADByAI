## 4. 高优先级问题

### HIGH-001：`seed_feature` 的校验按单个 id、执行按多个 id，可静默扩大到证据之外

**位置**
- `src/Workers/SolidWorks/Features/RealSolidWorksFeatureAdapter.cs:581-607`（`ResolveSeedFeatures`）
- `src/Workers/SolidWorks/Features/Pattern/PatternParameterRules.cs:17-42`（`ValidateSeedAndCount`）
- `src/Workers/SolidWorks/Features/Pattern/{Linear,Circular}PatternHandler.cs` 的 `ParameterSchema`

**问题**

三处对同一个参数的理解不一致：

| 位置 | 对 `seed_feature` 的理解 |
|---|---|
| Handler `ParameterSchema` | `"feature_id"`，**单个** |
| `ValidateSeedAndCount` | 当作**单个字符串**整体与 `ReferencedFeatures` 比对 |
| `ResolveSeedFeatures` | `.Split([';', ','])`，**允许多个** |

并且 `ValidateSeedAndCount` 的绑定检查带前置条件：

```csharp
if (feature.ReferencedFeatures.Count > 0 &&
    !feature.ReferencedFeatures.Contains(seed, StringComparer.OrdinalIgnoreCase))
```

`ReferencedFeatures` 为空时**整个检查被跳过**。因此 `seed_feature = "a;b"` 且 `referenced_features = []` 的规格可以通过全部校验，然后由适配器阵列**两个**种子。

**风险**

1. **超出已取证的参数档案。** `single_direction_linear_pattern;criteria_resolved_direction;principal_axis_cross_checked` 这个档案是在单种子条件下采集的，多种子行为从未被诊断覆盖，却能进入真实执行。
2. **绕过 FeatureGraph 依赖。** `referenced_features` 为空意味着图中没有依赖边，编译器不保证阵列排在种子之后。此时 `_features` 查不到会失败（fail-closed），但失败发生在**连接 COM 之后**，而本项目的设计原则是证据不足要在连接 COM 之前拒绝。
3. 与镜像不一致：`MirrorHandler.Validate` 是**先拆分再逐个比对**的（`MirrorHandler.cs` 中 `target_features` 的处理），只有阵列这两个 Handler 没跟上。

**建议修复**

1. `ValidateSeedAndCount` 改为先按 `[';', ',']` 拆分，再要求**恰好一个** id（schema 声明的是单数），多于一个直接返回 `invalid_feature_parameter`。
2. 去掉 `ReferencedFeatures.Count > 0` 这个前置条件——种子必须出现在 `referenced_features` 中是**无条件要求**，否则依赖边不存在。镜像的同名前置条件一并去掉。
3. 若确实需要多种子阵列，那是一个新的参数档案，必须单独取证，不能靠拆分器默默支持。

### HIGH-002：阵列方向依赖边的定向，而边的定向本身被文档标注为「不可依赖」

**位置**
- `src/Workers/SolidWorks/Features/RealSolidWorksFeatureAdapter.cs:385`（`FeatureLinearPattern4` 的 `FlipDir1` 实参恒为 `false`）
- `src/DomainSchemas/EdgeSelection.cs`（`EdgeDirection` 的文档注释）

**问题**

`EdgeDirection` 的注释是我自己写的，原文：

> 方向有符号但符号不可依赖：SolidWorks 的边定向取决于拓扑生成顺序。需要确定朝向时用特征自身的 reverse 选项，不要靠这里的正负号。

而适配器把 `FlipDir1` 硬编码成 `false`，即**完全依赖那个被声明为不可依赖的符号**。规格层也没有任何参数可以表达「往哪边阵列」——`direction` 只能填 `x`/`y`/`z`，`ResolveAxisEdge` 的平行性校验用的是 `Math.Abs(cosine)`，**正负都算通过**。

诊断能过是因为解出的那条棱恰好指向 +X，实例落在 x = -30/-10/10/30。若同一条棱在某次重建后定向翻转，实例会落到 x = -50/-70/-90，全部在板外。

**风险**

- 该失败模式**通常是响亮的**（SolidWorks 报错或实例创建失败），不是静默的假成功——这是它没被评为 BLOCKER 的原因。
- 但存在静默变体：若种子靠近零件中心、两侧都有材料，翻转后阵列**照样能建出来**，只是长在了对称的另一侧。此时体积变化量与正确情况完全相同，闭式解对照也过，只有落点探针能发现——而落点探针只在采证时跑，运行期不跑。
- 更根本的问题是：**规格无法表达一个必须表达的意图**。用户说「沿 x 方向排 4 个」，系统实际执行的是「沿这条棱恰好被 SolidWorks 定成的那个方向排 4 个」。

**建议修复**

1. `LinearPatternHandler` 增加可选参数 `direction_sign`（`positive` / `negative`，默认 `positive`），语义定义为**相对于声明的主轴正方向**而非相对于边。
2. 适配器把带符号的 `cosine`（不取绝对值）与 `direction_sign` 组合，算出 `FlipDir1` 实参，而不是恒 `false`。
3. `ResolveAxisEdge` 保留 `Math.Abs` 用于「是否平行」的判断，但把符号返回给调用方使用。
4. 圆周阵列的 `FlipDirection` 同理（当前也恒为 `false`，`angle_deg=360` 时不可见，非 360 度时会暴露）。

### HIGH-003：`EdgeDirection` 是新引用模型的核心数据，却没有任何单元测试

**位置**
- `src/Workers/SolidWorks/Features/SolidWorksEdgeEnumerator.cs`（`Normalize`、圆边取 `CircleParams[3..5]`、直线边取端点差）
- `tests/PlatformSelfCheck.Tests/V21AEdgeSelectionTests.cs`（195 行，**零处提及 `Direction`**）

**问题**

线性阵列的方向和圆周阵列的轴**全部**来自 `MeasuredEdge.Direction`。该字段的计算是纯逻辑，完全可单测：

- 圆边：`CircleParams` 索引 3/4/5 —— **索引取错不会有任何症状**，只会得到一个错误但合法的向量
- 直线边：端点差归一化
- `Normalize` 的零长度保护（返回 `null` 而非 `(0,0,0)`）

`V21AEdgeSelectionTests` 的夹具是真实探测的 16 条边，是很好的基础，但它们全部使用 `Direction = null`（默认值），从未构造过带方向的边。整个方向/轴模型**只被真机诊断覆盖过一次**。

**风险**

- 这是全项目历史上反复出现的模式的新形态：**保护存在于取证那一刻，不存在于代码里**。诊断是一次性的、需要 SolidWorks 的、不在 CI 中的；单测是每次提交都跑的。把唯一验证放在前者，等于该逻辑此后无人看守。
- 具体的静默失效路径：若有人重构 `CircleParams` 的索引或改动归一化，386 个测试全部通过，自检全绿，只有下次真机采证才会发现——而采证只在改动 `BoundSourcePaths` 时才被强制。

**建议修复**

在 `V21AEdgeSelectionTests` 中新增（不需要 SolidWorks）：

1. `Normalize` 的三个用例：普通向量归一化后模长为 1；零向量返回 `null`；非有限值返回 `null`。
2. 用真实探针数据构造带 `Direction` 的 `MeasuredEdge` 夹具：板顶面 100 mm 棱的方向应为 `(±1, 0, 0)`；中心孔顶面孔口的轴应为 `(0, ±1, 0)`。
3. 平行性交叉校验的判据本身（当前在适配器私有方法里，见 MEDIUM-004）：与主轴同向、反向、45 度三种情况，前两者通过、后者拒绝。

## 5. 中优先级问题

### MEDIUM-001：圆周阵列的轴只校验方向、不校验位置，而位置才是决定性的

**位置**：`RealSolidWorksFeatureAdapter.cs`（`ResolveAxisEdge` 的平行性校验）

**问题**

对线性阵列，方向是**位置无关**的：板上 4 条沿 X 的棱，无论解出哪一条，阵列结果完全相同。因此「平行于声明主轴」是一道有效的第二道闸。

对圆周阵列不然：轴是一条**有位置的直线**，绕 (0,0) 转和绕 (20,0) 转结果完全不同。而交叉校验只比对 `Direction`，**对圆心位置没有任何断言**。

现有保护只有 `ExpectedCount == 1`：判据必须唯一命中。这确实挡住了「命中多条随便挑一条」，但挡不住「判据写得能唯一命中，可命中的是另一个孔」——尤其在参数化改动导致孔位移动之后。

**风险**：中。要触发需要判据写错且仍唯一命中；一旦触发，阵列绕错误中心展开，体积变化量可能与正确情况相同（同样是 3 个 Ø6 通孔），闭式解对照**无法区分**。

**建议修复**：`CircularPatternHandler` 增加可选参数 `axis_origin_x_mm` / `axis_origin_z_mm`，适配器把解出圆边的锚点与之比对，超出容差即拒绝。语义与 `direction` 一致：声明意图，与解出的实体互相印证。

### MEDIUM-002：`Dispose` 清理了 `_sketches` 却没有清理 `_features`

**位置**：`RealSolidWorksFeatureAdapter.cs:790-813`

**问题**：`Dispose` 释放全部 `_ownedReferences` 后清空 `_ownedReferences`、`_ownedReferenceSet`、`_sketches`，唯独遗漏 `_features`（`:70` 声明，`:1008` 写入）。`_features` 中持有的正是刚被 `ReleaseComObject` 释放的那些 RCW。

**风险**：低-中。适配器由工厂按模型创建，实例随构建结束而废弃，当前无重用路径，因此没有已知的触发场景。但这是一个**与相邻代码不一致的遗漏**，一旦将来有人复用适配器实例或在 dispose 后做诊断快照，就会拿到悬空引用。

**建议修复**：在 `_sketches.Clear();` 之后加 `_features.Clear();`。一行，无风险。

### MEDIUM-003：两层参数 schema 的一致性刚出过事故，仍无测试锁住

**位置**：`src/DomainSchemas/FeatureParameterSchemaRegistry.cs:103-106`，各 Handler 的 `ParameterSchema`

**问题**

本轮修掉了一个存在已久的矛盾：规格层 `ValidPattern` 要求参数名 `count`，而 Handler 声明 `instance_count` 且拒绝未声明参数——**任何阵列规格都不可能同时通过两层**。它一直没暴露，只因为阵列从未真正执行过。

修复方式是把规格层改成 `instance_count`。但**没有任何测试保证这两层继续一致**，下一个新特征完全可能重犯。

**风险**：中。同类矛盾再次出现时，症状是「dry-run 就失败」，属于响亮失败而非假成功，但会在采证阶段才被发现，浪费一轮真机运行。

**建议修复**：新增测试，对 `FeatureHandlerRegistry.CreateDefault()` 中每个 Handler，用其 `ParameterSchema` 里全部 `Required = true` 的参数构造最小 `FeatureDefinition`，断言 `FeatureParameterSchemaRegistry.Validate` 通过。这把两层的一致性变成一条机械可验的断言。

### MEDIUM-004：适配器本轮新增的判定逻辑全部无单元测试

**位置**：`RealSolidWorksFeatureAdapter.cs` 的 `ResolveAxisEdge`、`RequiredPrincipalAxis`、`ResolveSeedFeatures`、`RequiredInstanceCount`、`VerifyCreatedFeatureKind`

**问题**：这些方法承载本轮全部新增的 fail-closed 判定（判据唯一性、边类别匹配、方向平行性、种子可解析、实例数下界、特征类别回读），全部是 `private` 且依赖 `_com`/`_model`，因此只能由真机诊断覆盖。`grep` 确认测试目录中零处提及。

**风险**：中。与 HIGH-003 同源但范围更广。适配器整体历史上就依赖真机验证，本轮新增 617 行使这个缺口显著变大。

**建议修复**：把不依赖 COM 的纯判定抽成 `internal static`（`RequiredPrincipalAxis`、平行性判据、种子 id 拆分与校验、实例数校验），交由单测覆盖；依赖 COM 的部分（`VerifyCreatedFeatureKind`、`SelectEntity`）保持现状由诊断覆盖。不需要引入 COM mock。

### MEDIUM-005：`DiagnosticFeatureTypes` 仍是硬编码白名单

**位置**：`tools/SolidWorksFeatureExecutionSmokeRunner/FeatureExecutionSmokeRunner.cs:120-133`

**问题**：本轮往这个 `HashSet` 里加了三个类型，但**没有改变它的形态**。当前它列出了 9 个类型中的 9 个（即「全部已注册」），因此这个白名单事实上已不再起过滤作用，只保留了它的失败模式：新增 Handler 而忘记加入时，诊断以 `unsupported_feature_type` 拒绝，错误信息指向注册表，而真正的原因在这个白名单里。

本轮就真实踩到过一次：倒角首次诊断失败于 `unsupported_feature_type: no handler is registered for chamfer`，而 `ChamferHandler` 明明已注册。

**风险**：中。失败是响亮的，但错误信息**指向错误的地方**，会消耗排查时间。

**建议修复**：二选一——(a) 若确实需要限制诊断范围，改为显式排除列表并在拒绝时给出「该类型不在诊断白名单」而非「未注册」的信息；(b) 若不再需要限制，直接删除白名单，改用注册表全集。

## 7. 架构评估

> **本节全部为自评**，被评价的架构决策由我本人做出，建议由未参与者复核。

- **边界一致性**：保持。Handler 不接触 COM（自检 `feature_handler_no_direct_com_access` 行为式验证，本轮曾因硬编码计数退化，已修复并纳入基线）。`CreatedObject` 继续只承载纯数据 `FeatureAdapterArtifact`，COM 句柄改由适配器内部 `_features` 持有——这个选择我认为是对的：把 IFeature 放进跨边界的 `ExecutionState` 会直接违反「Handler 不得拿到原始特征 RCW」。
- **接口稳定性**：`ISolidWorksFeatureAdapter` 未变。`MeasuredEdge` 新增 `Direction` 使用尾部可选参数，未破坏既有构造点。
- **耦合风险**：低。五个特征共用一套选择模型，没有新增零件专用逻辑，没有 `switch (feature_type)`。
- **扩展风险**：**中，且是本轮最值得关注的一点**。当前设计要求每个需要方向/轴的特征都在规格中写一段 `EdgeSelectionCriteria` JSON。这对「板上有一条 100 mm 棱」这类场景可用，但对参数化零件族，判据里的 `anchor_*` 是**绝对坐标**，随参数变化而失效。V2.1-A 的样例是固定尺寸诊断件，尚未暴露这个问题；一旦把阵列接入 `plate_basic_4holes` 这类参数化族，判据需要能表达相对量（如「顶面沿长边的棱」）。**这是下一阶段必须先解决的设计问题，不是实现细节。**
- **Workflow 兼容性**：保持。所有特征仍走 `FeatureGraph → BuildPlanCompiler → Registry → Handler → Adapter → GeometryValidator → QualityGate`，未新增队列、未绕过 QualityGate。

## 8. CAD / COM / 外部运行时风险评估

- **外部应用生命周期**：未变更。适配器沿用 `Own()` 登记 + `Dispose` 逐个 `ReleaseComObject` 的既有模式，本轮新增的 `CreateSelectData`、`GetDefinition`、`FirstFeature`/`GetNextFeature` 遍历均经 `Own()` 登记。遗漏见 MEDIUM-002（不影响释放，只影响字典清理）。
- **文件 I/O 安全性**：诊断产物写入 `--output` 指定目录，取证时显式指向 `evidence/solidworks`。注意 `output/solidworks/` 被 gitignore 吞掉，这是既有陷阱，本轮通过显式 `--output` 规避，但**规避方式依赖操作者记得加参数**，未固化为默认值。
- **Retry / Timeout 行为**：本轮未引入重试。选择集操作全部单次执行，失败即 `Stage(...)` 抛出并由 `Guard` 转为 `FeatureHandlerExecutionResult.Failed`，无静默吞异常。
- **失败恢复能力**：fail-closed 完整。判据非法 → `edge_selection_invalid_criteria`；命中数不符 → `edge_selection_ambiguous`（错误信息含 "refusing to guess"）；方向不平行 / 边类别不符 → `edge_selection_ambiguous`；种子解析不到 → `feature_result_invalid`；特征类别不符 → `feature_result_invalid`。**每一条都在错误信息中说明了拒绝的具体原因和实测值**，可执行性良好。
- **日志与可追踪性**：诊断报告记录 `result_object_validated` / `rebuild_passed` / `geometry_change_validated` 三个独立布尔 + 体积前后值，可事后复核。**但运行期不记录「判据解出了哪条边（index / anchor）」**——出问题时无法从日志判断选中的是不是预期那条，只能重跑探针。建议在 `SelectEdgesByCriteria` 与 `ResolveAxisEdge` 成功路径上各加一条日志，记录解出边的 index、kind、anchor 与 direction。

**特别记录一次被读回校验拦下的静默失败**：本轮曾尝试 `CreateDefinition` + 显式引用属性路线，`TrySetProperty("D1Axis", edge)` **返回成功但属性读回为 null**。若当时信了返回值，会带着一个没有方向引用的定义调用 `CreateFeature`，产出沿默认方向铺开的错误阵列。这条经验已写入三份 `api_evidence.md`，结论是「设置成功不等于写进去了」。

## 12. 最终结论

**PASS WITH COMMENTS —— 可以接受，但建议优化。**

V2.1-A 达成了它声明的目标，且验收强度高于本项目历史上任何一轮：五个复杂特征全部真机取证，每个都用闭式解与只读探针做了双重独立复核，没有出现「有文件、字段为 true 就算成功」的情况。实体引用这个自 V2.0-B 起就存在的模型缺口被一套统一方案解决，没有为每种特征各造一套。本轮还终结了一个反复出现七轮以上的模式——这次是在「谁来保护保护者」的位置上加锁，而不是又叠一层新保护。

不建议阻塞：三个 HIGH 中，HIGH-001 需要构造异常规格才能触发，HIGH-002 的主要失败形态是响亮的，HIGH-003 是覆盖缺口而非现存缺陷。当前 386 个测试全绿、自检能力回归闸通过、九个 Handler 的证据绑定全部有效。

但按协议第 9 节「假成功比显式失败更危险」，HIGH-001（超出已取证档案）与 HIGH-002 的静默变体（阵列长在对称的另一侧、体积完全相同）属于该类别，**应优先于任何新功能处理**。

**关于是否进入下一阶段**：技术上可以。但第 7 节「扩展风险」与修复计划第 11 项指出的问题——判据使用绝对坐标、无法承受参数化——会在阵列/镜像接入真实零件族的**第一天**就暴露。建议下一阶段的第一件事是设计相对判据，而不是继续加特征。

**最后重申独立性限制**：本报告审查的代码全部由我编写，第 7 节架构评估与「验收强度高于历史任何一轮」这类判断属于自评，建议由未参与本轮开发的审查者复核。客观取证部分（测试输出、体积数值、源码行号引用、两层矛盾的存在性）不受此限制。
