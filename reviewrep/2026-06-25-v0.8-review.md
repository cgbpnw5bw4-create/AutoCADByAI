## 5. 中优先级问题

### MEDIUM-001: self-check 中反射访问 `_httpClient` 私有字段脆性高

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:958` — `RunRuntimeReliabilityChecks`

**问题**:
```csharp
var httpClientField = openAIClientType.GetField("_httpClient", BindingFlags.NonPublic | BindingFlags.Instance)
    ?? throw new MissingFieldException(openAIClientType.FullName, "_httpClient");
var httpClient = httpClientField.GetValue(configuredClient) as HttpClient;
openAIClientTimeoutConfigured = httpClient?.Timeout == TimeSpan.FromSeconds(7);
```

此段代码通过反射访问 `OpenAICompatibleModelClient` 的私有字段 `_httpClient`。如果字段被重命名、改为属性、或改为 `HttpMessageHandler`（例如改用 `IHttpClientFactory`），此 self-check 将静默失败（被外层 `catch` 吞掉），返回 `openAIClientTimeoutConfigured = false`。

**风险**: 重构时 self-check 假失败——`openAIClientTimeoutConfigured` 为 false 但实际功能正确。这是 `failure_report_lying` 的另一种形式。

**建议修复**: 在 `OpenAICompatibleModelClient` 上暴露一个 `internal` 属性以供测试/self-check 使用，或通过 behavior-based 验证（例如 `RuntimeConfigurationReadsAndBoundsTimeoutSeconds` 测试已覆盖的部分）来替代反射访问私有字段。

### MEDIUM-002: self-check 通过源码文本搜索验证 `apiKeyNotLogged` 存在误判风险

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:986-989`

**问题**:
```csharp
apiKeyNotLogged =
    !invokerSource.Contains("ApiKey", StringComparison.OrdinalIgnoreCase) &&
    !invokerSource.Contains("Authorization", StringComparison.OrdinalIgnoreCase) &&
    !openAIClientSource.Contains("ex.Message", StringComparison.OrdinalIgnoreCase);
```

此方法通过搜索 `MicrosoftRuntimeAgentInvoker.cs` 源码中是否包含 "ApiKey" 或 "Authorization" 字符串来验证凭据不会泄露到日志中。但 `RuntimeConfiguration.ApiKey` 属性名本身包含 "ApiKey"——如果代码中有任何引用 `configuration.ApiKey` 的判断逻辑，self-check 将误判。

**当前情况**: `OpenAICompatibleModelClient.cs:43` 中有 `configuration.ApiKey is null` 但 self-check 搜索的是 `invokerSource`（即 `MicrosoftRuntimeAgentInvoker.cs`），不在同一文件。当前逻辑是巧合正确的，但依赖隐式知识。

**风险**: 如果 Codex 未来在 `MicrosoftRuntimeAgentInvoker.cs` 中添加对 `ApiKey` 的属性访问守卫逻辑（例如在调用 client 前预检），此 check 将假失败。

**建议修复**: 将验证逻辑改为基于行为的集成测试（已存在于 `AgentRuntimeMicrosoftTests` 的 `DoesNotContain("test-key")` 和 `DoesNotContain("Authorization")` 断言），而非对源码的字符串搜索。

### MEDIUM-003: `SequentialWorkflowEngine` 部分调用点未传 CancellationToken

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:72` — `RunAsync` 方法

**问题**: `platform.WorkflowEngine.ExecuteAsync(steps, context)` 未传 `CancellationToken`。`SequentialWorkflowEngine.ExecuteAsync` 签名已更新为 `(steps, context, cancellationToken = default)`，向后兼容，但 self-check 执行期间如果用户取消不会传播。

**风险**: 低——self-check 是启动时诊断，不涉及长时间运行的生产 Workflow。但如果 self-check 卡住（例如 retry delay 很长的某个步骤），无法取消。

**建议修复**: 为 `RunAsync` 添加可选的 `CancellationToken` 参数并传递给 `ExecuteAsync`。

## 6. 低优先级问题 / 细节建议

### LOW-001: `OpenAICompatibleModelClient` 构造函数链过长 (5 个重载)

**位置**: `src/AgentRuntime.Microsoft/OpenAICompatibleModelClient.cs:12-35`

**问题**: 5 个构造函数形成复杂重载链:
```
() → (TimeSpan) → (TimeSpan, HttpClient?)
(configuration) → (configuration, null) → (TimeSpan, HttpClient?)
```

V0.7 审查中 I8 建议简化 `MicrosoftAgentAdapter` 的重载链。此处同样适用。

**建议**: 保留 2 个核心构造函数: `(TimeSpan, HttpClient?)` 和 `(RuntimeConfiguration, HttpClient?)`。移除无参构造函数（通过 `RuntimeConfiguration.DefaultTimeoutSeconds` 常量已有清晰默认值）。

### LOW-002: `CancellationToken` 在 `WorkflowContext` 之外传递但与 Context 结构不一致

**位置**: `SequentialWorkflowEngine.cs:35` — `ExecuteAsync(IEnumerable<WorkflowStep> steps, WorkflowContext context, CancellationToken cancellationToken)`

**问题**: `WorkflowContext` 是 Workflow 的聚合参数对象，但 `CancellationToken` 作为独立参数传递。如果某处只传 `context` 而忘记传 token，取消不会生效。

**建议**: 未来考虑将 `CancellationToken` 纳入 `WorkflowContext`。当前不属于紧急问题，`default` 值保证向后兼容。

### LOW-003: `runtimeTimeoutConfigSupported` 检查只验证 `MaxTimeoutSeconds` 钳制，未验证 `MinTimeoutSeconds`

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:907-909`

**问题**:
```csharp
runtimeTimeoutConfigSupported =
    GetInt(timeoutConfig, "TimeoutSeconds", 0) == 7 &&
    GetInt(excessiveTimeoutConfig, "TimeoutSeconds", 0) == maxTimeout;
```

此检查验证了上限钳制 (9999 → `MaxTimeoutSeconds`)，但未验证下限钳制 (0 → `MinTimeoutSeconds`)。`RuntimeConfigurationReadsAndBoundsTimeoutSeconds` 单元测试已覆盖下限场景，但 self-check 运行时不验证。

**建议**: 添加一个 `belowMinTimeoutConfig` 检查:
```csharp
var belowMinTimeoutConfig = InvokeRuntimeConfigurationFromEnvironment(
    fromEnvironment,
    new Dictionary<string, string?> { ["AI_TIMEOUT_SECONDS"] = "-5" });
runtimeTimeoutConfigSupported =
    GetInt(timeoutConfig, "TimeoutSeconds", 0) == 7 &&
    GetInt(belowMinTimeoutConfig, "TimeoutSeconds", 0) == minTimeout &&
    GetInt(excessiveTimeoutConfig, "TimeoutSeconds", 0) == maxTimeout;
```

## 7. 架构评估

- **边界一致性**: ✅ 优秀。`RuntimeProviderException` 放在 `AgentRuntime.Microsoft` 项目中，不泄露到 Contracts 或 PlatformCore。`IssueType` 被 `MicrosoftRuntimeAgentInvoker` 消费后转换为平台 `AgentOutput`，类型不会跨层传播。

- **接口稳定性**: ⚠️ 注意。`SequentialWorkflowEngine.ExecuteAsync` 新增 `CancellationToken` 参数。由于使用 `default` 值，现有调用点无需修改即可编译通过——向后兼容性保持。`MicrosoftWorkflowRuntime.ExecuteAsync` 也新增了 token 参数，需确认所有调用点已更新。

- **耦合风险**: ✅ 低。`OpenAICompatibleModelClient` 和 `RuntimeProviderException` 之间的耦合是单向的（Client → Exception），Exception 不依赖任何平台类型。

- **扩展风险**: ✅ 受控。`RuntimeProviderException.IssueType` 使用字符串分类（而非枚举），未来新增错误类型（如 `"quota_exceeded"`, `"content_filter"`）无需改 API。

- **Workflow 兼容性**: ✅ 保持。CancellationToken 新增不影响现有 Workflow。`Failed`/`NeedsHumanApproval` 的不等待 retry delay 测试已验证。

---

## 8. CAD / COM / 外部运行时风险评估

- **外部应用生命周期**: ✅ 安全。无 COM 对象创建。`HttpClient` 通过 `CreateOwnedHttpClient` 创建时设置 `Timeout` 属性。

- **文件 I/O 安全性**: ✅ 安全。self-check 的 `File.ReadAllText` 仅读取已知位置的源码文件，用于文本搜索验证。

- **Retry / Timeout 行为**: ✅ 优秀。
  - **双层超时防护**: `HttpClient.Timeout` + `CancelAfter(TimeoutSeconds)` ——前者控制连接层，后者控制请求整体生命周期
  - **CancellationToken 全程传播**: `ExecuteAsync` → `while(true)` → `step.ExecuteAsync(context)` → `Task.Delay(retryDelay, cancellationToken)`
  - **取消 retry delay 测试验证**: 50ms 取消 5s retry delay，只执行 1 次
  - **Failed/NeedsHumanApproval 不等待 retry delay**: 5s delay 策略在 Failed/NeedsHumanApproval 时 < 1s

- **失败恢复能力**: ✅ 优秀。`OpenAICompatibleModelClient` 的异常转换链:
  - `HttpRequestException` → `RuntimeProviderException("auth_error"|"rate_limit"|"provider_error"|"network_error")`
  - `OperationCanceledException` (非外部取消) → `RuntimeProviderException("timeout")`
  - `JsonException` → `RuntimeProviderException("invalid_provider_response")`
  - 全部被 `MicrosoftRuntimeAgentInvoker` 的 `catch (RuntimeProviderException ex)` 捕获，转换为 `AgentOutputStatus.Failed` + Issues

- **日志与可追踪性**: ✅ 优秀。`RuntimeProviderException.IssueType` 记录到审计日志。凭据不泄露——测试断言 `DoesNotContain(test-key)`、`DoesNotContain(Authorization)`。
