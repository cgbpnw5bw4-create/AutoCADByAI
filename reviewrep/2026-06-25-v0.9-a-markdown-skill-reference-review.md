## 4. Improvements

以下为建议优化但不阻塞的问题：

### 4.1 【建议】Validator 的英文比例阈值应可配置

**当前状态：** `MarkdownChineseValidator.IsEnglishHeavy()` 硬编码了 `englishCount < 80` 的最小阈值和 `ratio >= 0.65 && englishCount > chineseCount * 2` 的判断条件。

**问题：** 如果将来需要调整阈值（例如放宽到 0.7 或收紧到 0.6），必须修改源码并重新编译。

**建议：** 在 `MarkdownChineseValidator` 中增加构造函数参数或配置读取。同时考虑在独立的 markdown 策略配置文件中定义阈值，由 self-check 读取。

**严重程度：** 低。当前阈值合理，不影响功能。

### 4.2 【建议】需要白名单机制豁免特定文件

**当前状态：** `MarkdownChineseValidator.ShouldSkip()` 只按目录名跳过 `.git`、`bin`、`obj`、`output`，没有内容级白名单。

**问题：** 如果将来项目添加 `LICENSE.md`（许可证原文，必须保留英文），或添加 `CHANGELOG.md`（国际通用格式），会导致 self-check 失败。

**建议：** 增加文件级白名单，例如在 `markdown_standard.md` 中定义可豁免的文件列表，或通过文件头部的 frontmatter/metadata 标记（如 `<!-- markdown-lang: exempt -->`）跳过检查。

**严重程度：** 低。当前项目暂无此类文件，不影响 V0.9-A。

### 4.3 【建议】将违反结果分为 Warning 与 Failed 两级

**当前状态：** `MarkdownChineseValidator.Validate()` 只返回 `"Passed"` 或 `"Failed"` 两种最终状态。任何文件的任何一个段落英文比例超标，整个 self-check 立即失败。

**问题：** 在 V0.9-B 开发阶段，如果新增模块的 README.md 草稿暂时包含英文，会导致 self-check 失败，影响开发迭代效率。

**建议：** 区分两个严重级别：
- **Warning**：新增文件英文比例超标（最近一次 git commit 引入的文件），self-check 仍然 Passed，但输出 Warning。
- **Failed**：已有文件（之前已通过检查的文件）英文比例退化，self-check Failed。

实现方式：对比 git diff 或维护一个已通过检查的文件列表。

**严重程度：** 中低。目前所有文件均通过，不影响 V0.9-A。但 V0.9-B 新增 SolidWorks Module 草稿时可能触发。

### 4.4 【建议】`SlashPathPattern` 正则可能产生误判

**当前状态：** `SlashPathPattern = new Regex(@"(?:[\w.-]+/)+[\w.-]+")` 用于过滤路径。但此正则会匹配类似 `this/is/a/test` 的英文短语。

**问题：** 如果有人写了 `"This module handles CAD/BIM/CAE integration"`，`CAD/BIM/CAE` 会被误判为路径而跳过检查，但实际上这是英文说明。

**建议：** 收紧 SlashPathPattern，要求至少包含一个已知的文件扩展名（如 `.cs`、`.md`、`.dll`）或目录前缀（如 `src/`、`docs/`）。或者接受一定的误过滤率，在 `EnglishHeavySections` 中记录被过滤的内容供人工审查。

**严重程度：** 低。这是一个边缘情况，实际影响很小。

### 4.5 【建议】为第三方参考资料建立 `references/external` 目录规范

**当前状态：** `references/external/` 目录下只有 `solidworks-automation-skill-analysis.md` 一个文件，没有目录级别的 README 或规范文件说明该目录的用途和格式。

**建议：** 添加 `references/external/README.md`（中文），规定：
- 该目录存放外部仓库/论文/文档的分析报告。
- 每个分析报告必须使用中文。
- 分析报告必须包含：仓库定位、可借鉴能力、不直接复用原因、架构映射、许可证注意事项。
- 禁止在该目录下直接放置外部源码。

**严重程度：** 低。不影响 V0.9-A。

### 4.6 【建议】`module.yaml` 的 description 字段部分仍为英文

**观察到：** self-check 报告中 Module 的 `description` 字段部分为英文（如 `"Plans BuildSpec handoff to CAD workers."`、`"Converts natural-language requirements into CADModelSpec."`）。

**分析：** 这些 description 来源于 `module.yaml` 文件，虽然 Markdown 检查只针对 `.md` 文件，但 YAML 中的 description 是面向用户的说明性文字，按 `markdown_standard.md` 的精神，也应逐步改为中文。

**建议：** 在 V0.9-B 中统一将 `module.yaml` 的 `description` 字段改为中文。

**严重程度：** 低。`module.yaml` 不在 Markdown 检查范围内，但属于同一规范精神的延伸。

## 5. solidworks-automation-skill 参考策略判断

### 5.1 只参考不直接复用源码：✅ 合理

理由：
- 本项目是 C# / .NET 平台，外部仓库是 Python 脚本包，技术栈不同，直接复用无意义。
- Worker 是唯一的外部执行层，将 Python COM 脚本直接嵌入会绕过 `WorkerContracts`、`QualityGate` 和审计边界。
- 当前阶段只做 dry-run skeleton，不连接真实 SolidWorks，复制 COM 脚本没有测试环境。
- 参考其 preflight → 自审查 → API 查证 → MCP 封装的工程思路，与项目既有的 Validator → Reviewer → QualityGate → Gateway 架构天然匹配。

### 5.2 MIT License 合规风险：✅ 当前无风险

- 只参考设计思想和能力分类，不复制源码 → MIT License 不触发。
- `THIRD_PARTY_NOTICES.md` 已明确记录来源、许可证和使用方式。
- 明确规定了如果未来引入源码片段时的合规要求（保留版权声明、记录来源文件、通过 Worker 边界执行）。

### 5.3 THIRD_PARTY_NOTICES.md：✅ 必要

- 即使当前不复制源码，记录第三方参考来源也是良好的开源合规实践。
- 为未来可能引入的代码片段预留了合规框架。
- 如果项目未来需要发布或接受外部审查，这份文件是必需的。

### 5.4 禁止复制 scripts 目录：✅ 正确

- V0.9/V1.0 阶段不需要真实 SolidWorks 连接，复制 scripts 没有价值。
- 即使未来需要，也应该通过 Worker 接口重新设计，而不是直接嵌入 Python 脚本。
- 禁止复制是防御性策略，防止开发者走捷径绕过平台分层。

### 5.5 未来小片段参考边界：✅ 可以允许，边界明确

如果未来确实需要参考小片段（例如特定 SolidWorks API 的参数格式、COM 枚举值映射），允许的边界：
- 必须记录在 `THIRD_PARTY_NOTICES.md` 中（来源文件、片段用途、修改情况）。
- 保留原 MIT License 和版权声明。
- 代码必须通过 `WorkerContracts` 接口封装，不直接在 Agent 或 Skill 中调用。
- 不开放任意 Python / VBA 执行能力。
- 片段引入需要经过 CodeReview Agent 审查。
