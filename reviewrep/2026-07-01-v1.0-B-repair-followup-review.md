## 4. 高优先级问题

### HIGH-001：committed self-check 的"最新诊断"指针指向失败运行，而非成功运行

- **位置**：`output/reports/platform_self_check_report.json` 字段 `solidworks_latest_diagnostic_report_path`（源代码侧为 self-check 组装"最新诊断报告路径"的逻辑）
- **问题**：
  - HEAD 版本指向 `20260630_041702`（Failed）。
  - 工作区新版本指向 `20260701_020338`（Failed）。
  - 磁盘上真正成功的运行是 `20260701_022710`（Passed，SLDPRT 73KB + STEP 37KB）。
  - self-check 在 `2026-07-01T02:26:46` 生成，而成功运行发生在 `02:27:10`——晚 24 秒。self-check 捕获了当时的"最新"= 失败运行 `020338`，之后未再刷新。
- **风险**：这是项目**权威状态产物**且被提交进仓库。任何人（或 Codex、或未来的 gate）读取 self-check，顺着 `solidworks_latest_diagnostic_report_path` 打开的是一次 `final_status: Failed` 的诊断，会误判真实 CAD 构建仍然失败；若只看 `final_status: Passed` 又会忽略这一点。与项目"避免假成功、保证可观测性"的核心红线直接冲突。`final_status: Passed` 本身对平台骨架是正确的（骨架自检确实通过，真实 CAD 不在通过判据内），但指针本身是过时且误导的。
- **建议修复**：
  1. 在成功诊断运行 `20260701_022710` **之后重新运行 self-check**，使 `solidworks_latest_diagnostic_report_path` 指向成功运行，然后再提交该 JSON。
  2. 增强可观测性：在 self-check 中额外记录被引用诊断的 `final_status`（例如新增 `solidworks_latest_diagnostic_final_status` 字段），使读者无需打开文件即可判断"最新诊断是否通过"；若"最新诊断"是 Failed，self-check 至少应给出显式提示，避免 Passed 与失败诊断并列。
- **为什么重要**：committed 报告是给人和 Codex 判断"能否进入下一阶段"的唯一入口。指针指向失败运行会让"已修复成功"的事实不可见，破坏可追踪性。

## 5. 中优先级问题

### MEDIUM-001：切孔"cut 类型校验"为死代码（`LooksLikeCutFeature` / `RequiresCutFeatureType`）

- **位置**：`SolidWorksPlateFeatureBuilder.cs:109`（守卫）、`:264`（`LooksLikeCutFeature`）、`:184/199/222/236/250`（候选构造）、`:567`（record 字段）
- **问题**：所有 5 个候选（宏路径 2 + fallback 3）的 `RequiresCutFeatureType` 均为 `false`，导致 `if (candidate.RequiresCutFeatureType && !LooksLikeCutFeature(feature))` 永远短路，`LooksLikeCutFeature` 永不执行。这是被放弃的"用 `FeatureExtrusion2` 当切孔候选、再验证返回是否为 cut/切除类型"方案的遗留脚手架。
- **风险**：给人"已有 cut 类型防误判"的错觉，实际完全未启用。当前只用 `FeatureCut4`（非空返回即真实切除，不会误建凸台），所以该校验此刻确实不必要——但**代码与文档不一致**：`failure_repair.md` / `CADModeling/api_evidence.md` 仍写"必须检查返回特征是否为 cut/切除类型"（见 MEDIUM-002）。
- **建议修复**：二选一——(a) 删除 `LooksLikeCutFeature`、`RequiresCutFeatureType` 字段及第 109 行守卫，保持"只用 `FeatureCut4`、非空即成功"的干净语义；或 (b) 若确实要保留几何/类型防线，先在成功运行里确认 `FeatureCut4` 的 `GetTypeName2` 真实返回值（如 `CutExtrude` / `切除-拉伸`），再将 fallback 候选置 `RequiresCutFeatureType: true` 并放宽 `LooksLikeCutFeature` 的匹配。切勿在未确认返回值前贸然启用，否则可能把上一轮已通过的切除误判为失败。

### MEDIUM-002：证据/修复文档内部自相矛盾（旧结论压在新结论之上）

- **位置**：`src/Workers/SolidWorks/api_evidence.md`、`src/Modules/CADModeling/api_evidence.md`、`src/Workers/SolidWorks/failure_repair.md`
- **问题**：每份文档都出现了两层相互冲突的结论：
  - `SolidWorks/api_evidence.md`：先有"切孔草图选择规则"段落断言"主路径……是在同一个草图里画矩形外轮廓和孔圆内轮廓，然后用 `FeatureExtrusion2` 一次拉伸生成带孔板件"；紧接着"V1.0-B-REPAIR 最新宏证据"段落又写"**禁止**继续把一草图内部轮廓拉伸作为当前主策略……`FeatureExtrusion2` 只用于创建板件基体，切孔用 `FeatureCut4`"。
  - `CADModeling/api_evidence.md`：先写"切孔应验证 `FeatureExtrusion2`……该候选必须检查返回特征是否为 cut/切除类型"；随后列表第 4 点又写"`FeatureExtrusion2` 不得再被当成切孔候选"。
  - `failure_repair.md`：先写"当前候选顺序是先尝试 `FeatureExtrusion2`，并确认返回特征类型为 cut/切除；若不成立，再回退 `FeatureCut4`"；随后"V1.0-B-REPAIR 最新切孔规则"又写"`FeatureExtrusion2` 是基体拉伸，不是切孔 API"。
- **风险**：文档同时给出被放弃的方案和最新方案，且旧段落在前。未来 Codex 依此修复时可能重新引入"`FeatureExtrusion2` 当切孔候选/单草图拉伸"这条已废弃路径，与现有代码（只用 `FeatureCut4`）背离，造成回归。这也是 MEDIUM-001 死代码的文档根源。
- **建议修复**：删除或改写三份文档中描述"单草图 `FeatureExtrusion2` 出孔 / `FeatureExtrusion2` 作为切孔候选并验证 cut 类型"的旧段落，只保留"第二份宏：`FeatureExtrusion2` 建基体 → 活动孔草图 `FeatureCut4` 切除 → 失败才走草图引用 fallback"这一份权威顺序，确保文档、代码（`CreateThroughHoles`）、证据 collector 三者一致。

### MEDIUM-003：成功路径的构建日志被误标为 `repair_log:`，污染 Warnings

- **位置**：`SolidWorksDiagnosticRunner.cs:84`、`:106`（成功路径也调用 `CopyRepairDiagnostics`）、`:350-353`（`CopyRepairDiagnostics` 把每条 log 加为 `report.Warnings.Add($"repair_log: {log}")`）
- **问题**：重构后 `base_plate` 与 `cut_holes` 的**成功**路径也调用 `CopyRepairDiagnostics`，于是第一轮正常构建的普通日志（如 `Selected sketch plane...`、`hole_circle_created...`）都被前缀成 `repair_log:` 塞进 `report.Warnings`。成功运行的报告里因此充斥"repair_log:"标签的条目，既暗示发生过 repair（实际没有），又让真实 warning 淹没其中。
- **风险**：可观测性下降——审查者/Codex 难以区分"真实告警"与"正常构建日志"，且"repair_log"标签制造"进行过修复"的误导。
- **建议修复**：为正常路径使用中性前缀（如 `build_log:`）或把 logs 写入独立集合；仅在 `TryRepairCutHolesOnce` 真正的修复路径里使用 `repair_log:`。也可将成功路径的 log 合并逻辑与"错误/告警合并"拆开，避免把 informational log 当 warning。

### MEDIUM-004：上一轮遗留的过时 evidence JSON 仍未刷新（上轮 Improvement #1 未闭环）

- **位置**：`output/solidworks/diagnostics/api_evidence/cut_holes_failed_api_evidence_report.json:210`
- **问题**：该 JSON 的 `selected_api_strategy` 仍是旧值 `stable_sketch_reference_then_featureextrusion2_cut_retry`，而源码 `SolidWorksApiEvidenceCollector.cs:89` 已更新为 `macro_recorded_active_sketch_featurecut4_after_base_extrusion`。上一轮（`2026-06-30-v1.0-b-repair-cut-holes-review.md` Improvement #1）已指出，本轮仍未处理。该文件已被 `.gitignore` 忽略（`git check-ignore` 命中），不会污染仓库，但磁盘上仍是过时内容。

## 6. 低优先级问题 / 细节建议

### LOW-001：`EnterSketch` 与 `ExitSketch` 实现完全相同（`InsertSketch(true)` 切换语义）

- **位置**：`SolidWorksPlateFeatureBuilder.cs:464-468`、`SolidWorksDiagnosticRunner.cs:427-431`
- **建议**：两者都调用 `InsertSketch(true)`，依赖当前编辑状态"进入/退出"切换。新流程更复杂（宏路径全部失败后在 `:93` 才 `ExitSketch`，而失败的 `FeatureCut4` 是否已隐式退出草图并不确定），切换语义的正确性完全依赖运行时状态。建议在关键转换点记录/断言当前 `GetActiveSketch2` 是否为 null（进入前应为 null、退出后应为 null），至少把编辑状态写入 log 便于定位。

### LOW-002：切孔后无几何校验，仅凭"SLDPRT 非空"判成功

- **位置**：`SolidWorksDiagnosticRunner.cs:448`（`SldprtExists && SldprtSizeBytes>0` 即成功）
- **建议**：`FeatureCut4` 非空返回代表添加了切除特征（真实），但方向错误的盲切可能生成一个不移除材料的特征却仍返回非空、文件照样保存 → 理论上的假成功。建议增加低成本后校验：切孔后读取 body 数量 / 质量属性 / 特征树里 cut 特征计数，确认确实产生了 4 个孔。当前成功运行几何正确，此为纵深防御建议。

### LOW-003（历史遗留，非本次引入）：无 COM 超时 / 模态弹窗处理，且未关闭 SolidWorks 进程

- **位置**：`SolidWorksDiagnosticRunner.cs`（`finally` 仅 `FinalReleaseComObject(model/application)`，无 `CloseDoc`/`ExitApp`；所有 COM 调用无超时）
- **建议**：`FinalReleaseComObject` 只释放 RCW，后台 `SLDWORKS.exe` 进程可能残留；反复诊断可能累积孤儿进程（协议 P0"外部应用……残留后台进程"）。若模态弹窗（模板选择、"保留草图？"）出现，late-bound COM 调用会无限阻塞（无超时）。建议后续在 Runner 结束时显式 `CloseDoc` + 可选 `ExitApp`，并评估对关键 COM 调用加超时/看门狗。本次 diff 未引入也未加重，列为待办。

## 8. CAD / COM / 外部运行时风险评估

- **外部应用生命周期**：⚠️ Runner 释放 RCW 但不关闭 SolidWorks 进程，可能残留后台进程（LOW-003）。本次未加重。

- **Retry / Timeout 行为**：✅ 无无限重试（候选列表有界，`MaxRepairAttempts=1`）。⚠️ 无 COM 调用超时（LOW-003）。
- **失败恢复能力**：✅ 两段式切孔（宏活动草图 → 草图引用 fallback）+ 一次 repair attempt；失败时 `Issues` 追加 `cut_holes_failed` 与 `api_evidence_insufficient`，`repair_failure_reason` 可行动。⚠️ 注意 repair 会在同一 model 上再次 `CreateThroughHoles`，即再建一份孔草图（首份失败草图残留在特征树）——为已存在行为，非本次引入，几何上首份未消费草图不影响最终切除，但会遗留冗余草图。
- **日志与可追踪性**：⚠️ 切孔候选/选择策略逐条记录（good），但成功路径 log 被误标 `repair_log:`（MEDIUM-003），且 self-check 指针指向失败运行（HIGH-001）。整体可观测性被这两点拖累。
