## 4. 高优先级问题

### HIGH-001：专用实例只靠 PID 识别，PID 复用时可能接管并结束用户的 SolidWorks

**位置**：`src/CadKernel/Sw.cs` 第 49–71 行 (`Alive`、`Connect`)、第 107 行 (`Recycle`)

**问题**：
- `.cad/sw_pid.txt` 只记了 PID。`Alive(pid)` 只检查进程名是否以 `SLDWORKS` 开头，`FromPid` 在运行对象表中查 `SolidWorks_PID_<pid>`——用户自己的 SolidWorks 也会注册这一条目。
- 专用实例退出后，若 Windows 把同一 PID 分给了用户后来打开的 SolidWorks，下次 `cad run` 就会**附着到用户实例**：
  - 内存超过 3.5 GB 时执行 `ExitApp()`，60 秒内没退出就 `Kill()` (第 60–64 行)；
  - 批量出图过程中 `Recycle` 同样可能 `Kill()`。
- 对话框看门狗也会去点用户实例里的"确定"。

**风险**：用户未保存的工作被强制结束。这属于 P0 "用户文件被破坏"。概率低，但平台会长期使用，`.cad/sw_pid.txt` 一直保留，概率随时间累积。

**建议修复**：
1. PID 文件改为同时记录 `PID + 进程启动时间` (`Process.StartTime`)。连接时两项都匹配才认作专用实例，否则当作没有实例，重新启动一个。
2. `ExitApp` / `Kill` 之前再核对一次启动时间。
3. 加一条纯逻辑测试：PID 相同、启动时间不同时，必须判定为"不是专用实例"。

### HIGH-002：回归校核不和已知正确的基准比对，出图或几何退化时仍会"通过"

**位置**：`src/CadKernel/Pipeline.cs` (`DoChecks`、`DoDrawings`)、`src/CadKernel/Checks.cs` 第 121 行

**问题**：
- 现有校核只判断"有没有错误"：干涉为 0、文件能打开、PDF 数量等于工程图数量、版面不出框。它们不检查**结果和以前一样对**。
- 本会话里的例子：齿轮剖视图的伪直径、盘类零件把外圆当孔、圆盘没有外形尺寸。这几处在版面审核下全部"通过"，是我目视看图才发现的。
- 移植保真度 (图纸比例逐张一致、零件质量一致、运动学表一致) 也是我手工比对的。下一次有人改 `Drawings.cs`，没有任何机制会发现比例变了、尺寸少了。
- 内核其实已经生成了"待补尺寸"标记，但没有接成校核项。

**风险**：旧平台为防止退化建了 7257 行自检，这次整体移除了。新机制只要还有这个缺口，就会重新出现"静默退化"，而且这一次连一个会翻红的字段都没有。

**建议修复**：
1. 每个回归样例在 `input/<任务>/expected.json` 写基准：
   - 零件种数与件数、总质量 (±0.5%)、装配外形 (±1 mm)；
   - 图纸清单，含每张的图幅与比例；
   - 每张图至少一个尺寸；
   - 专属指标 (如运动学残差)。
2. 流水线新增"回归基准"校核，逐项比对，任何一项偏离即不通过。
3. "待补尺寸"计数 > 0 时，`工程图生成` 判为不通过。

## 5. 中优先级问题

### MEDIUM-001：项目级元数据放在 `BuildParts` 里设置，续跑时丢失

**位置**：`Cfc650Module.cs` 第 34–38 行，`PlanetaryGearbox.cs` 第 92–93 行

**问题**：`Cat.ProjectName / Version / Date` 只在零件步骤里赋值。`cad resume --from drawings` 不执行零件步骤，装配图写入的"版本"就退回默认的 `V1.0`。清洗机应为 `V2.0`，续跑出的装配图与零件图版本不一致。

**建议修复**：在 `CadProject` 增加 `Prepare()` (或放进 `Validate()`)，由流水线在任何步骤之前调用。

### MEDIUM-002：`resume --from parts` 在零件步骤失败过的目录上无法续跑

**位置**：`Pipeline.cs` 第 60–61 行

**问题**：续跑一律先执行 `Cat.LoadReg()`，而登记表只在零件步骤成功后才保存。零件步骤失败过的运行目录没有 `registry.tsv`，`--from parts` 会直接抛"找不到登记表"。

**建议修复**：从 `parts` 续跑时跳过载入，或登记表不存在时视为空。

### MEDIUM-003：全局静态状态隐含"一个进程只跑一次"

**位置**：`Catalog.cs` 第 101 行起 (`Reg`、`Planned`、`Pending`、`Lazy`、`ProjectName`)、`Fasteners.cs` 第 110 行 (`Sets`)、`Drawings.cs` 第 38–39 行 (`Index`、`nOk`、`nFail`)

**问题**：这些状态都不会重置。命令行每次只跑一个任务，现在没有问题。但今后若做批量运行或进程内测试：
- 紧固件组缓存 `Std.Sets` 会把**上一次运行目录里的子装配路径**插进新装配体；
- `Cat.Lazy` 会保持 true；
- 出图失败计数会累加。

**建议修复**：在 `Run.Begin` / `Run.Resume` 时统一调用各静态类的 `Reset()`；至少在 `AGENTS.md` 里写明这一约束。

### MEDIUM-004：行星齿轮宣称参数化，但只验证过默认参数

**位置**：`PlanetaryGearbox.cs` 中的派生尺寸 (按模数缩放的轴径、行星架半径、螺栓孔分布圆等)

**问题**：类注释和 `input/README.md` 都说模数、齿数、行星轮数可以改，但真实运行只有默认组合 m=2、18/27/72。派生尺寸公式 (如螺栓孔分布圆取整、减重孔位置) 没有经过第二组参数的真机检验。另外，零件库齿形在 z=30~41 不可用，可选组合比看上去少。

**建议修复**：增加第二个输入任务 (例如 m=1.5、zs=21、zp=27、zr=75、3 个行星轮：满足同心条件，(21+75)/3=32 为整数，并避开 z=30~41)，跑通后再保留"参数化"的说法。

### MEDIUM-005："装配体外形"校核实际上不可能失败

**位置**：`Checks.cs` 第 121 行

**问题**：判据只是"零件数大于 0"，外形尺寸只记录、不比较。这是我在旧平台审查中批评过的"字段名许诺的 ≠ 判据实际检查的"同一模式，这次出在我自己的代码里。

**建议修复**：并入 HIGH-002 的基准比对；在基准落地之前，改为只记录信息、不计入通过/不通过。

### MEDIUM-006：用户选项恢复依据一个永不更新的原值文件

**位置**：`Sw.cs` 中 `Disconnect` 与 `PrefFile` (继承自清洗机)

**问题**：原值只在 `.cad/sw_pref_orig.txt` 不存在时记录一次，恢复后也不删除。如果用户之后自己改了"输入尺寸值"选项，平台每次运行结束都会把它改回第一次记下的旧值。

**建议修复**：恢复成功后删除该文件，下次运行重新记录当时的值。

### MEDIUM-007：对清洗机已验证行为的改动，只在中小规模上回归过

**位置**：

## 7. 架构评估

- **边界一致性**：良好。只有内核调用 COM，`python/` 只处理文件，零件库不依赖设计项目，这几条边界在代码中都成立。设计项目可以直接使用 SolidWorks 类型 (`Action<ModelDoc2>`)，这是有意的取舍：灵活，但也意味着设计项目能绕过 `Sk` 的体积防线。`AGENTS.md` 已明令禁止，代码层面没有强制。
- **接口稳定性**：`CadProject` 的五个钩子足以覆盖两个样例，但缺 `Prepare()` (见 MEDIUM-001)。
- **耦合风险**：内核大量使用静态类，这是继承来的设计 (见 MEDIUM-003)。
- **扩展风险**：新设计的成本低，一个样例约 300–600 行。真正的风险在 HIGH-002：扩展得越多，没有基准的退化就越难发现。
- **工作流兼容性**：旧的"网关 → 质量门 → 审批"工作流已整体移除，由用户决定。现在的工作流是 `design.json → cad run → run.json`，人工审批不在平台内。

## 8. CAD / COM / 外部运行时风险评估

- **外部应用生命周期**：专用实例与看门狗设计合理，但识别方式有缺陷 (HIGH-001)。运行结束只关闭文档，不退出实例，下次复用；这一点已在交付说明中告知用户。
- **文件 I/O 安全性**：每次运行写入新目录，`CloseAll` 只关闭 `output/` 下的文档，从结构上避免覆盖用户文件。
- **Retry / Timeout**：保存失败重试 3 次，内存超限时重启实例。连接实例最多等 6 分钟 (180 次 × 2 秒)，超时抛异常。
- **失败恢复**：可从步骤续跑，但有两处缺陷 (MEDIUM-001、002)。
- **日志与可追踪性**：`run.json` 记录每个步骤的状态、耗时、校核结论和 SolidWorks 版本，`run.log` 是完整日志。可追踪性比旧平台简单，也足够。
