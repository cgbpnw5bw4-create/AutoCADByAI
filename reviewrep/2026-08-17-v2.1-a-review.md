## 2. 结论理由

不是因为 V2.1-A 的代码写得差。夹套零件族本身的领域建模是干净的：参数 schema、独立 Validator（含壁厚下限）、FeatureGraph、BuildPlan Reviewer、Builder 注册、失败阶段常量都按既有模式对齐，V2.1-A 新增的自检字段也**首次以行为式取证为主**（真实生成 BuildPlan 并跑 Reviewer、反射校验 Builder 类型、真实调用 Worker 做 dry-run），这是我连续六轮点名的问题上第一次看到正确做法。

不批准的原因是三件与代码风格无关、但直接击穿本项目红线的事实：

**第一，本版本唯一一次真实验收运行交付了一个错误的产物，而平台全链路报告成功。**
`output/solidworks/e2e/jacket_basic/cad-e2e-20260811_080801_351-.../artifacts/jacket_basic.STEP` 的文件头字节为 `88 7d 1c 43 4f 00 08 00`，与同目录 `jacket_basic.SLDPRT` 的 `88 7d 1c ec 4f 00 08 00` 属同一种 SolidWorks 原生二进制容器；全文件搜索 `ISO-10303` 命中 **0 次**。ISO 10303-21 STEP 必须是以 `ISO-10303-21;` 开头的 ASCII 文本。**这个 21159 字节的 `.STEP` 不是 STEP 文件，是被改了扩展名的 SolidWorks 原生文档。** 而 `build_report.json` 写 `step_export_success: true` / `final_status: "Passed"`，`e2e_execution_report.json` 六个工作流步骤全 `Passed`、`deliverable_status: "Deliverable"`。

协议第 9 节写得非常清楚：「构建失败可以接受。看起来成功但实际错误的 CAD 输出不能接受。」这正是该情形。

**第二，V2.0-C / V2.0-D 建立的整套真实执行证据链现在是死的，而自检仍然 `Passed`。**
`output/solidworks/features/` 目录**已不存在**。四个 Feature Handler 与 V2.0-D 证据策略引用的 diagnostic 报告全部指向不存在的路径。磁盘上唯一幸存的测试结果 `self-check-2026-08-10.trx` 已经记录了这一失败：`V20CFeatureAdapterTests.ProductionEvidenceMatchesCurrentCompositeRevisionAndDiagnostic` — `feature_api_unverified: diagnostic report does not exist`。

后果是：**上一轮我确认为「本项目最有价值成果」的 V2.0-D 几何校验闭环，现在永远无法执行**（它的授权门必然 fail-closed）。当前唯一还能跑通真实 CAD 的路径，恰恰是没有证据策略、没有版本绑定、没有几何校验、没有强制重建检查的旧 part-family 路线——而 V2.1-A 正是往这条路线上又加了一个零件族。

**第三，本版本没有任何测试运行证据，且仅存的证据是红的。**
上一轮我追踪八轮才拿到的 `output/test-results/full-test.trx`（297/297 全绿）**已从磁盘上消失**。全仓库唯一 `.trx` 是 `self-check-2026-08-10.trx`（8 月 10 日 10:22，300 项 / 299 通过 / **1 失败**），时间早于 V2.1-A 全部源码改动（8 月 11 日 12:50–13:01）。V2.1-A 的测试程序集构建于 13:01，此后无任何运行记录。

## 3. 阻塞问题

### BLOCKER-001：`.STEP` 交付物不是 STEP 文件，主流程却判定 Passed / Deliverable

**位置**
- 导出实现：`src/Workers/SolidWorks/SolidWorksPartFamilyRealBuilders.cs:780-817`（`Export`）
- 校验实现：`src/Modules/CADModeling/validators/SolidWorksArtifactValidator.cs:332-351`（`ValidateRealArtifact`）、调用点 `:155`、`:231`
- 产物：`output/solidworks/real/jacket_basic/solidworks-main-workflow-task-8ae1a9a3ed8c4943b20717a207019b7e/jacket_basic.STEP`（21159 B）及其 e2e 副本

**问题**
`Export` 以 `TryExtensionSaveAs(activeDocument, path, null, ...)` → `SaveAs3(path, 0, 1)` → `SaveAs(path)` 依次回退，**全程不传任何导出格式常量，写完后也不校验文件格式**。SolidWorks 在当前运行时（`solidworks_version: "31.5.0"`）没有按 `.STEP` 扩展名走 STEP 转换器，而是落盘了原生文档。

`ValidateRealArtifact` 只做三件事：artifact 非 null、`File.Exists`、`Length > 0`。**不检查任何内容特征**。于是 21159 字节的原生文档顺利通过「STEP 产物合格」。

**风险**
交付给下游的 STEP 是行业交换格式，用途就是被第三方 CAD / CAE / CAM 读取。当前产物任何 STEP 消费方都打不开，而平台在 `build_report`、`e2e_execution_report`、`release_manifest`、`package_quality_report` 四处一致地宣称成功并标记 `Deliverable`。这是**四重报告一致地为一个错误产物背书**，比单点失败危险得多——它会让下游把「平台报 Passed」当作可信信号。

**建议修复（最小改动，按顺序）**
1. `Export` 改为显式 STEP 导出：先用 `ModelDocExtension.SaveAs` 传入明确的导出类型/选项，或先通过 `SetUserPreferenceIntegerValue(swStepAP, ...)` 设定 AP203/AP214 再导出；不要依赖扩展名推断。
2. **无论导出方式如何，落盘后必须做格式校验**：读取文件前 32 字节，要求以 `ISO-10303-21;` 开头（允许前置 BOM / 空白）；不满足即抛 `PartFamilyFailureStages.StepExportFailed`。这一条即使第 1 步暂时修不好也必须先加——它把「静默错误」变成「显式失败」，符合协议第 9 节。
3. `ValidateRealArtifact` 增加按扩展名分发的内容校验：`.STEP` 要求 `ISO-10303-21;` 头且包含 `ENDSEC;`；`.SLDPRT` / `.SLDDRW` 要求 SolidWorks 容器魔数；`.pdf` 要求 `%PDF-`。仅靠 `Length > 0` 不足以支撑「Deliverable」结论。
4. 在修好之前，**撤回 `docs/v2_1_a_jacket_basic.md` 中「STEP 通过即可判定成功」的表述**，并把 V2.1-A 的验收结论从 Passed 改为待定。

**为什么重要**
这是协议明文列为 BLOCKER 的「输出错误但报告成功」。且该缺陷位于 `SolidWorksPartFamilyBuilderBase.Export`，为 plate / flange / shaft / jacket / feature-graph **全部**族共用——影响面是整个平台，不止夹套。

### BLOCKER-002：V2.0-C / V2.0-D 真实执行证据链已失效，平台自检仍报 Passed

**位置**
- `src/Workers/SolidWorks/Features/Sketch/SketchHandler.cs:50`、`Extrude/ExtrudeBossHandler.cs:48`、`Cut/ExtrudeCutHandler.cs:47`、`Hole/HoleHandler.cs:44` — 均引用 `output/solidworks/features/20260730_085830_6592380/feature_execution_report.json`
- `src/Workers/SolidWorks/Features/V20DThreeCircleCutEvidencePolicy.cs:24` — 引用 `output/solidworks/features/20260803_064124_6127412/feature_execution_report.json`
- 校验逻辑：`src/Workers/SolidWorks/Features/FeatureExecutionEvidencePolicy.cs:171-176`
- `.gitignore:13` — `output/solidworks/`

**问题**
`output/solidworks/features/` 目录整体不存在（`ls` 返回 No such file or directory）。`git log --all -- output/solidworks/features/` 为空，说明该目录**从未被提交**，且被 `.gitignore:13` 排除。也就是说，V2.0-C/D 的 fail-closed 授权门**依赖一批 gitignored 的本机临时产物**。一旦清理 output、换机器或重新 clone，整条通用 Feature Adapter 路线与其上的 V2.0-D 几何校验闭环即永久不可用。

这不是推测——它已经发生了，并且已被测试捕获：`self-check-2026-08-10.trx` 中 `ProductionEvidenceMatchesCurrentCompositeRevisionAndDiagnostic` 失败，消息为 `feature_api_unverified: diagnostic report does not exist: ...\20260730_085830_6592380\feature_execution_report.json`。

**风险**
1. **能力静默消失**：项目投入两个版本建成的「证据绑定 + 几何实测 + 强制重建」体系，现在一行都跑不到，而 `platform_self_check_report.json` 仍是 `final_status: "Passed"`，`v2_0_d_documented` 等字段仍为 true。自检字段检查的是「类型和方法是否存在」，不是「这条路线现在还能不能真的执行」。
2. **风险向不受保护的路线迁移**：唯一还能真跑的是旧 part-family 路线。V2.1-A 恰好把新族加在那里（见 HIGH-001）。等于两个版本的安全投入被绕过。
3. 上一轮我写的「该模式稀释 self-check `Passed` 的含金量」——本轮从判断变成了**可验证的事实**。

**建议修复**
1. **证据产物必须纳入版本控制**：把被 `DiagnosticRunPath` 引用的 `feature_execution_report.json`（以及其绑定的 model/step 摘要）移到 `.gitignore` 之外的受控目录，例如 `evidence/solidworks/<run-id>/`，并提交。证据是授权凭据，不能存放在被忽略、可随时清理的 output 树里。
2. **自检必须包含证据链活性检查**：新增字段（如 `feature_evidence_chain_valid`），直接调用 `FeatureExecutionEvidencePolicy.ValidateEvidence` 对四个 Handler 各跑一次，任一失败即 `AllPassed = false`。当前自检对「V2.0-C/D 已经跑不动」完全无感，这是自检设计的实质缺口。
3. 修复或重新采集 diagnostic 后，重跑 `ProductionEvidenceMatchesCurrentCompositeRevisionAndDiagnostic` 至绿。

**为什么重要**
自检 `Passed` 是本项目判断能否进阶的核心机器。当核心能力已经失效而自检仍报 Passed，这台机器就不再可信——之后每一个版本的「Passed」都需要人工复核才敢采信。

### BLOCKER-003：夹套真实构建丢弃 `ForceRebuild3` 结果，重建失败仍写 Passed 报告

**位置**
- `src/Workers/SolidWorks/SolidWorksPartFamilyRealBuilders.cs:517` — `protected virtual bool RequiresStrictFinalRebuild => false;`
- 同文件 `:627-633` — `var finalRebuildPassed = Com.TryInvokeBool(model, "ForceRebuild3", false); if (RequiresStrictFinalRebuild && !finalRebuildPassed) { throw ... }`
- 覆写为 `true` 的仅有：`Features/SolidWorksFeatureGraphPartFamilyBuilder.cs:41`、`Features/V20DFeatureGraphPartFamilyBuilder.cs:45`
- `src/Workers/SolidWorks/JacketFeatureBuilder.cs` — **未覆写**，继承 `false`
- `src/Workers/SolidWorks/SolidWorksComInterop.cs:145-149` — `TryInvokeBool` 内部走 `TryInvoke`，COM/反射异常被吞为 null，最终返回 `false`

**问题**
对夹套（以及 flange / shaft）而言，`ForceRebuild3(false)` 的返回值被计算出来后**直接丢弃**。重建失败——或 `ForceRebuild3` 调用本身抛 COM 异常被 `TryInvokeBool` 吞掉——都不会阻断流程：代码继续 `Save` → `Export` → 写入 `final_status: "Passed"` 的 `build_report.json` → 返回 `Completed` + `RealCadExecuted: true`。

**风险**
夹套的内腔贯穿切除是整个特征序列中最容易产生重建错误的一步（薄壁环形、深径比 180:10）。若 `FeatureCut4` 返回了非 null 特征对象但该特征在重建时报错，`Require(...)` 的非空判断会通过，重建失败又被丢弃，最终落盘一个**带错误特征的 SLDPRT**，并被报告为成功。

这正是 V2.0-D 花了一整个版本、用「重建失败提前返回、不读几何」堵住的漏洞。**该防护是按路线加的，不是按平台加的**，所以新增的族一行都没继承到。

**建议修复**
1. `JacketFeatureBuilder` 覆写 `protected override bool RequiresStrictFinalRebuild => true;`（最小改动，一行）。
2. 更彻底也更推荐：把基类默认值改为 `RequiresStrictFinalRebuild => true`，让**必须显式声明放宽**而不是默认放宽。若 flange / shaft 因历史原因暂时不能收紧，在这两个类上显式覆写 `false` 并写明原因注释——这样「谁在放宽」在代码里一目了然，且新增族默认安全。
3. 区分「重建返回 false」与「重建调用异常」：`TryInvokeBool` 把两者都压成 `false`，失败报告里无法区分。建议在严格模式下改用能区分异常的调用，并把原因写进 `diagnostics.Issues`。

**为什么重要**
协议 P0 明列「异常被吞掉」与「产生看似成功但实际错误的 CAD 输出」。这里两条同时命中，且发生在本版本新引入的真实执行族上。

### ARCH-001（HIGH）：新族的真实 COM 执行由「自声明布尔值 + 自由文本」授权，绕过 V2.0-C/D 全部证据机制

**位置**
- 授权门：`src/Workers/SolidWorks/RealSolidWorksWorker.cs:253-265` — 判据仅为 `!partFamilyBuilder.SupportsRealExecution`
- 声明处：`src/Workers/SolidWorks/JacketFeatureBuilder.cs:19-22`
- 对照组：`src/Workers/SolidWorks/Features/FeatureExecutionEvidencePolicy.cs:59-111`、`:147-277`

**问题**
两条真实执行路线的授权强度完全不对等：

| | 通用 Feature Graph 路线（V2.0-C/D） | 旧 part-family 路线（V2.1-A 走这条） |
|---|---|---|
| 授权判据 | `FeatureExecutionEvidencePolicy.ValidateEvidence` | `SupportsRealExecution => true`（自己写 true） |
| 证据形态 | 结构化 `FeatureApiEvidence` 记录 | 一个自由文本字符串 |
| 源码 revision 绑定 | 12 个源文件的 SHA256 复合哈希 | 无 |
| diagnostic 运行绑定 | 必须存在且逐字段校验 | 无 |
| 运行时版本绑定 | 连接后比对 `SolidWorksVersion` | 无 |
| 参数档案约束 | 有（窄档案） | 无 |
| 强制最终重建 | 有 | 无（见 BLOCKER-003） |
| 几何校验 | 有（V2.0-D 闭环） | 无（见 ARCH-003） |

`JacketFeatureBuilder.ApiEvidence` 的值是 `"reuses_v1_9_flange_CreateCircle_FeatureExtrusion2_FeatureCut4_subset; v2_1_a_jacket_main_workflow_required"`。这个字符串**从未被任何代码解析或校验**——它只被原样抄进 `build_report.json` 的 `api_evidence` 字段。把它改成任意内容，真实执行照样放行。

一个具体佐证：夹套的真实运行发生在 **SolidWorks 31.5.0**（见 `build_report.json` 的 `solidworks_version`），而它声称复用的 V1.9 flange 证据、以及 V2.0-C/D 全部 Handler 证据都绑定 **33.5.0**（`ExtrudeCutHandler.cs:47` 等四处）。**跨大版本复用 API 证据，且没有任何机制发现这一点**——因为这条路线根本不检查运行时版本。

**建议修复**
1. 把 `IPartFamilyBuilder.ApiEvidence` 从 `string` 升级为结构化记录（至少含 `EvidenceId` / `SolidWorksVersion` / `DiagnosticRunPath` / `SourceRevision`），并在 `RealSolidWorksWorker` 连接 COM **之前**做与 `FeatureExecutionEvidencePolicy` 同级的校验。
2. 至少先补最低成本的一道：**连接后比对运行时 SolidWorks 版本与证据声明版本，不符即 fail-closed**。这一条独立可做，能立刻堵住跨版本复用。
3. 复用他族证据时，必须在证据记录里显式声明「被复用的原始 EvidenceId + 本族参数档案 + 本族独立 diagnostic 运行」。V2.0-C 的 `V20DThreeCircleCutEvidencePolicy` 已经示范过「补充而非放宽」的正确做法，夹套应对齐同一标准，而不是退回 V1.9 的写法。

### ARCH-002（HIGH）：FeatureGraph 声明的语义与 COM 实际执行不一致，Plan Reviewer 在校验一份不被兑现的契约

**位置**
- 声明：`src/DomainSchemas/PartFamilyGenericModelFactory.cs`（`CreateJacketBasic`）— 内圆草图 `"TopFace"`；`jacket_inner_cut` 参数 `["through_all"] = "true"`
- 校验：`src/DomainSchemas/PartFamilies.cs`（`ReviewJacket`）— `RequireValue(innerCut, "through_all", "true", issues)`
- 执行：`src/Workers/SolidWorks/JacketFeatureBuilder.cs:68-81`
- 平面选择实际行为：`src/Workers/SolidWorks/SolidWorksPlaneSelector.cs:11-13, 29-38` — 优先选 `"Top Plane"` **参考基准面**

**问题**
两处偏离：

1. **草图基准面**：FeatureGraph 声明内圆草图在 `TopFace`（拉伸体的顶面），实际执行调用 `SelectPlane(model, ...)`，选中的是原点处的 **Top Plane 参考基准面**，与外圆草图同一个面。
2. **切除终止条件**：FeatureGraph 声明 `through_all = "true"` 且 Reviewer 明确断言该值，实际执行传 `FlangeFeatureBuilder.ActiveSketchFeatureCut4Arguments(length * 2)`，其中终止条件常量是 `swEndCondBlind = 0`——**盲切 2 倍长度**，不是贯穿。

几何上，从原点基准面盲切 2 倍长度确实能穿透本体，所以当前参数下结果碰巧正确。但这意味着：**`SolidWorksBuildPlanReviewer` 校验通过的那份 BuildPlan，并不是 Worker 实际执行的东西**。Reviewer 在校验一份不被兑现的契约，它的 Passed 结论对真实产物没有约束力。

**风险**
- 后续任何按 FeatureGraph 语义推理的组件（几何校验器、参数更新服务、报表、未来的 LLM Runtime）都会基于错误前提。V2.0-D 的 `ModelUpdateService` 正是这类组件。
- 一旦有人依据「声明是 through_all」放宽参数范围（例如极大长径比），盲切 2×length 的隐含假设可能不再成立，而 Reviewer 不会报警。
- 这是典型的架构漂移：领域层与执行层各说各话，中间没有一致性校验。

**建议修复**

### ARCH-003（HIGH）：夹套无任何几何校验，V2.0-D 闭环未覆盖新族

**位置**：`src/Workers/SolidWorks/Features/`（`GeometryValidation` / `SolidWorksGeometryReader` 仅接入 feature-graph 路线）；夹套路线无接入点

**问题**
V2.0-D 建立的「读取真实 Body → 实测体积 / 包围盒 / 圆柱面直径 → 与 spec 推导期望值按严格容差比对 → fail-closed」在夹套上完全缺席。夹套产物的正确性判据退化为：文件存在 + 非空 + 报告字段为 true。
