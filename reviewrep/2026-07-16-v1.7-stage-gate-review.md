## 2. 结论理由

先给应得的评价：**V1.7 是这个项目迄今在"真实执行安全"上做得最完整的一版。** 我逐行读了 E2E runner、E2E 发布包、授权 profile 和五个 V1.7 测试，运行时的防线是真实且严密的：

- **fail-closed 是真的，且有测试。** `GetE2eConfirmationIssues`（E2E.cs:333-351）在任何真实 CAD 动作之前，独立复核五重条件：profile 授权 + `allow_real_cad_execution` + `!dry_run` + `SW_ENABLE_REAL_EXECUTION` + `SW_REAL_MAIN_WORKFLOW_TEST`。缺任一即写失败工作流、返回 `Failed`。测试 `E2eFailsClosedWithoutAnyRealExecutionConfirmation` 断言了 `RealCadExecuted=false`、`solidworks_launch_attempted=false`、`real_worker_invoked=false`、`failure_stage=local_execution_authorization_missing`——**dry-run 或未授权绝不可能被算成成功**。
- **假执行证据被拒，且有测试。** E2E 发布包的 `HasCompleteRealEvidence`（E2EReleasePackageBuilder.cs:191-205）要求四个 stage 全部 `RealSolidWorksWorker` + 精确 ExecutionMode + `RealCadExecuted && RealCadConnected && QualityGatePassed && FailureStage 为空`。测试 `ExplicitSameRunReleaseBlocksFakeExecutionEvidence` 传入 `realCadExecuted:false` 的证据，断言包被判 `real_execution_evidence_failed` + `NotDeliverable`。
- **只用本次 run 的产物。** E2E 发布包"never discovers latest files"（注释 9-12），sourceSet 只接受本 request_id 产出的精确路径（E2E.cs:113-124，`RequireRealExecutionEvidence:true`）。这**彻底修正了我历轮追踪的"发布包 Passed 却混入历史/Failed 组件"**。
- **授权源完整性校验，且有测试。** `SolidWorksLocalExecutionProfile.IsAuthorized` 要求 source 精确等于 `LocalDevelopmentProfile`；测试 `LocalDevelopmentProfileIsTheOnlyRecognizedV17AuthorizationSource` 断言 `UntrustedEnvironmentVariable` 源即使 `real_execution_authorized:true` 也不授权。
- **诚实措辞。** CLI 输出 "inspect final status before treating it as accepted"；E2E report 带 warning "historical latest outputs were not scanned"；`final_status` 由 `finalGate.Passed && AllSourceReportsPassed && DeliverableStatus==Deliverable` 三重合取。
- **主流程复用未破坏。** `BuildCompleteDrawingPackage` 经 `SolidWorksMainWorkflowRunner`（partial class，主 runner:98-99 路由）→ 逐 stage `ExecuteSingleStageAsync` → QualityGate（E2E.cs:151）→ 审计。WorkflowEngine 仍是入口，Router/Orchestrator 边界未破坏。

**那么为什么是"有条件"而不是"通过"？** 三件事：

1. **一个我上轮刚关闭、Codex 刚修复并加了防复发断言的模式，本轮在 self-check 里大规模复发**（ARCH-R1，详见 §4）。约 10 个新 self-check 字段靠读源码文本 `.Contains("字符串")` 判定，其中几个还在给**真实执行的安全授权属性**背书。self-check 的 `final_status` 是本项目判断"能否进阶"的核心机器，用字符串匹配给它喂料，直接侵蚀这台机器的可信度。

2. **我上轮列为"进入下一阶段必须"的条件一（`dotnet test` 通过证据）仍未兑现。** 磁盘上没有任何 TRX 或测试结果产物，self-check 也（按设计）不含测试信号。我能确认五个 V1.7 测试**编译进了 dll**，但无法确认它们**通过**——而 V1.7 全部安全论证都压在这些测试上。

3. **我上轮列为"强烈建议同批"的条件二（`RunGit` stderr 死锁）原封未动。** `RedirectStandardError=true` + 同步 `ReadToEnd()` + `WaitForExit` 一字未改。

这三件事都不构成 BLOCKER——代码能编译、self-check 能跑（`final_status:Passed`）、运行时保护经测试覆盖、无假成功横行。但它们合在一起意味着：**V1.7 的工程实质够格作为基线，可它的"自我证明机制"和两个已知欠账仍需清理**，否则下一次"进阶"会建立在一台可信度被侵蚀的 self-check 之上。

## 4. 架构风险

### ARCH-R1（HIGH，复发）：self-check 用源码字符串匹配当能力证据，且给安全授权属性背书

**位置**：`src/PlatformCore/PlatformSelfCheckRunner.cs`（V1.7 新增判定块）

约 10 个新 self-check 字段是这样算出来的（节选）：

```csharp
var realCadE2eCliEntryExists = cliProgramText.Contains("run-cad-workflow", ...);
var realCadE2ePassesQualityGate = e2eRunnerText.Contains("DefaultGatekeeper", ...) &&
    e2eRunnerText.Contains("quality_gate_after_complete_drawing_package", ...);
var realCadE2eRequiresEnvConfirmation = e2eRunnerText.Contains("EnableRealExecution", ...) &&
    e2eRunnerText.Contains("MainWorkflowExecutionEnabled", ...);
var realCadE2eLocalAuthorizationProfileSupported =
    ... && cliProgramText.Contains("SolidWorksLocalExecutionProfile.Load", ...) &&
    e2eRunnerText.Contains("LocalDevelopmentProfile authorization", ...);
```

即：**读取 `Program.cs` / `SolidWorksMainWorkflowRunner.E2E.cs` / 发布包源文件的文本，检查里面有没有出现某个标识符或字面量**，然后把结果并入 `final_status`。

这正是 **v1.6 二次审查中我判为 HIGH（ARCH-R1）、Codex 删除了 8 个此类字段、并额外加了反向断言 `Assert.False(TryGetProperty("solidworks_com_false_success_tests_added"))` 来防止复发的那个模式**。V1.7 把它请了回来，而且规模更大（约 10 个字段），Codex 上轮那条防复发断言只钉死了一个具体字段名，没能形成通用约束。

三个具体问题：

1. **它不构成"能力具备"的证据。** `realCadE2ePassesQualityGate` 只要 E2E 源码里出现字符串 `"DefaultGatekeeper"` 和 `"quality_gate_after_complete_drawing_package"` 就为真——把 QualityGate 调用整段注释掉、只留这两个字符串（比如在一句注释里），字段照样绿，`final_status` 照样 Passed。
2. **最不该用 grep 背书的恰恰是安全属性。** `realCadE2eRequiresEnvConfirmation` / `realCadE2eRequiresRequestConfirmation` / `realCadE2eLocalAuthorizationProfileSupported` 声称的是"真实执行需要环境/请求/profile 确认"这些**安全门禁**。用"源码里有没有这个标识符"来证明一道安全门存在，是把安全保证降级成了文本搜索。
3. **它侵蚀 self-check 的 `final_status` 可信度。** self-check 是这个项目判断"能否进阶"的核心机器。一旦它的合取项里混入约 10 个"源码里有某字符串即为真"的字段，`final_status:Passed` 就不再等价于"能力真的具备"。

**为什么是 HIGH 而不是 BLOCKER**：这些字段所声称的能力，大多**另有真实行为测试覆盖**——`realCadE2eRequiresEnvConfirmation` 由 `E2eFailsClosedWithoutAnyRealExecutionConfirmation` 真实验证，`realCadE2eLocalAuthorizationProfileSupported` 由 `LocalDevelopmentProfileIsTheOnly...` 验证，`realCadE2eDefaultDisabled` / `realCadE2eLocalAuthorizationDefaultDisabled` 本身就是真实行为断言（`FromEnvironment(空)`、`Load(不存在目录)`）。所以字符串字段是**劣质的冗余**，不是唯一防线。但它是刚关闭的模式复发 + 安全属性字符串背书 + 污染 self-check，必须认真对待。

**建议修复**：删除全部 `*Text.Contains("...")` 形式的能力字段。凡需在 self-check 表达的能力，走两条路之一：(a) 反射校验真实类型/方法/属性（V1.7 里 `realCadE2eCanInvokeRealWorker` 用 `Type.GetType(...)` 就是正确范例）；(b) 真实执行一次并断言行为（`realCadE2eDefaultDisabled` 是正确范例）。并把"self-check 字段不得来自源码文本匹配"写成一条通用约束（例如一条扫描 `PlatformSelfCheckRunner.cs` 自身、禁止 `ProgramText.Contains`/`RunnerText.Contains` 出现在字段赋值中的元测试），而不是逐个字段名钉死。

### ARCH-R2（MEDIUM，新，需明确知晓）：真实执行授权收敛为单一本地文件根授权

**位置**：`src/PlatformCore/SolidWorksLocalExecutionProfile.cs` + `src/Interfaces/CliHost/Program.cs`

V1.7 的真实 CAD 执行现在有唯一实用触发路径：创建 `config/solidworks.local.json` 且 `real_execution_authorized:true`。一旦该文件授权，`ApplyToCurrentProcess()`（profile:82-90）设置 `SW_ENABLE_REAL_EXECUTION` / `SW_REAL_MAIN_WORKFLOW_TEST` 等环境变量，`ToGatewayContext`（Program.cs）强制 `allow_real_cad_execution=true` + `dry_run=false`。**原本正交的多重开关，其真值现在全部由这一个文件派生。**

需要如实说明利弊，不武断判负：

**这个设计在几个维度其实更严格**：
- 默认安全：文件不存在→`Disabled`（profile:30-33），example 为 `false`，`.gitignore` 已加 `config/solidworks.local.json`。
- **环境变量不能单独绕过**：即使手动 `export SW_ENABLE_REAL_EXECUTION=true` 并在 input 里设 flag，只要没有 profile，`GetE2eConfirmationIssues` 仍因 `!IsAuthorized` 而 fail-closed（版本索引 V1.7-REAL-AUTH 行明文："不允许环境变量单独绕过配置"）。这比 v1.6 之前"环境变量单独可触发"更安全。
- 有 source 完整性校验 + fail-closed，均经测试。
- profile 明确"never consulted by CI or self-check"（profile:6-7），self-check 里对它的调用只针对一个不存在的目录以验证默认禁用。

**代价**：纵深防御的价值在于"多个独立来源各自把关"。V1.7 把它变成"单一根授权 + 多点复核同一根的派生值"。一旦 `config/solidworks.local.json` 被置为 `true`（人为误写、被脚本生成、或在某台机器上遗留），下一次 `run-cad-workflow` 即打通全链路真实启动 SolidWorks，无需任何其他独立确认。全部安全性押在这个 gitignored 文件的保护上。

**建议**：保留至少一个 **profile 之外**的独立因子。最小改动：`ApplyToCurrentProcess` 不代设 `SW_ENABLE_REAL_EXECUTION`，改为要求用户在 shell 显式 export 它——这样"配置文件"与"当前 shell 环境"成为两个必须同时满足的独立来源，误触发需要两处同时出错。此为设计权衡，非缺陷，请团队明确选择。

### 其余架构面：未见退化

WorkflowEngine 仍是统一入口；Orchestrator 仅编排（CAD 分支经 Router → Runner）；QualityGate 复用于 E2E 总评（E2E.cs:151）；`PlatformCore` 通过 `Type.GetType` 反射调用 `SolidWorksE2EReleasePackageBuilder`，未新增对 Workers 的编译期依赖；`IRuntimeModelClient` 接入点未动；四个防假成功守卫仍在位。ARCH-B（`InternalRoute` 硬编码四步）延续，已在账本登记，不阻塞。

## 5. 可靠性风险

### REL-R1（MEDIUM，延续未修）：`RunGit` 管道死锁模式，5 秒超时守不住

**位置**：`src/PlatformCore/PlatformSelfCheckRunner.cs:2595-2620`

上轮 MEDIUM-001 原文指出的问题**一字未改**：`RedirectStandardError = true` 但 stderr 从不读取，主线程同步 `StandardOutput.ReadToEnd()` 阻塞，`WaitForExit(5_000)` 在其之后——若 git 向 stderr 写满管道缓冲区（本仓库每次 git 操作都产生一批 `LF will be replaced by CRLF` 警告），git 阻塞于写 stderr，主线程永久卡在 `ReadToEnd()`，超时护栏执行不到。`RunGit` 现在是 `ResolveSourceRevision` 的依赖，即 provenance 字段的来源，挂死会拖垮 self-check（CliHost + 8 个测试的入口）。

**建议修复**（同上轮）：`RedirectStandardError = false`（`rev-parse`/`status` 的 stderr 无需捕获）；或改双 `ReadToEndAsync()` 再 `WaitForExit`。

### REL-R2（LOW/MEDIUM，新）：provenance 字段已生效并暴露不一致，但无消费方校验

**位置**：`output/reports/platform_self_check_report.json` + `ResolveSourceRevision`

上轮我引入 `source_revision` 是为了让陈旧报告可被机器识别。V1.7 里这个字段**第一次实战就暴露了它该暴露的东西**：当前报告 `source_revision = 3175e85…-dirty`（v1.6 commit + 未提交改动），而它所在的 commit 是 `e52a486`（v1.7）。也就是说，这份报告是在 v1.7 代码写完但尚未提交时生成的，随后连同报告一起被提交。**字段忠实记录了真相，但没有任何消费方去比对"报告的 source_revision 是否等于当前 HEAD"。** provenance 修复只完成了一半：记录了来源，未强制"来源与当前状态一致"的断言。

**建议**：在 self-check 或一个轻量校验里，比对 `report.source_revision` 与 `git rev-parse HEAD`（含 dirty 判定），不一致时告警或拒绝采信。这样才把"陈旧/错配报告"从记录变成可执行的门禁。

### REL-R3（LOW，新）：`SolidWorksLocalExecutionProfile.Load` 在单次 E2E 中被重复读盘 4 次

**位置**：`SolidWorksMainWorkflowRunner.E2E.cs:21, 243, 244` + `GetE2eConfirmationIssues`

同一个 `config/solidworks.local.json` 在一次 E2E 中被 `Load`（读文件 + 反序列化）至少 4 次。轻微低效，且存在 TOCTOU：若文件在执行期间被改，授权判定（line 21）与报告记录（line 243-244）可能读到不同内容。**建议**：`Load` 一次，作为参数传递。

### 其余可靠性面：通过

- **假成功 / 部分成功报成功**：E2E `passed`（E2E.cs:138-142）与发布包 `DeliverableStatus`（E2EReleasePackageBuilder.cs:183）均为严格合取 fail-closed，经测试覆盖。`StagePassedForE2e` 要求 `RealCadExecuted && RealCadConnected`，dry-run 不可能被计为通过。
- **异常吞掉**：`ReadJsonString` / `ReadReportStatus` / `BuildE2eReleasePackageAsync` 只捕 IO/Json/Unauthorized/反射异常，转为失败状态，不静默成功。
- **文件覆盖**：E2E 发布包 `File.Copy(overwrite:true)` 目标是隔离的 `releaseDirectory/artifacts`（按 run_id 时间戳隔离），源在别处，无覆盖用户源风险。所有 E2E 输出在 `output/solidworks/e2e/...`，被 `.gitignore` 覆盖。
- **COM 挂死**：`RealSolidWorksWorker` 新增 `ExecuteWithControlledDocumentCleanupAsync`，在同一受控回调内 `CloseWorkflowDocuments`（按文档名 `CloseDoc`）+ 250ms 延迟等句柄释放，复用既有执行超时。无新增无超时外部调用（除 `RunGit`，见 REL-R1）。`Task.Delay(250)` 是等文件句柄释放的经验硬编码（LOW，CAD 自动化常见妥协）。
- **环境依赖声明**：`docs/solidworks_real_acceptance_protocol.md` 已存在并描述授权流程；但 self-check 对 `git` 可执行文件的隐式依赖（REL-R1 附带）仍未在文档声明。

## 6. 测试缺口

### 已补齐（V1.7 新增 5 条，质量高）

`RouterRecognizesOnlyTheControlledStructuredE2eOperation`、`E2eFailsClosedWithoutAnyRealExecutionConfirmation`（fail-closed）、`ExplicitSameRunReleaseBlocksFakeExecutionEvidence`（假证据拒绝）、`GatewayInvokesChiefEngineerAndWritesTheFailClosedE2eReport`（端到端经 gateway）、`LocalDevelopmentProfileIsTheOnlyRecognizedV17AuthorizationSource`（授权源完整性）。均为真实行为断言，四条已确认编译入 `PlatformSelfCheck.Tests.dll`。

### 缺口

1. **【条件一，延续未兑现】无 `dotnet test` 通过证据。** 无 TRX、无测试摘要产物，self-check 不含测试信号。测试编译入 dll ≠ 断言通过。V1.7 全部安全论证都压在这五条测试上，却无法从磁盘证明它们跑通。**这是本轮最重要的缺口。**
2. **无"self-check 字段为 false ⇒ `final_status` 为 Failed"的负向测试。** v1.6 二次审查已指出，v1.7 仍缺。若有此测试，ARCH-R1 那些字符串字段的脆弱性会更容易暴露。
3. **未覆盖"真实成功路径"。** 五条测试全部覆盖 fail-closed / 拒绝路径（这是对的、也是最重要的），但**没有一条断言"授权齐备时 E2E 走到 Passed"**——因为那需要真实 SolidWorks。这不是缺陷（真实 CAD 无法在 CI 跑），但意味着"成功路径"仍只有代码、没有证据（见 §9）。
4. **`RunGit` 无测试**（超时 / git 缺失 / stderr 溢出三分支）。
5. **`SolidWorksLocalExecutionProfile` 授权时 `ApplyToCurrentProcess` 的环境副作用无测试**（授权后五重环境是否如预期设置）。
