## 2. 结论理由

**支持进入下一阶段的理由（明确）：**

1. **核心架构稳定未回退。** `SequentialWorkflowEngine` 自 `18009c8`（ARCH-2 异常边界修复）后未再改动，仍是统一执行入口，四态（Passed/Rejected/Failed/NeedsHumanApproval）集中处理、异常兜底、RetryPolicy 有界、内部 Agent 经 QualityGate 质量循环——均保持上一轮 stage-gate 已验证的状态。`648cde3` 未触碰任何核心编排代码。
2. **真实 CAD 执行的最大历史隐患已彻底闭环。** HIGH-001（执行阶段无超时）在上一轮已在会话层单点修复并接入全部真实路径，本轮 V1.4 发布包是纯文件编排、**不触碰 COM/CAD**，不新增挂死面。
3. **V1.4 发布包设计安全、可测。** 纯文件收集/校验：拷贝进按时间戳+GUID 隔离的新目录（`overwrite:true` 只作用于新目录内，不覆盖源）、SHA256、校验存在且非空、读报告状态字段；失败即 `Failed` 且 failure_stage 可行动。因为无 COM，它**有真正的纯单元测试**（happy path + 缺失源 → 可行动失败），补上了 COM builder 一直缺的失败路径回归。
4. **技术债治理规范。** `technical_debt.md` 有 V1.1/V1.2/V1.3 三段，逐项登记并显式把执行超时"从债提升为修复项"，规则一致（真实 CAD 默认关闭）。
5. **self-check 仍 Passed**，发布包字段齐全且默认不启动 CAD。

**不建议无条件进入的理由（明确）：**

1. **真实 CAD 主流程尚未集成**（§4 ARCH-A，本轮核心发现）：`grep` 确认 `RealSolidWorksWorker` 仅被 `PlatformSelfCheckRunner` 调用，`src/Modules` 下无任何 Agent/Skill/Workflow 调用它。文档描述的主链路（`CADModelSpec → Skill → Validator → Worker → Reviewer → QualityGate`）在真实 CAD 上**未接线**。
2. **集成接缝仍冻结在 V0.6**（§4 ARCH-B，延续首份 stage-gate 的 ARCH-1）：`ChiefEngineerOrchestrator.InternalRoute` 仍是硬编码静态路由，推荐语仍写"do not call CAD workers in V0.6"（`:158`），已滞后 5+ 个版本。
3. **发布包"Passed"可包含失败组件**（§5 REL-A）：某个源报告 `final_status=Failed` 时只发 warning，不影响发布包 `Passed`。属"已收集≠已验证/可发布"的语义假成功风险，虽有披露，但"release Passed"易被误读为"可交付"。

这些都不使当前状态不安全，故为 APPROVED WITH CONDITIONS 而非 NOT APPROVED。

## 4. 架构风险

### ARCH-A（本轮核心发现，MEDIUM→需决策）：真实 CAD 能力是平行支线，未接入主工作流

- **证据**：`grep -rn RealSolidWorksWorker src`（排除 Workers/SolidWorks 与 test）仅命中 `PlatformSelfCheckRunner.cs` 与 `SolidWorksBuildPlan.cs`（schema）；`src/Modules` 下无任何 Agent/Skill/Reviewer 调用真实 Worker。内部 Agent（`cad-modeler` 等）仍是确定性 Mock，不调用 Worker。
- **含义**：V1.0-B（建模）→ V1.1（工程图）→ V1.2（尺寸）→ V1.3（标题栏）→ V1.4（发布包）这条巨大的真实 CAD 投入，目前只能通过 `SW_*` 环境开关 + self-check smoke 手动触发验证，**未与 `WorkflowEngine → Orchestrator → Agent → Worker` 主流程连接**。两条链路（Agent 编排链 / 真实 CAD 链）当前是平行世界。
- **为什么不是缺陷**：在隔离环境把 CAD 能力逐段做实、做安全，再接入主流程，是合理的工程策略；且真实 CAD 默认关闭，隔离期不影响平台安全。
- **为什么必须现在决策**：真实 CAD 能力已成熟到 V1.4（能出完整发布包），继续往下堆功能（BOM、装配、批量）而不接主流程，会让"未集成的平行支线"越来越大、集成成本越来越高，也让 QualityGate/Reviewer/HumanApproval 对真实 CAD 结果的门禁一直缺席。
- **建议**：把"将 `RealSolidWorksWorker` 通过 `ISolidWorksWorker` 接入主工作流（Skill 生成 BuildPlan → Validator → Worker → SolidWorksArtifactValidator/Reviewer → QualityGate）"列为下一阶段**头号架构任务**，优先级高于继续新增 CAD 子功能。集成时复用已就绪的：ARCH-2 异常边界、Worker 结构化 Failed、执行超时、各 builder 的防假成功门禁。

### ARCH-B（延续首份 stage-gate 的 ARCH-1，未解决）：编排接缝仍冻结在 V0.6

- **位置**：`ChiefEngineerOrchestrator.cs:9`（硬编码 `InternalRoute`）、`:158`（"do not call CAD workers in V0.6" 陈述字符串）。
- **问题**：内部多 Agent 路由自 V0.6 起未演进——仍是写死的 4 步 Mock 序列，chief-engineer 的 LLM 建议不决定路由；推荐语仍引用 V0.6，已滞后至 V1.4。这正是 ARCH-A 集成将要落地的接缝。
- **建议**：与 ARCH-A 一并处理——把静态 `InternalRoute` 改为由 chief-engineer 输出/LLM 决策驱动的动态步骤集合，并清理 `V0.6` 等阶段性字符串。当前阶段不动亦可，但不应在真实 CAD 集成时继续绕过它。

### 其余架构面 — 未发现明显风险

- 模块边界清晰：`Contracts / DomainSchemas / QualityGate / AgentRuntime.Microsoft / Modules / Workers` 分层良好，COM 不泄漏到接口层。V1.4 发布包为独立文件编排类，未侵入 Worker COM 层。
- 无绕过主流程的快捷实现（真实 CAD 走 Worker 接口 + 安全开关；发布包只读产物、写隔离目录）。
- LLM Runtime 接口仍保留（`IRuntimeModelClient` + `RuntimeConfiguration` + Mock 回退 + 仅 chief-engineer）。
- Worker 层"每版一个真实模式"目前仍可控（build/drawing/dimension/title-block 四个 COM 模式 + 发布包非 COM），但重复代码（保存/导出/COM 释放/报告写入）在累积——`technical_debt.md` 已登记"抽取共享工具"，建议随 ARCH-A 集成一并做。

## 5. 可靠性风险

### REL-A（本轮新增，MEDIUM，语义假成功）：发布包可在含失败组件时报 Passed

- **位置**：`SolidWorksReleasePackageBuilder.cs:450-456`（`source_report_not_passed` 仅 warning）、`SolidWorksReleasePackageValidator.DetermineQualityFailureStage`（`:463-491`，不因组件 `final_status=Failed` 判失败）。
- **问题**：只要源报告存在、非空、暴露 `final_status` 与 `failure_stage`，即便其 `final_status=Failed`，发布包 `FinalStatus` 仍为 `Passed`，仅产 `source_report_not_passed` warning。即"release Passed"证明的是"文件收齐 + 报告格式合规"，**不证明各交付物本身通过了各自 QA**。
- **缓解现状**：summary 明确写"本阶段只检查文件存在、大小、路径、PDF 存在以及报告状态字段"，manifest 逐项记录 `final_status`——属**已披露的 V1.4 范围边界**（与 title-block `custom_properties_only` 同类处理）。
- **风险**：但"release"一词天然暗示可交付，顶层 `Passed` 与"含失败组件"并存仍可能误导下游。
- **建议**：新增顶层字段 `all_source_reports_passed`（或 `release_gate=collection_only`），使"发布包 Passed"不被读成"发布已验证/可交付"；或在后续版本让发布包 gate 依赖所有源报告 Passed。低成本，直接消除语义误读。

### REL-B（本轮新增，LOW）：跨产物无同源一致性校验

- **位置**：`SolidWorksReleaseSourceSet.Discover`（`:530-572`）各产物独立按 `LastWriteTimeUtc` 取最新。
- **问题**：SLDPRT/STEP 取自 `plate` 目录、SLDDRW/PDF 取自 title-block/dimension/drawing 目录、各报告各取各目录最新——**彼此可能来自不同构建批次**。仅有 `build_report_not_in_selected_sldprt_directory` 一条弱一致性 warning，无跨产物 provenance 关联。
- **风险**：发布包可能打包"零件来自构建 A、图纸来自构建 B"的错配集合，却报 Passed。
- **建议**：后续为发布包引入同源标识（如共享 run-id / 校验各报告引用同一 SLDPRT SHA256），或至少把跨目录时间跨度过大列为 warning/failure。当前 V1.4 最小范围可延后。

### 其余可靠性面 — 表现良好

- **无假成功（功能层）**：发布包 `Exists && SizeBytes>0` 校验 + 缺失即 failure_stage；COM builders 失败即 `Failed`（含超时 `solidworks_execution_timeout`）；真实构建/工程图/尺寸/标题栏 smoke 多条件门禁。
- **无异常吞成成功**：发布包 catch IOException/Unauthorized/JsonException → `Failed`；坏 JSON 报告 → `("InvalidJson","source_report_missing")` 显式标记。
- **无无限重试**：RetryPolicy 有界未变。
- **外部调用超时**：LLM 双超时；COM 连接/断开/**执行**三阶段均有超时（本轮确认执行超时已全接入）。
- **文件覆盖**：发布包写隔离时间戳目录，源只读；各 builder 落盘校验非空。**无覆盖用户源风险。**
- **路径硬编码**：发布包全部 projectRoot 相对；`Discover` 目录名为约定的 `output/solidworks/real/*`，属项目内约定非机器硬编码。
- **环境依赖**：`SW_*` 开关、`AI_TIMEOUT_SECONDS`、`SW_*_TIMEOUT` 经 FromEnvironment 声明。
- **COM 挂死**：三阶段超时护栏已就位；残留进程仍未显式 `ExitApp`（技术债）。
