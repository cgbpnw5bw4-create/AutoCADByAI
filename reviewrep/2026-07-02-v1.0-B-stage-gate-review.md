## 1. 审查结论

**APPROVED WITH CONDITIONS — 有条件通过。**

当前架构是稳定、健全的，核心执行主干（WorkflowEngine 统一入口 + QualityGate 质量循环 + 可复用的 Retry/FailureReport/HumanApproval + 受限 LLM Runtime 接口 + 多条件防假成功）没有阻塞性缺陷。可以在满足少量前置条件后进入下一阶段。

但存在 1 个从上一轮延续、尚未闭环的高优先级产物问题，以及 2 个在本轮深度审查中浮现的架构级隐患（异常边界、COM 协作式超时），它们不影响当前状态的安全性，却正好落在"下一阶段要接入真实可失败步骤 / 真实动态路由"的高风险面上，应在扩大真实执行面之前处理。

## 2. 结论理由

**支持进入下一阶段的理由（明确）：**

1. **WorkflowEngine 确实是统一执行入口。** `SequentialWorkflowEngine.ExecuteAsync`（[SequentialWorkflowEngine.cs:32](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/WorkflowEngine/SequentialWorkflowEngine.cs:32)）是唯一的步骤执行循环，`GateDecisionResult` 的四种结果（Passed/Rejected/Failed/NeedsHumanApproval）全部在此集中处理并产出结构化输出。Orchestrator（[ChiefEngineerOrchestrator.cs:40](AI_Mechanical_Engineering_Agent_Platform/src/Modules/RequirementUnderstanding/agents/ChiefEngineerOrchestrator.cs:40)）只负责构造步骤 + 委托引擎 + 汇总报告，不承载业务细节。
2. **Internal Agent 调度受质量循环保护。** `InternalAgentWorkflowStep.ExecuteAsync`（[InternalAgentWorkflowStep.cs:67](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/WorkflowEngine/InternalAgentWorkflowStep.cs:67)）每次调用内部 Agent 后强制 `AgentOutput → ReviewReport → Gatekeeper.Evaluate → GateDecision`，无旁路。
3. **Retry / FailureReport / HumanApproval 可复用且集中。** 三者都在引擎里统一生成（`BuildFailureReport`、`BuildHumanApprovalRequest`、Retry 分支），不散落在各 Agent。RetryPolicy 有界（[DefaultRetryPolicy 的 `ShouldRetry`：`retryCount >= MaxRetries` 即停](AI_Mechanical_Engineering_Agent_Platform/src/QualityGate/RetryPolicy/DefaultRetryPolicy.cs)），并支持 `critical`/`non_retryable` 短路，无无限重试。
4. **真实 LLM Runtime 接口已预留且受限。** `IRuntimeModelClient.GenerateTextAsync` + `RuntimeConfiguration` + 模式切换（Microsoft/Mock 回退），且真实运行时仅对 `chief-engineer` 开放（[MicrosoftRuntimeAgentInvoker.cs:46](AI_Mechanical_Engineering_Agent_Platform/src/AgentRuntime.Microsoft/MicrosoftRuntimeAgentInvoker.cs:46)）。LLM HTTP 调用有超时（linked CTS + `CancelAfter` + `HttpClient.Timeout`，[OpenAICompatibleModelClient.cs:50-52](AI_Mechanical_Engineering_Agent_Platform/src/AgentRuntime.Microsoft/OpenAICompatibleModelClient.cs:50)）、结构化失败、不泄漏凭证、能区分超时与外部取消。
5. **防假成功机制到位。** 真实构建 smoke 自检要求"状态 Completed + RealCadConnected + RealCadExecuted + SLDPRT/STEP/JSON 均存在且非空 + ArtifactValidator 通过"全部满足才算 Passed（[PlatformSelfCheckRunner.cs:1321-1329](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/PlatformSelfCheckRunner.cs:1321)）；`RealSolidWorksWorker` 在预检/连接/构建失败时均返回 `Failed` 而非 Completed。
6. **测试覆盖对齐可靠性关键路径。** 已覆盖 workflow 的 Passed / Rejected-retry-passed / Rejected-max-retries / HumanApproval，internal workflow 的 Passed / Retry-then-passed / MaxRetriesExceeded / Failed / HumanApproval，retry 延迟真实等待 + 取消，以及 runtime/timeout/cancel 场景。

**不建议无条件进入的理由（明确）：**

1. 提交进仓库的 `platform_self_check_report.json` 的"最新诊断"指针指向一次**失败**运行，权威状态产物与真实"已成功"事实不符（详见 §5、§7，延续上一轮 HIGH-001，仍未闭环）。
2. WorkflowEngine 与 InternalAgentRouter **没有在步骤/Agent 执行外层做异常兜底**，抛出的异常会绕过 FailureReport 结构化失败路径。当前内部 Agent 是确定性 Mock，影响低；但下一阶段一旦接入真实/可失败步骤，这会变成"崩溃或丢失失败上下文"的真实风险面（详见 §4 ARCH-2）。
3. CAD 连接超时是**协作式**的，无法中断同步阻塞的 COM 调用（模态弹窗），真实挂死时调用方仍会阻塞（详见 §5 REL-1）。

这些都不是"当前不安全"，而是"扩大真实执行面之前应先补的护栏"，因此评级为 APPROVED WITH CONDITIONS 而非 NOT APPROVED。

## 4. 架构风险

### ARCH-1（MEDIUM）：Orchestrator 内部路由为硬编码流程，尚未由 chief-engineer/LLM 驱动

- **位置**：[ChiefEngineerOrchestrator.cs:9-15](AI_Mechanical_Engineering_Agent_Platform/src/Modules/RequirementUnderstanding/agents/ChiefEngineerOrchestrator.cs:9) 的 `InternalRoute`（固定 `mechanical-designer → cad-modeler → drawing-engineer → drawing-reviewer`）。
- **问题**：无论 chief-engineer 的 LLM 建议如何，实际执行的内部 Agent 序列是写死的固定 4 步。`MicrosoftAgentAdapter` 把"运行时建议 + 工作流编排"拼接，但**建议并不决定路由**。此外，报告推荐语仍写 `V0.6`（[ChiefEngineerOrchestrator.cs:158](AI_Mechanical_Engineering_Agent_Platform/src/Modules/RequirementUnderstanding/agents/ChiefEngineerOrchestrator.cs:158) "do not call CAD workers in V0.6"），与当前 V1.0-B 阶段脱节。
- **风险**：这是"硬编码流程假设"。对当前阶段可接受（流程稳定、可测试、仍走 WorkflowEngine + QualityGate），但当下一阶段要实现"chief-engineer 真正决定调度哪些 Agent"时，需要把静态路由改为由 chief-engineer 输出/LLM 决策驱动的动态步骤集合。现在把它记为下一阶段最大的架构债。
- **建议**：下一阶段把 `InternalRoute` 从常量改为"由 chief-engineer AgentOutput（或运行时建议）解析出的有序 agentId 列表"，并对非法/空路由回退到安全默认；同时清理 `V0.6` 等阶段性陈述字符串。**当前阶段不必动。**

### ARCH-2（MEDIUM）：WorkflowEngine / Router 缺少步骤执行的异常兜底，抛出异常会绕过 FailureReport

- **位置**：[SequentialWorkflowEngine.cs:54](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/WorkflowEngine/SequentialWorkflowEngine.cs:54)（`await step.ExecuteAsync(context)` 无 try/catch）；[InternalAgentRouter.cs:27](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/AgentRegistry/InternalAgentRouter.cs:27)（`await agent.ExecuteAsync(context)` 无 try/catch）。
- **问题**：引擎依赖步骤"返回带 Failed 的 GateDecision"来表达失败，但如果步骤/Agent 真的**抛出**异常（未来的真实内部 Agent、worker 支撑的步骤、意料外的 null/COM 异常），异常会一路向上冒泡，跳过 `BuildFailureReport` 和 `workflow_step_failed` 审计记录，可能直接使整个 workflow 崩溃或被上层非结构化地吞掉。这与协议 P0"异常被吞掉/假成功"是一体两面：这里的风险是"结构化失败路径被异常绕过"。
- **为什么现在影响低**：当前内部 Agent（mechanical-designer 等）是确定性实现、不抛异常；chief-engineer 的真实运行时异常已在 `MicrosoftRuntimeAgentInvoker`（[:91-114](AI_Mechanical_Engineering_Agent_Platform/src/AgentRuntime.Microsoft/MicrosoftRuntimeAgentInvoker.cs:91)）内部被转成 `AgentOutput.Failed`，不会冒泡到引擎。
- **为什么下一阶段影响高**：下一阶段接入真实/可失败步骤（真实工程图生成、worker 支撑步骤、动态路由）后，任意一步抛异常就会绕过 FailureReport，既拿不到可行动的失败上下文，也可能使 workflow 非受控中断。
- **建议**：在 `SequentialWorkflowEngine` 的步骤执行外层加 try/catch，把非取消类异常转换为 `GateDecisionResult.Failed` + `FailureReport`（保留 `OperationCanceledException` 继续向上传播以支持协作取消），并补一条回归测试（见 TEST-3）。**建议在下一阶段接入真实步骤之前完成。**

### 其余架构面 — 未发现明显风险

- 模块边界清晰：`Contracts / DomainSchemas / QualityGate / AgentRuntime.Microsoft / Modules / Workers` 分层良好，COM 类型不泄漏到接口层（`ISolidWorksWorker` 使用纯 C# 类型）。
- 无绕过主流程的快捷实现：内部 Agent 一律经 Router + QualityGate；真实 Worker 经 `ISolidWorksPlateBuilder` 委托；Gateway 只暴露 chief-engineer。
- 接口稳定：核心公共签名未变。
- 与历史架构建议一致：上一轮"SmokeRunner 复用生产 FeatureBuilder"已落地（诊断路径现在验证生产代码）。

## 5. 可靠性风险

### REL-1（MEDIUM）：CAD 连接超时为协作式，无法中断同步阻塞的 COM 调用

- **位置**：[SolidWorksSessionManager.cs:66-73](AI_Mechanical_Engineering_Agent_Platform/src/Workers/SolidWorks/SolidWorksSessionManager.cs:66)（`CreateLinkedTokenSource` + `CancelAfter` + `await Task.Run(() => ConnectCore(options, timeout.Token), timeout.Token)`）。
- **问题**：`CancelAfter` 会让 token 到期，但 `ConnectCore` 内部若卡在同步阻塞的 COM 调用（如 `Activator.CreateInstance`、模态弹窗），该调用不感知 CancellationToken，`Task.Run` 线程不会被中断；而此处是**直接 `await Task.Run(...)`**，调用方会一直阻塞到 COM 调用自己返回。对比之下，断开连接用的是 `await disconnectTask.WaitAsync(disconnectCts.Token)`（[RealSolidWorksWorker.cs:413](AI_Mechanical_Engineering_Agent_Platform/src/Workers/SolidWorks/RealSolidWorksWorker.cs:413)），token 到期能让调用方解阻塞（后台任务成孤儿）。两处模式不一致。
- **风险**：真实 SolidWorks 出现模态对话框（模板选择、"是否保留草图"、许可证弹窗等）时，超时不能真正生效，worker 线程与等待方仍会挂住（协议 P3/P0"COM 自动化失控 / 外部应用卡死"）。
- **建议**：连接/构建统一改用 `await task.WaitAsync(timeoutToken)` 让调用方在超时后可控返回，并在文档中明确"真正挂死的 COM 模态无法靠 token 强杀，需要进程级终止"。可延后，但在扩大真实构建频率前应处理。

### REL-2（HIGH，延续上一轮 HIGH-001，仍未闭环）：self-check"最新诊断"指针指向失败运行

- **位置**：`output/reports/platform_self_check_report.json` 的 `solidworks_latest_diagnostic_report_path`。
- **问题**：工作区版本指向 `20260701_020338`（Failed），HEAD 版本指向 `20260630_041702`（Failed），而真正成功的运行是 `20260701_022710`（Passed）。self-check 在 `02:26:46` 生成，早于成功运行 `02:27:10` 约 24 秒，生成后未刷新。磁盘已核对：6 次运行仅最后一次 Passed。
- **风险**：提交进仓库的权威状态产物会让人/Codex 顺着指针打开一次失败诊断，误判真实 CAD 仍失败；`final_status: Passed` 本身是对平台骨架而言正确的（真实 CAD 不在默认通过判据内，[PlatformSelfCheckRunner.cs:292-314](AI_Mechanical_Engineering_Agent_Platform/src/PlatformCore/PlatformSelfCheckRunner.cs:292) 的 Strict/Attempted 逻辑设计合理），但指针本身过时误导。
- **建议**：成功运行后重跑 self-check 使指针指向 `022710` 再提交；并新增 `solidworks_latest_diagnostic_final_status` 字段直接暴露被引用诊断状态。**这是进入下一阶段前应先修的一项。**

### REL-3（LOW→MEDIUM，历史遗留）：残留 SolidWorks 进程风险

- **位置**：`SolidWorksDiagnosticRunner`/`RealSolidWorksWorker` 只 `FinalReleaseComObject`，无保证性的 `CloseDoc`/`ExitApp`。
- **风险**：反复真实运行可能累积孤儿 `SLDWORKS.exe`（协议 P0"残留后台进程"）。
- **建议**：运行结束显式关闭文档/进程；可延后。

### 其余可靠性面 — 表现良好

- **无假成功**：引擎终态映射正确；真实构建 smoke 多条件校验（§2 第 5 点）；worker 失败即 Failed。
- **异常未被静默吞成成功**：`MicrosoftRuntimeAgentInvoker` 与 `RealSolidWorksWorker` 的 catch 都转为 `Failed` 结构化输出并记录 issue，不返回 Completed。
- **无无限重试**：RetryPolicy 有界 + 非可重试短路。
- **LLM 外部调用有超时**：双重超时 + 结构化失败 + 不泄漏凭证。
- **文件覆盖/输出**：`SavePart`/smoke 校验 `Exists && Length>0`，缺失即抛 `IOException`；`build_report_write_failed` 有 IOException 兜底。
- **路径硬编码**：`FindProjectRoot` 向上查找 `.sln`，非绝对路径硬编码；输出目录派生自 projectRoot。（self-check JSON 里的 `D:\文件\...` 绝对路径是生成产物、机器相关，非源码硬编码。）
- **环境依赖已声明**：`SW_ENABLE_REAL_EXECUTION`、`SW_REAL_BUILD_SMOKE_TEST`、`AI_TIMEOUT_SECONDS`、`SW_CONNECT_TIMEOUT_SECONDS` 等经 `FromEnvironment` 读取并在文档说明。

## 6. 测试缺口

### TEST-1（MEDIUM）：缺少文件输出（保存/导出）失败路径的单元测试

- **证据**：全测试目录按方法名统计 `Save`=0、`Export`=0。而 `SolidWorksPlateFeatureBuilder.SavePart`（[:135-169](AI_Mechanical_Engineering_Agent_Platform/src/Workers/SolidWorks/SolidWorksPlateFeatureBuilder.cs:135)）通过注入的 `tryExtensionSaveAs`/`tryInvokeBool` 委托，**完全可以脱离 COM 单测**（注入返回 false 或模拟文件缺失，断言抛 `IOException`、不返回 Passed）。
- **风险**：协议 C 明确要求"覆盖文件输出异常"，且核心红线是"SLDPRT 缺失不得返回 Passed"，目前这一路径无回归保护。
- **建议**：新增 SavePart 失败路径测试（SaveAs 全 false → IOException；文件存在但 Length=0 → 视为失败）。

### TEST-2（MEDIUM，延续上一轮）：切孔链路的纯函数/顺序未覆盖

- 缺 `SketchNameCandidates` 中英文互换（`Sketch3`↔`草图3`，纯函数易测）、宏候选先于 fallback 的顺序断言、`CopyRepairDiagnostics` 日志前缀行为。

### TEST-3（MEDIUM，与 ARCH-2 绑定）：无"步骤抛异常 → FailureReport"的回归测试

- 当前引擎不捕获步骤异常，所以也没有对应测试。修复 ARCH-2 后应补：一个会抛异常的假步骤，断言 workflow 返回 `Failed` + 非空 `FailureReport` + 审计有 `workflow_step_failed`。

### 已覆盖良好、未发现缺口的部分

- Workflow 中断（Rejected/Failed/HumanApproval 终态）、Retry 行为（含延迟真实等待与取消）、HumanApproval Gate、External Runtime Failure（runtime=16、timeout=5、cancel=5、RealRuntimeIntegrationTests + AgentRuntimeMicrosoftTests）均有对应场景测试。
