## 4. 高优先级问题

### HIGH-001：自检的异常处理把「读不到文件」误判成「安全能力回归」，且丢弃失败原因

**位置**：`src/PlatformCore/V21BHoleSelfCheck.cs`，四类型循环末尾的 `catch`

```csharp
catch (Exception exception) when (exception is IOException or JsonException or InvalidOperationException or TargetInvocationException)
{ supported = false; allBlocked = false; typeValidation = false; geometry = false; semantics = false; }
```

**问题**

两个独立缺陷叠在一起：

1. **一个样例文件读不到，会把五个不相关的标志同时置 false**，其中 `allBlocked` 最终写入 `unverified_hole_blocks_real_execution`——一个**安全能力**字段。文件缺失并不意味着阻断行为退化了，只意味着这次检查没跑成。而该字段已进入受保护基线，因此结果是能力回归闸报告**「能力回归」**，而不是**「配置/环境错误」**。

   这正是 V2.1-A 轮中已经在 `SelfCheckCapabilityRegressionGate` 里区分开的两件事：基线里有、但自检没观测到的字段判为配置错误而非回归。本轮在一个新位置上把这个区分丢掉了。

2. **`exception` 被捕获却从未使用**，失败原因完全丢弃——没有日志、没有 issue 文本。运维看到的是「十一个孔字段里有五个 false」，看不到「因为 `examples/hole_tapped_plate.json` 解析失败」。这违反协议第 5 节 P5「错误信息可执行」。

**风险**

中高。触发条件不苛刻：四个样例 JSON **不在** `FeatureExecutionEvidencePolicy.BoundSourcePaths` 中，任何人编辑或移动它们都不会让证据失效，却会让自检字段翻转。届时排查方向会被错误信息带偏到「阻断能力坏了」，而真正的原因是一个样例文件。

**建议修复**

1. `catch` 中只置 `supported = false`，其余四个标志改为「未观测」而不是 false——例如把 `checks` 的值类型改为可空布尔，或单独记录一个 `hole_selfcheck_inputs_readable` 字段并让其他字段跳过本次类型。
2. 把 `exception.Message` 与出错的样例路径写入自检报告的 issue 列表。
3. 把四个样例 JSON 纳入某种完整性绑定（最简单：自检启动时先断言四个文件存在且可解析，失败即报配置错误并中止本组）。

### HIGH-002：`hole_feature_regression_tests_passed` 名不副实，且已写入受保护基线

**位置**：`src/PlatformCore/V21BHoleSelfCheck.cs`

```csharp
checks["hole_feature_regression_tests_passed"] = checks.Values.All(v => v);
```

**问题**

该字段**不运行任何测试**，只是同一个字典里其他检查结果的逻辑与。字段名宣称「孔特征回归测试通过」，实际验证的是「上面几项自检都为真」。

两重后果：

1. **信息量为零且重复计数**。任一子项退化时它必然同时退化，对回归闸没有任何增量鉴别力，却在基线里占一个受保护位置。
2. **名称误导**。基线 `docs/self_check_capability_baseline.json` 是**受版本控制的能力契约**，读者看到 `hole_feature_regression_tests_passed: true` 会认为回归测试跑过了。实际上 449 个 xUnit 测试与这个字段没有任何关系。

这是 V2.0-E 二次审查中 MEDIUM-001（`feature_graph_template_reuse_supported` 宣称模板复用、实际只检查类型存在）**同型问题的复发**，位置换了，形态一样：**字段名承诺的事 ≠ 判据实际验证的事**。

**风险**

中高。它不会造成错误执行，但会造成**错误的安全感**，而本项目的核心风险模型就是「以为验证过了」。且它在基线中，等于把一个恒等式锁成了能力契约。

**建议修复**

三选一：

1. 删除该字段，从基线中一并移除（基线规则允许显式删除并说明理由，禁止的是改成 false）。
2. 若确实要表达「孔相关回归测试通过」，改为真实判据——例如断言 `V21BHoleFeatureTests` 中的用例数不少于某个下界且测试程序集可加载，或读取测试结果文件。
3. 保留聚合但改名为 `hole_self_check_group_passed`，并在基线注释中写明它是派生字段。

我倾向第 1 项：派生字段进基线只会稀释基线的含义。

## 5. 中优先级问题

### MEDIUM-001：证据门以「参数是否存在」为开关，而非以「实际执行档案」为开关

**位置**：`src/Workers/SolidWorks/Features/Hole/HoleHandler.cs:143-150`

```csharp
if (!result.IsValid || !feature.Parameters.ContainsKey("hole_type")) return result;
```

`hole_type` 一旦出现，**无论取值**（含 `SimpleHole`）一律拒绝真实执行；省略 `hole_type` 则走 V2.1-A 已取证的盲切路径。

方向是安全的（更明确的规格被拒绝，不会反过来），且四类新档案确实涉及 `reference_face` / `position` / `through_all` 等未取证语义，因此判定本身站得住。但开关选错了对象：

- 使用者写 `hole_type: "SimpleHole"` 并给出与旧档案完全相同的直径与盲深，语义上就是已取证的那条路，却被拒绝；删掉一个声明性字段反而通过。
- 结果是 schema 里的 `hole_type` 事实上变成「主动选择被拒绝」的开关，与它的描述（「SimpleHole、CounterboreHole、CountersinkHole、TappedHole」）不符。

**风险**：中。不产生错误几何，但会让使用者得出「写得越清楚越不能用」的结论，长期会诱导大家省略声明性字段——而省略信息正是本项目最不想鼓励的行为。

**建议修复**：把判据从「`hole_type` 是否存在」改为「解析出的孔定义是否落在已取证档案内」。即：`HoleValidator` 解析后，若 `HoleType == Simple` 且未使用 `reference_face` / `position` / `quantity` / `through_all` 等新语义，则视同旧档案放行；否则按类型拒绝。

### MEDIUM-002：`*_hole_supported` 的命名与项目自身对「Supported」的定义冲突

**位置**：`docs/self_check_capability_baseline.json`、`V21BHoleSelfCheck.cs`

能力矩阵定义 `Supported` 为「Handler 已实现且有 Feature 级真实执行证据」。而 `counterbore_hole_supported = true` 时，沉孔**完全不能执行**——该字段的实际含义是「定义、校验、计划编译与 dry-run 链路通」。

矩阵文档里已经写了免责说明（「`simple_hole_supported` 等自检字段表示定义与模拟能力，不表示矩阵中的真实 `Supported`」），这一点做得对。但**基线文件里没有这个上下文**，而基线是独立的能力契约文档，会被单独阅读、被回归闸单独引用。

**风险**：中。文档已缓解，但同一个词在两份契约文档中含义相反，是可预期的误读来源。

**建议修复**：字段重命名为 `counterbore_hole_definition_supported` / `..._dry_run_supported` 之类，或在基线 JSON 的 `description` 中加一句说明「`*_hole_supported` 表示定义与模拟能力，不代表真实执行授权」。后者成本最低。

### MEDIUM-003：自检的几何判定使用自造的 `MeasuredGeometry`，字段名未体现这一点

**位置**：`V21BHoleSelfCheck.cs`，`var measured = new MeasuredGeometry(...)`

`hole_geometry_validation_supported` 的判据是：构造一份合成的实测几何 → 断言 `Passed`；再构造三份被破坏的（`Holes = null`、`DepthMm = 1`、`DiameterMm = 99`）→ 断言 `Failed`。

**这个判据本身是好的**——它是可鉴别的（有反例），正是历次审查一直要求的形态。问题只在于它验证的是**判定规则**，不是**真实几何**，而字段名读起来像后者。文档中已注明「独立测量夹具仅证明判定规则」，与 MEDIUM-002 同类。

另外期望体积用了硬编码表 `{simple:108, counterbore:216, countersink:144, tapped:75}` 乘 `Math.PI`，没有写出推导过程。数值本身不影响正确性（只要与样例一致），但无法复核。

**建议修复**：字段改名为 `hole_geometry_validation_rules_supported`；在硬编码体积表上方加一行注释写明每个数字的来源（孔径、深度、类型）。

### MEDIUM-004：自检期间执行 dry-run Worker 并写入 `output/`，边界扩大

**位置**：`V21BHoleSelfCheck.cs` 中 `worker.ExecuteAsync(... Path.Combine(root, "output", "solidworks", "self-check", "v2_1_b", name) ... DryRun: true)`

自检从「读取 + 反射 + 纯逻辑判定」扩展为「实际调用 Worker 并写盘」。使用的是 `FakeSolidWorksWorker` 且 `DryRun: true`，不触碰真实 CAD，因此安全性可接受。但两个副作用值得记录：

1. `self-check` 现在会在 `output/solidworks/self-check/` 下产生文件，进一步扩大了 LOW-002 描述的「只读验证命令会写盘」问题。
2. 自检耗时与失败面变大——Worker 的任何回归都会表现为孔能力字段翻转。

**建议修复**：不必回退，但应在 `docs/v2_1_b_hole_features.md` 中明确记录「self-check 会执行 dry-run 并写入 output」，并与 LOW-002 一并考虑给自检加 `--output`。

### MEDIUM-005：`HoleHandler.ParameterSchema` 使用前导逗号，与文件内既有风格不一致

**位置**：`src/Workers/SolidWorks/Features/Hole/HoleHandler.cs:12-33`

前四项用尾逗号，后十四项用前导逗号（`,new(...)`）。语法合法、编译通过，但同一个集合内两种风格并存，是「追加式补丁」留下的痕迹。该 schema 是 Handler 的对外契约，可读性直接影响后续维护者是否会漏读参数。

## 7. 架构评估

- **边界一致性**：保持。四类孔复用**同一个** `HoleHandler` 与 `ExecuteHoleAsync`，没有新增 Hole Agent、没有新增队列、没有 `switch (part_type)`。`HoleExecutionStrategies` 只声明类型/失败阶段/证据，注释明写「不承载 COM」，实际也确实没有 COM 代码。这与 V2.1-A 建立的「一套模型服务多个特征」方向一致。（*此项含自评成分：被复用的 Handler 是我写的。*）
- **接口稳定性**：`FeatureHandlerReport` 新增 `HoleType` / `HoleParameters` 两个字段；`IFeatureHandler` 通过 `ValidateParameterProfileForRealExecution` / `BuildPlan` / `GenerateReport` 的 `override` 扩展，未改接口签名。向后兼容。
- **耦合风险**：**新增一处需要留意的耦合**——自检的孔能力字段现在依赖 `examples/hole_*_plate.json` 四个文件。样例文件从「文档性资产」变成了「自检输入」，却没有相应的完整性保护（见 HIGH-001）。
- **扩展风险**：中。孔向导四类的真实取证是下一步最大的未知：`IWizardHoleFeatureData2` 的标准/紧固件枚举映射、`thread_pitch` 与 `HoleWizard5.Length` 的区分，都还只有文档级的警告，没有实证。证据文档已把这些点逐条列为禁止事项，方向正确。
- **Workflow 兼容性**：保持。新增 `dry-run-cad` CLI 入口通过 `CadDryRunCliContract.ForceDryRun` 强制覆写 `dry_run=true` 等六个键，并有测试 `DryRunCliForcesSafeModeDespiteContradictoryInput` 锁住「矛盾输入也不能翻出安全模式」。这个设计是对的：不信任输入，直接覆写。

## 8. CAD / COM / 外部运行时风险评估

- **外部应用生命周期**：本轮未新增 COM 调用路径。四类孔在适配器入口即返回失败，`ReleaseComObject` 相关逻辑未变（`V21BHoleFeatureTests` 中有 `ReleaseComObject` 相关用例）。

- **Retry / Timeout**：未引入重试。四类孔为一次性拒绝。
- **失败恢复能力**：fail-closed 完整且分层清晰。新增专用失败阶段 `CounterboreExecutionFailed` / `CountersinkExecutionFailed` / `TappedHoleExecutionFailed` / `TappedHoleApiUnverified`，攻丝单独用 `tapped_hole_api_unverified` 与其余三类区分——**这个区分是有意义的**，因为攻丝最容易被普通 Cut 或装饰螺纹冒充，单独的失败阶段让日志能直接定位。
- **日志与可追踪性**：诊断侧显著增强——每份采证目录都带 `probe.json` 与 `probe_console.log`，把我上一轮手动跑的探针复核固化成了流程。**但自检侧相反**：HIGH-001 的 `catch` 丢弃异常信息，是本轮唯一的可观测性倒退。

**特别记录**：`HoleHandler.GenerateReport` 在 `hole_type` 存在时把 `ApiEvidenceStatus` 改回 `unverified` 并把六个 evidence 字段置 `null`。这是一处**主动放弃已有证据**的设计，与本项目一贯「尽量证明成功」的压力方向相反，值得肯定——它堵死的正是「用旧档案的证据给新档案背书」这条最隐蔽的假成功路径。

## 12. 最终结论

**PASS WITH COMMENTS —— 可以接受，但建议优化。**

V2.1-B 在「不假装能用」这件事上做得比本项目以往任何一轮都彻底：四类孔三重拒绝、适配器零 COM 代码、`GenerateReport` 主动清空继承来的证据、能力矩阵与证据文档逐条写明不得复用历史档案、449 个测试里新增的多是对抗性用例、证据链做了真实重采并把只读探针固化进流程。对上一份报告的 13 项建议登记完整、方案具体，且 Codex 对自身协议的修改经核查是纯追加、无自我松绑。

问题集中在**自检判据本身**而非被检对象：HIGH-001 把「读不到输入」误报成「安全能力回归」并丢弃原因，HIGH-002 把一个恒等聚合锁进了能力契约。两者都不会造成错误的 CAD 输出，但都会造成**错误的判断依据**——而这个项目的整套机制正是建立在自检字段可信之上的。按协议第 9 节的精神，污染判断依据与产生假成功属于同一类风险的上下游。

**关于是否进入下一阶段**：可以，条件是先完成第 11 节第 1、2 项。这两项都不涉及真机采证，成本低。

四类孔的真实取证是独立于本轮的下一件事，届时 `IWizardHoleFeatureData2` 的枚举映射与螺距语义是主要未知——证据文档已把风险点列全，方向没有问题。

**独立性限制重申**：本轮 V2.1-B 改动出自 Codex，第 3–6 节为独立判断；但底层九个 Handler 与适配器是我写的，第 7 节含自评成分，建议由未参与者复核。
