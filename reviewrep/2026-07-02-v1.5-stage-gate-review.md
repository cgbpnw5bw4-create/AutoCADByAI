## 2. 结论理由

**支持进入下一阶段的理由（明确）：**

1. **ARCH-A 已实质解决——两条平行世界开始合流。** 上一份 stage-gate 的核心发现（真实 CAD 只被 self-check 调用、未接主流程）本轮被正面解决：新增 `SolidWorksMainWorkflowRunner`（4 步：Skill 生成 BuildPlan → Validator+Reviewer → Worker 执行 → ArtifactValidator + QualityGate，全程走 `SequentialWorkflowEngine`），并由 `PlatformBootstrapper` 注入进 `ChiefEngineerOrchestrator`（`PlatformBootstrapper.cs:97-101`），使真实 CAD 结果**第一次真正经过 QualityGate**。有集成测试（`ChiefEngineerOrchestratorInvokesSolidWorksMainWorkflowForPlateRequest` 断言审计存在 `quality_gate_after_solidworks_main_workflow`）与安全开关测试（`...UsesFakeWorkerByDefaultAndRequiresBothRealFlags`）。
2. **安全开关在集成路径中完整保留。** 真实执行需三重条件同时满足：请求级 `allow_real_cad_execution` + 显式 `dry_run=false` + 环境 `SW_ENABLE_REAL_EXECUTION`（`SolidWorksMainWorkflowRunner.cs:83-84`）。默认（无 flag）→ `dryRun=true` → Fake worker。self-check 默认走 Fake、不启动 COM。
3. **REL-A 已修（V1.4 §8-A #1）。** 发布包新增 `AllSourceReportsPassed` / `DeliverableStatus`：任一源报告 `final_status=Failed` → `DeliverableStatus=NotDeliverable` → 发布包 `FinalStatus=Failed`（`SolidWorksReleasePackageBuilder.cs:308-321`）。含失败组件**不再报 Passed**，有 `Deliverable`/`NotDeliverable` 双测试 + 3 个 self-check 字段。
4. **核心架构无回退，且被复用而非改写。** `SequentialWorkflowEngine`（末次改动 `18009c8` ARCH-2）与 `DefaultRetryPolicy` 本轮未动；集成通过标准 `WorkflowStep` + `GateDecision` 复用引擎的异常边界、Retry、四态处理、FailureReport。ARCH-B 的 V0.6 陈述字符串已清除。
5. **无假成功（功能层）。** `BuildFinalReview.passed` 需 worker Completed + 三层校验全 pass + `issues.Length==0`（fail-closed）；`RealCadExecuted`/`RealCadConnected`/`ExecutionMode` 如实上报；Fake 干跑不冒充真实执行。self-check Passed，集成字段纳入通过判据。

1. **Orchestrator 出现业务/路由细节漂移**（§4 ARCH-A'）：`ChiefEngineerOrchestrator` 现承担关键字触发判断、flag 解析、projectRoot/输出目录解析、硬编码 `CADModelSpec` 构造——偏离了"Orchestrator 只负责编排"的既定原则。
2. **CAD 触发是关键字匹配 + 硬编码零件流程**（§4 ARCH-B'）：`IsSolidWorksMainWorkflowRequest` 靠消息含 "solidworks"/"plate_basic_4holes" 触发，且无论请求内容如何都只建 `plate_basic_4holes`。属"硬编码流程假设 + 脆弱触发"。
3. **TEST-A 仍未闭合**（§6）：四个 COM builder 内部防假成功守卫仍无纯单测（本轮未触碰）。

这些均不使当前不安全，故 APPROVED WITH CONDITIONS。

## 4. 架构风险

### ARCH-A'（本轮新增，MEDIUM）：Orchestrator 承担了业务/路由细节，偏离"只负责编排"

- **位置**：`ChiefEngineerOrchestrator.cs` 新增 `TryRunSolidWorksMainWorkflowAsync`、`IsSolidWorksMainWorkflowRequest`（关键字匹配）、`ResolveProjectRoot`/`ResolveSolidWorksOutputDirectory`（路径逻辑）、`CreatePlateBasicFourHolesSpec`（硬编码域对象构造）、flag 解析工具。
- **问题**：上一轮 stage-gate 曾肯定该 Orchestrator "只构造步骤 + 委托引擎 + 汇总报告"。本轮它开始做"是否触发 CAD、用什么 spec、写哪里、真实与否"的决策与构造，编排层变厚。这类"触发决策 + 域对象构造 + 路径解析"更适合放在专门的路由/策略组件或 Runner 内，保持 Orchestrator 纯粹排序。
- **风险**：编排层与业务决策耦合，后续再接入更多 Worker/子流程时，Orchestrator 会持续膨胀成"隐形调度中枢 + 业务装配器"。
- **建议**：抽一个 `SolidWorksWorkflowRouter`（或在 Runner 内提供 `ShouldRun(context) + BuildRequest(context)`），把"是否触发 / spec / 路径 / flag 解析"移出 Orchestrator，让 Orchestrator 只调用 `router.TryBuildRequest(...)` 再委托 Runner。当前阶段可先记录，随下一次触碰就近重构。

### ARCH-B'（部分解决 + 本轮新增，MEDIUM）：内部路由仍硬编码；CAD 触发用关键字匹配 + 固定零件规格

- **位置**：`ChiefEngineerOrchestrator.InternalRoute`（仍硬编码 4 步）；`IsSolidWorksMainWorkflowRequest`（`:关键字 solidworks/plate_basic_4holes`）；`CreatePlateBasicFourHolesSpec`（永远 160×80×12 四孔）。
- **已改善**：V0.6 陈述字符串已替换为"Proceed through the platform workflow boundary before any CAD Worker execution."（ARCH-B 的表层问题已修）。
- **仍存在**：① 内部 Agent 路由依旧写死、chief-engineer 不动态决策；② CAD 是否触发靠消息子串匹配，易误触发（一条只是"讨论 SolidWorks"的消息也会触发一次 Fake CAD 干跑）且无论请求什么都只建 plate_basic_4holes。这属协议明确关注的"硬编码流程假设"。
- **风险**：当前单零件、单路由可控；但若扩到多零件/多路由，关键字触发 + 硬编码 spec 会成为错误来源（建了不该建的、或建错了零件却报成功）。
- **建议**：下一阶段把"触发 + 选零件 + 选路由"改为结构化输入驱动（例如从 CADModelSpec / 请求字段解析，而非扫消息子串），并把动态内部路由列为 ARCH-B 的收尾目标。当前阶段不强求。

### ARCH-其他 — 未发现明显风险

- **模块边界**：清晰。`SolidWorksMainWorkflowRunner` 通过反射（`Type.GetType("SolidWorksWorker.RealSolidWorksWorker,…")` + `Activator.CreateInstance`）加载真实 Worker，**刻意避免 PlatformCore 编译期依赖 Workers 项目**——是正确的解耦（代价是绑定改为运行时校验，已由测试兜底）。Fake worker 经 `WorkerRegistry` 解析。COM 不泄漏到 PlatformCore。
- **WorkflowEngine 仍是统一入口**：集成走标准 `ExecuteAsync(steps, context)`，未新增旁路引擎。
- **Retry/FailureReport/HumanApproval 可复用**：集成复用引擎四态；`ResolveFailureStage` 把各步失败映射为可行动 failure_stage。
- **LLM Runtime 接口**：仍保留（`IRuntimeModelClient` + Mock 回退 + 仅 chief-engineer）。
- **共享工具抽取有进展**：新增 `PlatformPathResolver.FindProjectRoot()` 被 CliHost/Orchestrator/Bootstrapper/self-check 复用——回应了技术债中的"共享工具"。
- **LOW：双重硬编码 plate spec**：`SolidWorksMainWorkflowRunner.CreateDefaultPlateSpec` 与 `ChiefEngineerOrchestrator.CreatePlateBasicFourHolesSpec` 近乎重复，建议合一。

## 5. 可靠性风险

### REL-B'（本轮新增，LOW）：真实 CAD 集成路径无执行前 HumanApproval 门

- **位置**：`SolidWorksMainWorkflowRunner` 步骤 3 在三重开关满足时直接执行真实 Worker；QualityGate 在执行之后（产物校验）。
- **问题**：真实 CAD 会启动 COM、写文件，但集成路径靠"请求 flag + dry_run=false + 环境 flag"三重显式开关放行，**没有执行前的 HumanApproval 门**。引擎本身支持 `NeedsHumanApproval`，此处未用于 CAD 前置审批。
- **评估**：三重开关本身已是强显式 opt-in，风险可接受；但对"启动真实 CAD"这种外部副作用操作，可考虑增加一个可选的执行前 HumanApproval 步骤。当前不阻塞。
- **建议**：下一阶段评估是否在真实执行前插入 HumanApproval Gate（复用引擎既有能力），或至少在文档中明确"真实 CAD 由三重开关而非审批门控制"。

### REL-C'（本轮新增，LOW）：每次触发都会写入时间戳输出目录

- 集成触发后（即使 Fake 干跑）都在 `output/solidworks/main_workflow/plate_basic_4holes/<时间戳>` 写产物；反复调用会累积目录（隔离、无覆盖，仅磁盘增长）。建议后续加保留策略或清理指引。

### 其余可靠性面 — 表现良好

- **无假成功**：集成 `qualityGatePassed = finalDecision==Passed && workflow==Passed`；`BuildFinalReview` fail-closed；发布包 `deliverable_status` 现阻断失败组件（REL-A 已修）。
- **无异常吞成成功**：集成经引擎异常边界（ARCH-2）；Worker/发布包失败即 Failed。
- **无无限重试 / 外部调用有超时**：RetryPolicy 有界；LLM 双超时；COM 连接/断开/执行三阶段超时（上一轮已确认）。
- **文件覆盖**：集成写隔离时间戳目录；发布包只读源、写隔离目录；各 builder 落盘校验非空。**无覆盖用户源风险。**
- **路径硬编码**：集成用 `PlatformPathResolver` + 可由 context 覆盖 `project_root`/`solidworks_output_directory`；无机器绝对路径硬编码。
- **环境依赖**：`SW_ENABLE_REAL_EXECUTION` 等经 `FromEnvironment` 声明；集成 flag 经 context 传入。
- **COM 挂死**：三阶段超时护栏就位（集成真实执行走同一 Worker）。残留进程 `ExitApp` 仍在技术债。
