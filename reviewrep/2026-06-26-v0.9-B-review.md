## 4. 高优先级问题

### HIGH-001：PlatformBootstrapper 注册 PlaceholderWorker 而非 FakeSolidWorksWorker — self-check 产生假通过

**位置**:
- `src/PlatformCore/PlatformBootstrapper.cs:130` — `platform.WorkerRegistry.Register(new PlaceholderWorker("FakeSolidWorksWorker", "SolidWorks"))`
- `src/PlatformCore/PlatformSelfCheckRunner.cs:532` — `fakeSolidWorksWorkerRegistered = platform.WorkerRegistry.GetAll().Any(worker => worker.Name == "FakeSolidWorksWorker")`
- `src/PlatformCore/WorkerRegistry/PlaceholderWorker.cs:6-35` — PlaceholderWorker 只实现 `IWorker`，不实现 `ISolidWorksWorker`

**问题**:
平台启动时注册的 Worker 是 `PlaceholderWorker`（名称碰巧叫 "FakeSolidWorksWorker"），而不是 `SolidWorksWorker.FakeSolidWorksWorker`。两者的行为完全不同：

| | PlaceholderWorker (当前注册) | FakeSolidWorksWorker (self-check 反射创建) |
|---|---|---|
| 实现接口 | `IWorker` | `IWorker` + `ISolidWorksWorker` |
| `ExecuteAsync(WorkerInput)` | 返回一个通用 placeholder JSON artifact | 委托给类型化的 `ExecuteAsync(SolidWorksWorkerRequest)` |
| `ExecuteAsync(SolidWorksWorkerRequest)` | 不存在 — 调用会崩溃 | 生成 SLDPRT.txt / STEP.txt / build_report.json / 日志 |
| CAD 安全断言 | 无 | 有 ("No SolidWorks process" / "No COM call" 等) |
| Dry-run 边界检查 | 无 | 有 (拒绝 `DryRun=false` / `AllowRealCadExecution=true`) |

self-check 的 `RunSolidWorksSkeletonChecks` (第 537 行) 通过反射从 `SolidWorksWorker.dll` 加载真正的 `FakeSolidWorksWorker` 并测试，但第 532 行的 `fakeSolidWorksWorkerRegistered` 字段只检查 `platform.WorkerRegistry` 中是否有**名称**为 "FakeSolidWorksWorker" 的 Worker。PlaceholderWorker 满足此条件，因此该字段返回 `true`，但运行时任何调用 `WorkerRegistry.GetByName("FakeSolidWorksWorker")` 的代码获得的都是 PlaceholderWorker，不会执行真正的 dry-run 断言。

**风险**:
- **假通过**: self-check 报告 `fake_solidworks_worker_registered: true`，但平台实际注册的是 PlaceholderWorker
- **运行时行为不一致**: self-check 验证了正确的 FakeSolidWorksWorker，但生产路径走的是 PlaceholderWorker
- **接口转型崩溃**: 任何将 `IWorker` 转型为 `ISolidWorksWorker` 的代码会在运行时抛出 `InvalidCastException`
- **分层绕过**: PlaceholderWorker 的 `ExecuteAsync(WorkerInput)` 直接返回 Completed，不会执行任何 dry-run 安全检查，相当于绕过 Validator/Reviewer/QualityGate 链路

**建议修复**:
```csharp
// PlatformBootstrapper.cs:130
// 改为注册真正的 FakeSolidWorksWorker
platform.WorkerRegistry.Register(new SolidWorksWorker.FakeSolidWorksWorker());
```

如果需要保持 PlaceholderWorker 作为后备（推荐），可同时注册两者：
```csharp
platform.WorkerRegistry.Register(new SolidWorksWorker.FakeSolidWorksWorker());
// PlaceholderWorker 不再以 "FakeSolidWorksWorker" 命名，避免名称混淆
```

同时建议 `fakeSolidWorksWorkerRegistered` 的检查逻辑从名称匹配改为类型匹配：
```csharp
var fakeSolidWorksWorkerRegistered = platform.WorkerRegistry.GetAll()
    .Any(worker => worker is SolidWorksWorker.FakeSolidWorksWorker);
```

**为什么重要**: 这是 self-check 可靠性问题的核心 — self-check 验证了正确的代码但平台运行了错误的实现。与历史上 I7 问题的 `failure_report_lying` 模式同源：日志/检查声明了某个行为已就绪，但实际运行时并未生效。

## 5. 中优先级问题

### MEDIUM-001：CreateFakeSolidWorksWorker 硬编码 Debug 构建路径

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:630`

**问题**:
```csharp
?? Assembly.LoadFrom(Path.Combine(projectRoot, "src", "Workers", "SolidWorks",
    "bin", "Debug", "net10.0", "SolidWorksWorker.dll"));
```

路径硬编码了 `bin/Debug/net10.0`。在 Release 构建或使用不同 .NET 版本（如 `net9.0`）时，`Assembly.LoadFrom` 将抛出 `FileNotFoundException`，被外层 `catch` 吞掉并返回全部 `false` 的检查结果。

**风险**: self-check 在非 Debug 环境下全部 SolidWorks 字段静默返回 `false`。

**建议修复**: 使用 `typeof(FakeSolidWorksWorker).Assembly` 或扫描 `bin` 目录查找实际输出路径。

### MEDIUM-002：SolidWorksArtifactValidator 路径边界检查使用字符串 IndexOf 可被绕过

**位置**: `src/Modules/CADModeling/validators/SolidWorksArtifactValidator.cs:50-53`

**问题**:
```csharp
if (fullPath.IndexOf($"{Path.DirectorySeparatorChar}output{Path.DirectorySeparatorChar}solidworks{Path.DirectorySeparatorChar}",
    StringComparison.OrdinalIgnoreCase) < 0 && ...)
```

该检查使用字符串包含判断而非路径规范化比较。恶意或异常构造的路径（如 `output\solidworks\..\..\..\Windows\System32\evil.dll`）可以通过 `IndexOf` 检查（因为包含 `output\solidworks\`）但实际解析后指向 `Windows\System32`。

**风险**: 低 — 当前所有路径由平台内部生成（FakeSolidWorksWorker 内部拼接），攻击面小。但作为防御性代码，建议使用正确的路径边界检查。

**建议修复**: 使用 `Path.GetFullPath` 规范化后检查是否以预期的 `output\solidworks` 绝对路径开头：
```csharp
var expectedRoot = Path.GetFullPath(Path.Combine(/* base */, "output", "solidworks"));
if (!fullPath.StartsWith(expectedRoot, StringComparison.OrdinalIgnoreCase))
{
    issues.Add($"...");
}
```

### MEDIUM-003：FakeSolidWorksWorker 的 IWorker.ExecuteAsync 重载丢失 CancellationToken

**位置**: `src/Workers/SolidWorks/FakeSolidWorksWorker.cs:107`

**问题**:
```csharp
var result = await ExecuteAsync(request, CancellationToken.None);
```

`ExecuteAsync(WorkerInput)` 重载（IWorker 接口实现）调用类型化重载时传入 `CancellationToken.None`，完全丢失了调用方的取消支持。如果 WorkflowEngine 在步骤超时时尝试取消 Worker，取消信号不会传播到文件 I/O 操作。

**风险**: Worker 执行不可取消 — 文件 I/O 可能阻塞到 OS 超时。

**建议修复**: 从 `IWorker` 接口获取 CancellationToken（如果接口支持），或至少记录此限制为已知问题并在 V1.0 修复。

### MEDIUM-004：SolidWorksBuildPlanReviewer 的 ParseDouble/ParseInt 返回 0 产生歧义

**位置**: `src/Modules/CADModeling/reviewers/SolidWorksBuildPlanReviewer.cs:74-86`

**问题**:
```csharp
private static double ParseDouble(SolidWorksOperation? operation, string key) =>
    operation is not null &&
    operation.Parameters.TryGetValue(key, out var value) &&
    double.TryParse(value, out var parsed)
        ? parsed
        : 0;  // ← 0 既表示 "解析失败/参数缺失" 也表示 "值恰好为 0"
```

`ParseDouble` 和 `ParseInt` 在参数缺失、格式错误或 operation 为 null 时均返回 `0`。对于 `length_mm`、`hole_diameter_mm` 等必须为正数的维度，返回 `0` 会被下游的逻辑（如 `dimensions.LengthMm <= 0`）正确拒绝。但这是偶然正确 — 如果将来有人添加一个"0 是合法值"的维度参数，会产生误判。

**风险**: 低 — 当前所有维度参数均为正数。但解析失败静默降级为 0 而没有任何日志，调试困难。

**建议修复**: 将 ParseDouble 改为返回 `double?`（null 表示解析失败），或在解析失败时记录日志。

## 12. 重点确认

### 12.1 V0.9-B 架构分层是否正确？

**✅ 正确。** 代码严格遵循 Skill → Worker → Validator → Reviewer → QualityGate 分层。Skill 不调用 Worker，Agent 不调用 Worker，Gateway 不暴露 Worker。`ISolidWorksWorker` 接口扩展了 `IWorker`，设计合理。

### 12.2 Worker 注册不一致是否为设计意图？
