## 4. 高优先级问题

### HIGH-001：本机存在间歇性包装 SolidWorks 输出文件的第三方过滤层，已波及证据与至少一个发布包，现有门禁对它基本不可见

**位置**：运行环境；受影响文件见下表。检测缺口在 `SolidWorksArtifactValidator`、发布包校验与证据审计。

**问题（事实）**：

| 位置 | 原生 SLDPRT | 带外来文件头 | 外来文件头 |
|---|---:|---:|---|
| `evidence/solidworks/**`（已入库） | 90 | **8**（08-24 一份 + `v2_1_b_refresh` 七份） | `88 7d 1c ?? 4f 00 08 00` |
| `output/solidworks/**`（本地，gitignored） | 33 | **7**（含 `cad-e2e-20260811_…/artifacts/jacket_basic.SLDPRT`，以及 08-28 我 V2.1-A 开发期的 4 次诊断） | 同上 |

- 这 8 个入库文件就是全部 `size_bytes` 失配的文件，差值均为 +4096，且只有它们缺少原生特征（原生文件偏移 4–7 为 `00 00 00 04`，并多次出现容器签名 `14 00 06 00 08 00 68 94`）。
- `git cat-file` 证明 **`ab63fbd` 入库的就是包装后的字节**。
- 文件 mtime 早于同组报告写入时间 0.5 秒，之后未变，因此不是后期被改写。
- 2026-09-07 我运行 `dotnet test` 时，这 7 份的物理长度校验**通过了**（449/449）；09-09 Codex 用同一校验看到 +4096。同一份磁盘文件，不同时间、不同进程看到的长度不同。
- 09-09 之后（V2.2-C、V2.2-D 共数十份）没有再出现。

**推断（标注为推断，未证实）**：上述现象与透明加密/DLP 类文件过滤驱动一致。这类驱动的典型行为是：给受控进程（如 CAD）写出的文件加 4 KB 头并加密正文，对白名单进程呈现解密视图，对其他进程呈现原始字节。V2.2-C 文档记录 09-09 时 `LeaderTerm` 与 `LdMFilter` 在运行。具体产品与策略需要向 IT 确认，我无法从仓库内证实。

**风险**：

1. **看似成功但实际错误的 CAD 交付物**：发布包里的 SLDPRT 在本机 SolidWorks 中能打开、能通过重开验收，拷到没有该驱动的机器上却可能无法读取。08-11 的夹套发布包已经是这种情况。
2. **现有防线大多走白名单视图**：SolidWorks 重开验收、可能还有 .NET 的长度读取，都看不到原始字节。只有「报告写入时」与「后来校验时」的视图恰好不一致，才会触发失配。V2.2-D 的清单 SHA-256 由 Python 计算，若计算时拿到的是原始字节，可以起到检测作用，但这一点依赖驱动当时的策略，不可依赖。
3. 已入库的 8 个 SLDPRT 在别的机器上很可能不可读。它们已不再参与授权，影响限于历史审计。

**建议修复**：

1. **（需要你本人或 IT 处理）** 确认 `LdMFilter`/`LeaderTerm` 是什么、策略是否覆盖本项目目录，能否把项目目录排除在外。这属于安全软件配置，Codex 和我都不应自行修改。
2. **（Codex）** 在 SLDPRT 保存后、发布包组装后、证据审计时增加**原生格式签名检查**作为绊线，并加入**独立进程的原始字节比对**，例如与 `git hash-object` 的结果或非 CAD 进程计算的 SHA-256 比对。失配即失败关闭。
3. **（Codex）** 在 `docs/technical_debt.md` 与对应 `api_evidence.md` 中，把「4096 字节原因未查明」更新为上述物理事实，并列出 8 个受影响的历史文件。**不改动这些文件本身。**

### HIGH-002：两个受保护的「未取证即拒绝」自检字段不再检查它们名字所说的事，其中一个本轮被换弱，另一个（我的）早已空转

**问题**：

- **`unverified_api_blocks_real_execution`（Codex，本轮）**
  - **原判据**：注册表中存在自报 `unverified` 的 Handler，并且 `registry.ValidateForRealExecution(probePlan)` 在连接前以 `feature_api_unverified` 拒绝。这是真实预检路径上的行为证明。
  - **Revolve 取证后**：注册表里已经没有 `unverified` Handler，原判据会翻成 false。
  - **新判据**：用反射克隆第一个 Handler 的证据并把 `Status` 设成 `"unverified"`，直接调用 `FeatureExecutionEvidencePolicy.ValidateEvidence`。该函数第一行就是 `if (!evidence.AllowsRealExecution)`，所以这实际上只验证了「`AllowsRealExecution` 对 `unverified` 返回 false」。
  - 另一个条件 `preflightRunsBeforeConnection` 只检查两个方法**是否存在**。
  - 上方注释仍写着「判据是『注册表里存在未取证 Handler，且它在连接 COM 之前被拒绝』」，与代码矛盾。
- **`unverified_feature_blocks_execution`（我，V2.1-A）**
  - 这是我做的「双向、状态驱动」判据：遍历五个复杂特征，verified 必须能过门，unverified 必须被拒。
  - 自 `bbeafc9` 五个全部取证后，「unverified 必须被拒」这一半**没有任何样本**，一直空洞为真。
  - 我在 V2.1-A 报告里把它当作优点写，没有意识到它会在「全部取证」时失去一半鉴别力。

**风险**：

- 真实行为目前没有丢：xUnit 用新增的 `UnverifiedRevolveFixture` 注入未取证 Handler，端到端断言 Worker 在连接前拒绝、`ConnectAsync` 次数为 0。这一点我在测试 diff 中逐条核对过，完整测试也通过了。

  1. V2.1-A 的 `handlers.Length == 5`；
  2. 我的判据空转；
  3. 本轮的替换。
- 「被保护的东西修好了 → 保护它的检查随之失效或被改弱」。下次有人重构 `ValidateEvidence`，自检仍会报 true。

**建议修复**（`PlatformSelfCheckRunner.cs` 不在证据绑定清单中，修复**不需要重采证据**）：

1. `unverified_api_blocks_real_execution`：在自检内构造一个注册表，与测试夹具同法用 `unverified` 克隆替换其中一个 Handler，调用**该注册表**的 `ValidateForRealExecution(probePlan)`，要求以 `feature_api_unverified` 拒绝。删除只查方法存在的 `preflightRunsBeforeConnection`，或改为行为断言。同步修正注释。

3. 加一条通用约束：**每个受保护的「拒绝类」判据必须实际观测到至少一个负样本**，否则字段为 `null`（未观测），不能为 `true`。这与 V2.1-B 已引入的 `bool?` 语义一致。

- 令牌实现是好的：32 字节随机数，仅保存 SHA-256，用 `FixedTimeEquals` 比较，`404` 不区分「任务不存在」与「无权访问」，并以 `SemaphoreSlim` 防并发。
- 但持有令牌的一方就是发起请求的一方，`submitted_by` 只用于审计。**请求者可以批准自己的请求**，其中包括触发真实 CAD 的请求。

**风险**：单人本地使用时没有问题；一旦接入多用户宿主，HumanApproval 门的实际强度就只等于令牌保密程度。

**建议**：在多用户部署前，把审批人身份绑定到宿主认证，并禁止审批人与请求者为同一身份。在此之前，保持文档中的现有限定说明。

## 6. 低优先级问题 / 细节建议

- **LOW-001：47 个入库路径超过 260 字符（最长 313）**。来源是自检夹具树嵌套在 `output/validation/<阶段>/solidworks/self-check/release-source/output/solidworks/…` 之下。本机 `core.longpaths=true` 所以无感，但在未开启该选项的 Windows 上，全新克隆会检出失败。建议把自检夹具归档路径压平。
- **LOW-002：仓库体积增长**。`output/validation` 31 MB、`evidence` 17 MB，`e87a635` 一次新增 16.7 万行，其中大量是构建日志与测试 TRX。建议制定保留策略，二进制文件考虑使用 LFS。
- **LOW-003（自评）：`feature_regression_tests_passed` 名不副实**。它运行的是五个样本的 Validate 与 BuildPlan dry-run，**并不运行测试**。这是我在 V2.1-A 起的名字，与我在 V2.1-B 报告中批评 Codex 的 `hole_feature_regression_tests_passed` 同属命名问题；程度较轻，因为它不是纯合取式，确有内容。建议改名为 `complex_feature_dry_run_passed`，并同步基线。
- **LOW-004：`FeatureExecutionEvidencePolicy.ValidateEvidence` 新增了公开参数 `evidenceOverride`**。目前仅 `SketchHandler` 传入自身的 `RightPlaneApiEvidence`，自检用它注入伪造证据。公开接口允许任意调用方指定证据，信任面比必要的大。建议改为 `internal`，或由 Handler 提供 `EvidenceFor(feature)`。
- **LOW-005：`docs/technical_debt.md` 状态过期**。V2.1-A 的 `HIGH-001`（种子拆分）与 `HIGH-002`（方向符号）已在 V2.2-C 修复：代码已核对（`ValidateSingleSeed`、`PrincipalAxisRules.TryResolveFlip`），并有四方向真机候选；但该文档仍标为「待处理，优先安排」。

## 7. 架构评估

- **边界一致性**：
  - 良好。旋转与 RightPlane 草图只在 Adapter 内触达 COM，Handler 只做校验与转发。
  - `RevolveProfileRules` 是纯规则，被 Handler 前置校验与 Adapter 防御校验复用，没有复制逻辑。
  - 旧 Adapter 通过默认接口方法失败关闭，不需要替身伪造支持。
- **接口稳定性**：
  - `ISolidWorksFeatureAdapter` 新增带失败默认实现的方法，兼容性好。
  - `PlatformSelfCheckRunner.RunAsync` 在 `CancellationToken` **之后**追加了可选参数 `partFamilyEvidenceRoot`，调用方需用命名参数，属于轻微的 API 形状问题。
- **耦合风险**：
  - `PartFamilyProductionEvidencePolicy` 目前硬编码「只服务 shaft/jacket」、各族最少用例数和唯一的清单常量。再加一个族时，就需要改它并重采全部 14 组候选。
  - 建议下一次扩族前，把「受限族」做成数据驱动：每个族一份清单、一个常量。
- **扩展风险**：
  - V2.2-D 的授权绑定精确参数档案（三组输入）。文档明说不外推，这一点是对的。
  - 但也意味着每新增一个尺寸就要一轮真机采证。这是有意的取舍，应在路线图中写明成本。
- **Workflow 兼容性**：
  - V2.2-B 的质量门组合采用「最严重结果获胜」（Failed > Rejected > NeedsHumanApproval > Passed），门禁抛异常即判 Failed，不能用人工审批覆盖另一门的打回。**失败关闭正确。**
  - V2.2-A 审批以存储原子操作三键匹配并消费，防重放与防并发都有测试覆盖。

## 12. 最终结论

**PASS WITH COMMENTS — 可以继续。**

V2.2-C 与 V2.2-D 是本项目迄今质量最高的两轮 CAD 工作：

- V2.2-C 找出了一个潜伏至少一个月、连我这个作者兼审查者都没有发现的 STEP 假成功，并从封送、回退、身份核对、双格式独立验收四个层面修复，而不是只修症状；
- V2.2-D 的族证据门在「不信任报告自报结果」这一点上做得最彻底，我对 STEP 顶点的独立解析也与其声明一致；
- 过程中的失败候选全部保留、没有被追认。

需要注意的是两个方向：

1. **环境层面（HIGH-001）**：本机有一个会改写 CAD 文件字节的过滤层。它已经包装过一个发布包产物，而平台现有的大部分验证都经过它的白名单视图，看不到原始字节。**这是对外交付前必须排除的风险**，需要你本人确认。
2. **自检语义层面（HIGH-002）**：受保护字段的判据被换弱或空转，而回归闸看不见这种变化。修复成本低，不需要重采。

建议先完成 HIGH-002 再提交 V2.2-D；HIGH-001 的平台绊线可与下一次重采合并完成。
