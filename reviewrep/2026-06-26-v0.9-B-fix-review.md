## 4. 高优先级问题

### HIGH-001：Self-check 反射调用失败时静默降级，不区分"功能不可用"与"自检基础设施损坏"

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:628`

```csharp
catch (Exception ex) when (ex is IOException or InvalidOperationException or MissingMethodException
    or TargetInvocationException or FileNotFoundException or FileLoadException or BadImageFormatException)
{
    platform.AuditLog.Record("solidworks", "self-check", "solidworks_skeleton_check_failed", ex.GetBaseException().Message);
    return new SolidWorksSkeletonSelfCheckResult(false, false, false, false, false, false, false, false, false, false, false, false, false, false);
}
```

**问题**: 当 `workerMethod.Invoke()` 因方法签名变更抛出 `TargetInvocationException` 时，该 catch 返回全部 14 个字段为 `false` 的 `SolidWorksSkeletonSelfCheckResult`。审计日志记录了错误，但 self-check 报告中无法区分以下三种情况：
1. SolidWorks 模块真的未启用（`module.yaml` 缺少配置）
2. Worker 类型正确加载但签名不匹配（代码 bug）
3. 反射调用过程中抛出了意外异常（运行时环境问题）

三者产生的 self-check JSON 输出完全一致（14 个 `false`）。

**风险**: 如果 Codex 未来修改了 `ISolidWorksWorker.ExecuteAsync` 的方法签名（例如增加参数），self-check 不会显式报错 — 它只是静默地报告 "SolidWorks 检查全部不通过"，而没有明确指出 "自检本身的反射调用失败了"。这种**假阴性**会误导排查方向。

**建议修复**:
```csharp
// 在 catch 块中返回时标记一个专用字段（需在 SelfCheckReport 中新增）
return new SolidWorksSkeletonSelfCheckResult(
    false, false, false, false, false, false, false, false, false, false, false, false, false, false)
{
    SelfCheckInfrastructureError = ex.GetBaseException().Message
};
```

或在 SelfCheckReport 中增加一个 `SolidWorksSelfCheckError` 字符串字段，在正常路径设为 `null`，异常路径写入 `ex.GetBaseException().Message`。

**为什么重要**: 假阴性同样危险 — 如果自检基础设施损坏但没有暴露，开发者会花费大量时间排查"为什么模块未启用"，而真正的问题是自检代码本身需要更新。这与 V0.9-B 的 HIGH-001 是同源的"声明与行为不一致"模式。

### HIGH-002：PlaceholderWorker 回退路径中 CancellationToken 完全丢失

**位置**:
- `src/WorkerContracts/IWorker.cs:11-12` — 默认接口方法
- `src/PlatformCore/PlatformBootstrapper.cs:144` — PlaceholderWorker 回退
- `src/PlatformCore/WorkerRegistry/PlaceholderWorker.cs` — 不覆盖 CancellationToken 重载

**问题**: `IWorker` 的默认接口方法实现：

```csharp
Task<WorkerOutput> ExecuteAsync(WorkerInput input, CancellationToken cancellationToken) =>
    ExecuteAsync(input);  // ← token 直接丢弃
```

当 `PlatformBootstrapper.TryCreateWorker` 返回 `null`（例如 SolidWorksWorker.dll 未编译或被移动），回退到 `PlaceholderWorker`。但 `PlaceholderWorker` 不覆盖 `ExecuteAsync(WorkerInput, CancellationToken)`，因此继承默认实现 — token 被丢弃。任何通过 WorkflowEngine 对 PlaceholderWorker 发起的超时取消都不会生效。

**风险**: 如果 WorkflowEngine 配置了步骤超时（例如 30s），当 PlaceholderWorker 因某种原因阻塞时，`CancellationToken` 不会被检查，导致：
- Workflow 步骤永久挂起
- 超时逻辑被绕过
- 异常可能以 `TaskCanceledException` 而非干净的超时形式抛出

**建议修复**:
1. 在 `PlaceholderWorker` 中覆盖 `ExecuteAsync(WorkerInput, CancellationToken)`，在方法入口调用 `cancellationToken.ThrowIfCancellationRequested()`
2. 或者，让默认接口方法也检查 token：
```csharp
Task<WorkerOutput> ExecuteAsync(WorkerInput input, CancellationToken cancellationToken)
{
    cancellationToken.ThrowIfCancellationRequested();
    return ExecuteAsync(input);
}
```
   这样所有未覆盖的 IWorker 实现至少会在入口处响应取消。

**为什么重要**: 取消机制是 Workflow 可靠性的最后防线。回退路径丢失取消支持意味着在最需要超时保护的场景（外部依赖不可用时）反而最脆弱。

## 5. 中优先级问题

### MEDIUM-001：Self-check 类型验证使用 FullName 字符串比较，对命名空间变更脆弱

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:552`

```csharp
var fakeSolidWorksWorkerRegistered =
    registeredFakeSolidWorksWorker?.GetType().FullName == "SolidWorksWorker.FakeSolidWorksWorker" &&
    registeredFakeSolidWorksWorker.GetType().GetMethods().Any(method =>
        method.Name == "ExecuteAsync" &&
        method.GetParameters().Length == 2 &&
        method.GetParameters()[0].ParameterType.Name == nameof(SolidWorksWorkerRequest));
```

**问题**: `FullName == "SolidWorksWorker.FakeSolidWorksWorker"` 是区分大小写的字符串字面量比较。如果命名空间从 `SolidWorksWorker` 变更为 `PlatformCore.Workers.SolidWorks` 或类重命名，此检查静默返回 `false`，然后 `workerResult` 不会被创建（第 559 行 `if (plan is not null && fakeSolidWorksWorkerRegistered && ...)` 为 false），导致 SolidWorks self-check 大量字段变为 false。

**风险**: 中等 — 新测试 `PlatformBootstrapperRegistersRealFakeSolidWorksWorker` 通过 `Assert.IsType<FakeSolidWorksWorker>(worker)` 提供了一定保护，但该测试是编译时类型检查。如果命名空间变更，需要同时更新两处字符串。

**建议修复**: 使用 `is` 模式匹配或 `typeof(FakeSolidWorksWorker).IsAssignableFrom(worker.GetType())`：
```csharp
var fakeSolidWorksWorkerRegistered =
    registeredFakeSolidWorksWorker is FakeSolidWorksWorker &&
    ...
```
但这需要 `PlatformSelfCheckRunner` 引用 `SolidWorksWorker` 项目。如果不想增加项目引用，至少将字符串提取为 `const string`：
```csharp
private const string FakeSolidWorksWorkerFullName = "SolidWorksWorker.FakeSolidWorksWorker";
```

### MEDIUM-004：CandidateAssemblyPaths 未处理子目录权限异常

**位置**: `src/PlatformCore/PlatformBootstrapper.cs:216-218`

```csharp
foreach (var path in Directory
             .EnumerateFiles(workerRoot, fileName, SearchOption.AllDirectories)
             .Where(path => ...)
             .OrderByDescending(File.GetLastWriteTimeUtc))
```

**问题**: `Directory.EnumerateFiles(workerRoot, ..., SearchOption.AllDirectories)` 在 `src/Workers` 子目录权限受限时会抛出 `UnauthorizedAccessException`，该异常在 `CandidateAssemblies` 的 foreach 循环中出现，但没有被 `CandidateAssemblies` 捕获（它的 try-catch 只包裹 `Assembly.LoadFrom`）。这会导致整个 `RegisterWorkers` 调用失败。

**风险**: 低 — 开发环境中 `src/Workers` 子目录不太可能有权限问题。但在受限用户账户或某些 CI 环境中可能触发。

**建议修复**: 在 `CandidateAssemblyPaths` 中对 `EnumerateFiles` 增加 try-catch，或使用 `EnumerateFiles` 的重载 + `EnumerationOptions` 跳过不可访问目录（.NET 7+ 支持）。

## 7. 架构评估

### 边界一致性: ✅ 良好

- **Worker 注册改进**: Bootstrapper 现在优先通过反射加载真实 `FakeSolidWorksWorker`，回退到 PlaceholderWorker。这个"尝试-回退"模式比之前直接用 PlaceholderWorker 冒充真实 Worker 正确得多。
- **IWorker 接口扩展**: 新增的 `ExecuteAsync(WorkerInput, CancellationToken)` 默认接口方法遵循开闭原则 — 不破坏已有实现，允许逐步迁移。
- **self-check 与运行时一致性**: self-check 现在使用 WorkerRegistry 中已注册的同一个 Worker 实例，消除了 V0.9-B 中"self-check 验证 A 但平台运行 B"的不一致。✅

### 接口稳定性: ✅ 良好

- `IWorker` 新增 CancellationToken 重载 — 默认实现委托给无参版本，所有已有 IWorker 实现行为不变。
- `SolidWorksArtifactValidator` 新增可选 `configuredOutputRoot` 构造参数 — 无参构造函数保持原有行为。
- `SolidWorksBuildPlanReviewer.ExtractDimensions` 返回类型从值元组变为可空元组 — 调用方已全部适配。

### 耦合风险: ✅ 低

- `PlatformBootstrapper` 新增对 `System.Reflection` 的依赖，但这是 .NET 标准库，不引入外部依赖。
- `TryCreateWorker` / `CandidateAssemblies` / `CandidateAssemblyPaths` 均为 private static，不暴露给外部消费者。

### 扩展风险: ✅ 受控

- 新增 Worker 时只需确保 Worker 项目被编译到 `bin` 目录，Bootstrapper 的 `CandidateAssemblyPaths` 会自动发现。但依赖"最新的 bin 目录"隐式约定（`OrderByDescending(File.GetLastWriteTimeUtc)`），在同时存在 Debug 和 Release 构建时可能选择非预期版本。

### Workflow 兼容性: ✅ 无影响

- 本次修改不触及 WorkflowEngine、RetryPolicy 或 Orchestrator 核心逻辑。
