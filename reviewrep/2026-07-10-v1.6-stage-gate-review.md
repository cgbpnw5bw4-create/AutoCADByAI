## 2. 结论理由

先说清楚：**本轮的工程实质是我连续四轮点名的 TEST-A，Codex 这次真正做对了，而且做得很好。** COM 调用层被抽象为 `ISolidWorksComFacade` / `ISolidWorksFileVerifier` / `ISolidWorksPropertyReader` 三个可注入接口，四个 builder 全部改为构造函数注入，配套的单元测试是**真实的行为测试**（注入 fake 让 `FeatureCut4` 返回 null、让 `SaveAs` 返回 true 但文件校验器报告文件不存在），不是占位。标题栏属性回读的语义也从"读不回来就当通过"收紧为"必须读回且相等"——这修掉了一个真实的潜在假成功。

但是本版本**不能进入下一阶段**，理由是三条硬性的、可验证的事实：

1. **主项目当前无法编译。** `PlatformSelfCheckRunner.cs` 新增的 `WriteRealAcceptanceOutputs` 方法引用了 **9 个从未定义的符号**（1 个类型 + 8 个方法）。`PlatformSelfCheckRunner` 是单文件、非 `partial` 的 `public static class`，文件内也没有 `using static`，因此这些符号无处可寻。`PlatformCore` 会以 CS0246 / CS0103 失败，进而**所有测试和 self-check 都无法运行**。协议第 6 节明确把"构建失败"列为 BLOCKER。

2. **即使补齐编译，self-check 的 `final_status` 也必然是 `Failed`。** 新增的门禁条件要求 `docs/solidworks_real_acceptance_protocol.md` 存在、且 `docs/version_stage_index.md` 含 `V1.6-TEST-A` 字样。两者**都不存在**。

3. **磁盘上唯一的 self-check 报告是 07-08 的旧报告，`final_status: "Passed"`，且完全不含本轮新增的 12 个字段。** 它与当前代码不对应。任何人（包括我上一轮）若引用它作为"本版本通过"的证据，都会得到一个假成功。这正是本项目最高优先级红线所禁止的模式，只不过这次发生在证据层而不是 CAD 输出层。

换句话说：**代码里的防假成功做得更好了，但围绕这份代码的"证明它没问题"的那套机制，本身正在制造假成功。** 这个反差是我给出 NOT APPROVED 的核心原因，而不是那 9 个漏写的符号——符号补上是十分钟的事。

## 4. 架构风险

### ARCH-R1（新增，HIGH）：self-check 从"验证行为"退化为"匹配源码字符串"

**位置**：`src/PlatformCore/PlatformSelfCheckRunner.cs:176-215`

新增的 12 个字段里，有 8 个是这样判定的：

```csharp
var solidWorksComFalseSuccessTestsAdded =
    testFileText.Contains("RejectsComFalse", StringComparison.OrdinalIgnoreCase);
var solidWorksPlateBuilderFakeSuccessGuardTested =
    testFileText.Contains("PlateFeatureBuilderRejectsFeatureCutNull", ...) &&
    testFileText.Contains("PlateBuildReportWriterRejectsPassed", ...);
var solidWorksZeroByteArtifactRejected =
    testFileText.Contains("RejectsEmptySlddrwFile", ...) &&
    solidWorksComInteropText.Contains("SizeBytes <= 0", ...);
```

即：**读取测试源文件的文本，检查里面是否出现某个方法名子串**，然后把结果并入 `final_status`。

这有三个独立的问题：

1. **它不构成"测试通过"的证据。** 字段名叫 `..._fake_success_guard_tested`，但它只证明某个字符串出现在某个 `.cs` 文件里——出现在注释里、出现在一个空的 `[Fact] public void RejectsComFalse() {}` 里，同样为 `true`。这是治理层的假成功：一个自称"守卫已被测试"的字段，与守卫是否真被测试无因果关系。
2. **`solidWorksComInteropText.Contains("SizeBytes <= 0")` 把门禁耦合到源码字面量。** 把 `SizeBytes <= 0` 重构成 `SizeBytes < 1` 或改用已有的 `IsNonEmptyFile(path)`，行为完全等价，self-check 却会失败。这会训练开发者"为了过门禁而不敢重构"。
3. **反向也成立**：删掉测试体只留方法名，门禁照样绿。

**建议修复**：删除这 8 个字符串匹配字段，让 `dotnet test` 成为测试是否通过的唯一证据源。如果确实需要在 self-check 里表达"注入缝存在"，用反射（项目里已经有正确范例：测试 `SolidWorksComFacadeInjectionSeamsAreAvailable` 用 `typeof(LateBoundSolidWorksPlateBuilder).GetConstructor(...)` 断言构造函数签名）——反射检查的是**编译后的真实类型**，字符串匹配检查的是文本。

## 5. 可靠性风险

### REL-R1（MEDIUM）：`real_acceptance_report.json` 内部来源不一致，可自相矛盾

**位置**：`PlatformSelfCheckRunner.cs:2529-2546`

```csharp
var allSourceReportsPassed = ReadJsonBool(packageQualityReportPath, "all_source_reports_passed") ??
                             (sourceReportStatuses.Count > 0 && ...全部 Passed);
var deliverableStatus = ReadJsonString(packageQualityReportPath, "deliverable_status") ??
                        (allSourceReportsPassed ? "Deliverable" : "NotDeliverable");
```

`source_report_final_status` 映射是**当场从最新的各单项报告读出来的**；而 `all_source_reports_passed` 和 `deliverable_status` 只要 `package_quality_report` 存在就**直接采信它**，不做交叉校验。

失败场景：一次旧的发布打包留下 `deliverable_status: "Deliverable"` 的 `package_quality_report.json`；之后一次真实构建失败，产生新的 `build_report.json` (`final_status: "Failed"`)。`WriteRealAcceptanceOutputs` 会生成一份同时写着 `| build_report final_status | Failed |` 和 `| deliverable_status | Deliverable |` 的 `latest_real_outputs.md`。人工验收看表尾就会放行。

**建议修复**：先算 `sourceReportStatuses`，若其中任何一项非 `Passed`，强制 `deliverable_status = "NotDeliverable"` 并追加一条 `deliverable_blocked_by: [...]`；package_quality_report 的值只能收紧、不能放宽。同时给两份产物加 `run_id` / `generated_from_commit`，让跨运行的产物无法被混拼。

### REL-R2（MEDIUM）：位置回退会伪造 `ViewsConfirmed`，而新守卫正以它为证据

**位置**：`src/Workers/SolidWorks/SolidWorksDrawingDimensionBuilder.cs:529-539`

```csharp

{
    report.Warnings.Add("drawing_view_name_fallback: 视图名称或方向名不可完全读取，按 V1.1 创建顺序确认 Front/Top/Right/Isometric。");
```

而 `SolidWorksFakeSuccessGuard.ValidateDimension`（`SolidWorksComInterop.cs:394-400`）正是靠 `report.ViewsConfirmed` 判断四个视图是否到位。

这个回退是 V1.1 就有的既有妥协，本身还算克制（发了 warning）。问题在于**本轮新守卫把它当成了硬证据**：当 SolidWorks 读不出视图名时，`ViewsConfirmed` 会被填满四项，守卫必过。守卫的实际保证强度低于它的字面含义。

**风险等级说明**：当前四个尺寸都是 `CreateLinearDim4` / `ICreateDiamDim4` 的**非关联**标注，用固定图纸坐标，不依附具体视图，所以现阶段不会画错尺寸。但 `ViewsConfirmed` 作为验收证据是不成立的，且一旦将来改为关联标注，这里会直接变成"标到错误视图上但报告 Passed"。

**建议修复**：在 `SolidWorksDrawingDimensionReport` 增加 `views_confirmed_by_position_fallback: bool`；`ValidateDimension` 在该标志为 `true` 时拒绝判 `Passed`（或至少不把 `ViewsConfirmed` 计为已确认证据）。

### REL-R3（MEDIUM）：新记录字段的默认值偏向"成功"，且依赖 `"none"` 魔法哨兵

**位置**：`src/DomainSchemas/SolidWorksBuildPlan.cs:213-219`

```csharp
public sealed record SolidWorksDrawingDimensionResult(
    string Name, double ExpectedValueMm, string Status, string FailureStage,
    string ApiStrategy, string Message,
    bool Attempted = true,        // ← 默认成功
    bool Success = true,          // ← 默认成功
    string FailureReason = "none");
```

两个问题：

1. **在一个以"假成功比显式失败更危险"为最高原则的代码库里，把 `Success` 的默认值设为 `true`。** 任何忘记传参的构造点都会静默产出一条"成功"的尺寸证据。当前两个构造点（`SolidWorksDrawingDimensionBuilder.cs:445-453`、`:493-503`）都显式传了值，所以现在无害；但这是一个等着被踩的默认值。

2. **`ValidateDimension` 依赖 `FailureReason` 非空**：

```csharp
if (!dimension.Attempted || !dimension.Success ||
    !dimension.Status.Equals("Passed", ...) ||
    string.IsNullOrWhiteSpace(dimension.FailureReason))   // ← 通过的尺寸必须有非空 FailureReason
```

这条只因为哨兵值恰好是 `"none"` 而成立。如果有人"清理"代码、把通过时的 `FailureReason` 改成 `""`（这是最自然的写法），**所有通过的尺寸报告会被翻成 `Failed`**——一个假失败。逻辑读起来是反的，只靠一个约定串撑着。

**建议修复**：`Attempted` / `Success` 去掉默认值（改为必填）；`FailureReason` 改为 `string?`，通过时为 `null`；`ValidateDimension` 去掉 `IsNullOrWhiteSpace(FailureReason)` 这一项，改为 `dimension is { Attempted: true, Success: true } && dimension.Status == "Passed"`，把"失败必须有原因"单独作为一条断言：`!Success ⇒ FailureReason 非空`。

### 未见退化的可靠性面（本轮显著改善）

- **`SavePart` / `SaveDrawing` / `ExportPdf` 现在显式 `throw new IOException`**，不再"记一条 error 然后继续走到 `FinalStatus = Passed`"。三处（`SolidWorksPlateFeatureBuilder.cs:157-161`、`SolidWorksDrawingBuilder.cs:371-376`、`SolidWorksDrawingTitleBlockBuilder.cs:496-500`）均已修正。
- **标题栏属性回读语义收紧**（`SolidWorksDrawingTitleBlockBuilder.cs:450-452`）：
  `verified` 由旧的 `IsNullOrWhiteSpace(v) || v == value`（读不到就当通过）改为 `!IsNullOrWhiteSpace(v) && v == value`（必须读到且相等）。这修掉了一个我此前未单独立项的真实假成功缺口。
