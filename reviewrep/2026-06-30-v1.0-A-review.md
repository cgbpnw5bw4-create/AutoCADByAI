## 5. 中优先级问题

### MEDIUM-001：DisconnectAsync 无超时 — COM 对象释放路径可能阻塞

**位置**: `src/Workers/SolidWorks/RealSolidWorksWorker.cs:77`

```csharp
await _sessionManager.DisconnectAsync(CancellationToken.None);
```

**问题**: 连接 smoke test 成功后（第 72 行），立即调用 `DisconnectAsync(CancellationToken.None)` 断开连接。`CancellationToken.None` 意味着此调用没有超时、不可取消。如果 `Marshal.FinalReleaseComObject` 因 COM apartment 问题阻塞（例如 SolidWorks 进程正在处理模态对话框），此调用将永久挂起。

同时 `SolidWorksSessionManager.DisconnectAsync` 会获取 `_connectionLock` 信号量。如果 COM 释放阻塞，信号量永远不会释放，后续任何 `ConnectAsync` / `DisconnectAsync` 调用都会在 `WaitAsync` 处死锁。

**风险**: 低概率 — `FinalReleaseComObject` 在正常情况下立即返回。但在 SolidWorks 处于异常状态（许可证过期弹窗、崩溃恢复对话框）时，COM 引用计数归零可能触发进程内清理逻辑，导致阻塞。

**建议修复**: 为 `DisconnectAsync` 添加超时参数（可重用 `ConnectTimeoutSeconds`）：
```csharp
using var disconnectTimeout = new CancellationTokenSource(
    TimeSpan.FromSeconds(options.ConnectTimeoutSeconds));
try
{
    await _sessionManager.DisconnectAsync(disconnectTimeout.Token);
}
catch (OperationCanceledException)
{
    logs.Add("solidworks_disconnect_timeout: COM release timed out, resources may not be fully cleaned up.");
}
```

**为什么重要**: 虽然 `RealSolidWorksWorker` 的 smoke test 路径只连接-断开而不执行任何建模操作，但如果 COM 释放阻塞导致整个 Worker 挂起，WorkflowEngine 的步骤超时也无法恢复（因为 disconnect 使用 `CancellationToken.None`，不受 WorkflowEngine 的 CancellationToken 控制）。

### MEDIUM-002：self-check 中 `Activator.CreateInstance(realSolidWorksWorkerType)` 每次检查都创建新的 SessionManager

**位置**: `src/PlatformCore/PlatformSelfCheckRunner.cs:848` 和 `:734`

```csharp
// InvokeRealSolidWorksWorkerAsync (line 848):
var worker = Activator.CreateInstance(realSolidWorksWorkerType, new object?[] { null, options })

// self-check line 734-735 — SupportsRealBuild 检查:
solidWorksRealBuildNotImplemented =
    realSolidWorksWorkerType.GetProperty("SupportsRealBuild")?.GetValue(
        Activator.CreateInstance(realSolidWorksWorkerType)) is false;
```

**问题**: `Activator.CreateInstance(realSolidWorksWorkerType)` 调用无参构造函数，该构造函数执行 `_sessionManager = sessionManager ?? new SolidWorksSessionManager()`。每次创建实例都会分配一个新的 `SemaphoreSlim` 和一个新的 `LateBoundSolidWorksComActivator`。

在 self-check 的正常路径中（不触发 smoke test），至少创建 **2 个** `RealSolidWorksWorker` 实例：
1. `InvokeRealSolidWorksWorkerAsync` 调用（request flag probe）
2. `InvokeRealSolidWorksWorkerAsync` 调用（env flag probe）
3. `SupportsRealBuild` 属性反射检查（第 734 行）

每次创建都分配了不会被使用的 `SemaphoreSlim`。不会造成功能问题，但属资源浪费。

**风险**: 低 — `SemaphoreSlim` 和 `LateBoundSolidWorksComActivator` 是轻量对象，无 COM 连接。但在频繁运行 self-check 的 CI 环境中，不必要地分配和丢弃同步原语是坏习惯。

**建议修复**: 为 `SupportsRealBuild` 检查使用 `realSolidWorksWorkerType` 的静态反射（`GetProperty` 不需要实例），或者缓存创建的实例：
```csharp
// SupportsRealBuild 是实例属性但返回常量 false — 可通过静态分析验证
// 或者：
using var probeWorker = (IDisposable?)Activator.CreateInstance(realSolidWorksWorkerType);
solidWorksRealBuildNotImplemented = realSolidWorksWorkerType.GetProperty("SupportsRealBuild")
    ?.GetValue(probeWorker) is false;
```

### MEDIUM-003：`SolidWorksSessionManager` 持有 `SemaphoreSlim` 但未实现 `IDisposable`

**位置**: `src/Workers/SolidWorks/SolidWorksSessionManager.cs:35`

```csharp
private readonly SemaphoreSlim _connectionLock = new(1, 1);
```

**问题**: `SemaphoreSlim` 实现了 `IDisposable`，但 `SolidWorksSessionManager` 不实现 `IDisposable`。在 `RealSolidWorksWorker` 的典型使用模式中（`new SolidWorksSessionManager()` 作为默认参数），SessionManager 的生命周期与 Worker 相同。Worker 被 GC 回收时，`SemaphoreSlim` 的 finalizer 最终会释放原生资源，但这不是确定性释放。

如果未来 `SolidWorksSessionManager` 被注入为单例（长生命周期），`SemaphoreSlim` 的 `WaitHandle` 可能永远不会被确定性释放。

**风险**: 低 — `SemaphoreSlim` 的 finalizer 会兜底。`WaitAsync` 不使用 `WaitHandle`（在 .NET 现代版本中），所以不会有句柄泄漏。

**建议修复**: 为 `SolidWorksSessionManager` 添加 `IDisposable` 实现：
```csharp
public sealed class SolidWorksSessionManager : ISolidWorksSessionManager, IDisposable
{
    public void Dispose()
    {
        _connectionLock.Dispose();
    }
}
```

## 7. 架构评估

### 边界一致性: ✅ 优秀

- **Worker 分层清晰**: `RealSolidWorksWorker` 实现 `ISolidWorksWorker : IWorker`，与 `FakeSolidWorksWorker` 同级。两者可以互换（通过 Bootstrapper 或依赖注入），不破坏任何上游消费者。
- **COM 隔离正确**: `ISolidWorksComActivator` 接口将 COM 细节（`Type.GetTypeFromProgID`、`Activator.CreateInstance`、`InvokeMember`、`Marshal.FinalReleaseComObject`）完全封装在 `LateBoundSolidWorksComActivator` 中。测试可以通过 `TrackingSolidWorksComActivator` 完全替换 COM 依赖。
- **Preflight 共享**: `SolidWorksPreflightEvaluator` 是静态工具类，被 `RealSolidWorksWorker`（创建 preflight 报告）和 `SolidWorksEnvironmentValidator`（作为 IValidator 对外暴露）共享。避免了 preflight 逻辑重复。
- **SessionManager 一层封装**: `SolidWorksSessionManager` 封装了 COM 连接/断开/超时/错误转换，对上暴露 `ISolidWorksSessionManager` 接口。
- **Agent / Gateway 隔离保持**: `AgentRegistry` 和 `Gateway` 仍不暴露任何 SolidWorks Worker。测试 `GatewayAndAgentRegistryDoNotExposeRealSolidWorksWorker` 验证了这一点。

### 接口稳定性: ✅ 优秀

- `SolidWorksWorkerRequest` 无破坏性变更 — `DryRun` 和 `AllowRealCadExecution` 保持默认值。
- `SolidWorksWorkerResult` 新增 `RealCadConnected` 和 `PreflightReport` 可选字段 — 向后兼容。
- 新增类型（`SolidWorksRuntimeOptions`、`SolidWorksPreflightReport`、`SolidWorksSessionConnectionResult`）均为独立记录类型，不影响已有消费者。
- `SolidWorksPreflightEvaluator` 是纯静态方法，无状态。

### 耦合风险: ✅ 低

- `RealSolidWorksWorker` → `ISolidWorksSessionManager` → `ISolidWorksComActivator` 依赖链是单向的。
- `SolidWorksEnvironmentValidator` → `SolidWorksPreflightEvaluator` 是单向依赖。
- 无跨层引用。SolidWorks Worker 项目不依赖 PlatformCore。
- `SolidWorksRuntimeOptions.FromEnvironment()` 遵循与 `RuntimeConfiguration.FromEnvironment()` 相同的模式。

### 扩展风险: ✅ 受控

- **V1.0-B 真实建模**: `RealSolidWorksWorker.SupportsRealBuild => false` 和 `RealBuild` 执行模式预留了清晰的扩展点。`RealCadExecuted` 字段已存在但当前始终为 `false`。
- **多 CAD 系统支持**: `TargetSystem` 属性（来自 `IWorker`）已预留。`ISolidWorksSessionManager` 接口可扩展为 `ICadSessionManager`。
- **新 Worker 集成**: Bootstrapper 的 `CandidateAssemblyPaths` 使用的 `EnumerationOptions.IgnoreInaccessible` 确保新 Worker 程序集能被安全发现。

### Workflow 兼容性: ✅ 无影响

- 本次修改不触及 `SequentialWorkflowEngine`、`IRetryPolicy`、`QualityGate` 或 `Orchestrator` 核心逻辑。Worker 的 `ExecuteAsync` 接口保持不变。

## 8. CAD / COM / 外部运行时风险评估

### 外部应用生命周期: ✅ 安全

**三重安全开关设计**（缺一不可）:

| 开关 | 层级 | 激活方式 | V1.0-A 默认值 |
|------|------|---------|-------------|
| `request.DryRun` | 请求级 | `SolidWorksWorkerRequest.DryRun = false` | `true` |
| `request.AllowRealCadExecution` | 请求级 | `SolidWorksWorkerRequest.AllowRealCadExecution = true` | `false` |
| `options.EnableRealExecution` | 环境级 | `SW_ENABLE_REAL_EXECUTION=true` | `false` |

只有当三个开关全部启用时，`RealSolidWorksWorker` 才会尝试 COM 连接。self-check 验证了每个开关的独立性（`SolidWorksRealExecutionRequiresRequestFlag` / `SolidWorksRealExecutionRequiresEnvFlag`）。

**COM 连接保护**:
- `SolidWorksSessionManager.ConnectAsync` 在非 Windows 系统上立即返回 `Connected: false` + 诊断信息
- `ConnectTimeoutSeconds` 默认 30s，钳制范围 [1, 600]
- `SemaphoreSlim(1,1)` 确保 COM STA 串行访问
- COM 连接通过 `Task.Run` 在后台线程执行（避免阻塞异步上下文）
- `Marshal.FinalReleaseComObject` 用于释放 COM 引用（而非 `Marshal.ReleaseComObject`）
- Smoke test 需要额外环境变量 `SW_REAL_SMOKE_TEST=true`
- 严格模式 `SW_STRICT_REAL_SMOKE_TEST=true` 会使连接失败导致 `FinalStatus = "Failed"`

**执行模式边界**:
- `Fake` — FakeSolidWorksWorker（默认）
- `RealPreflightOnly` — 只执行 preflight，不连接 COM
- `RealConnectionSmokeTest` — 连接→立即断开，不执行建模命令
- `RealBuild` — 预留，V1.0-A 不可用（`SupportsRealBuild => false`）

### 文件 I/O 安全性: ✅ 安全

- `SolidWorksPreflightEvaluator.EnsureOutputDirectoryWritable` 创建探针文件 + 删除，验证目录可写性
- 探针文件使用 `Guid.NewGuid():N` 保证唯一性
- IO 异常被转换为 preflight issue（不崩溃）
- 默认输出目录 `output/solidworks/real` 在 `.gitignore` 范围内

### Retry / Timeout 行为: ✅ 良好

- COM 连接超时：`CancellationTokenSource.CancelAfter(ConnectTimeoutSeconds)`
- `WaitAsync(cancellationToken)` 获取信号量时使用原始 token（非 timeout token）— 这是合理的设计选择（超时仅约束 COM 操作，不约束排队等待）
- 超时后正确释放 COM 对象（`ReleaseCurrentApplication`）
- ⚠️ 断开路径无超时（见 MEDIUM-001）

### 失败恢复能力: ✅ 优秀

- COM 连接失败 → `SolidWorksSessionConnectionResult.Connected = false` + 结构化 issue
- COM 异常 → 捕获 `COMException` / `UnauthorizedAccessException` / `InvalidOperationException`
- 超时异常 → 区分外部取消 vs 超时取消（`OperationCanceledException` when 守卫）
- Preflight 失败 → `ShouldRejectBeforeConnection` + `preflight.FinalStatus == "Failed"` 两条拒绝路径
- 所有失败路径都生成结构化 `SolidWorksWorkerResult`（不是异常传播）

### 日志与可追踪性: ✅ 优秀

- `RealSolidWorksWorker` 日志明确记录执行模式（`RealPreflightOnly` / `RealConnectionSmokeTest`）
- `SolidWorksSessionManager` 日志记录连接状态（`"SolidWorks COM session connected for smoke test only."`）
- Preflight report 包含 13 个检查字段
- self-check 中 13 个新字段覆盖从"类型存在"到"安全开关行为"到"smoke test 结果"的全部维度
- `SolidWorksSelfCheckError` 字段在异常路径中记录了 `ex.GetBaseException().Message`
- ⚠️ `SolidWorksStrictRealSmokeTest` 未在报告中暴露（见 LOW-001）

## 12. 重点确认

### 12.1 三重安全开关是否真的无法被绕过？

**✅ 是的。** 三条拒绝路径相互独立：

1. `ShouldRejectBeforeConnection`（第 46 行）— 检查 `request.DryRun || !request.AllowRealCadExecution || !options.EnableRealExecution`，任一为 true 即拒绝
2. `preflight.FinalStatus == "Failed"`（第 59 行）— 由 `SolidWorksPreflightEvaluator` 计算，当 `EnableRealExecution=false` 且输出目录不可写时返回 Failed
3. self-check 独立验证了 `request.AllowRealCadExecution` 缺失和 `SW_ENABLE_REAL_EXECUTION` 缺失两条路径（`RealSolidWorksWorkerRejectsWhenRequestOrEnvironmentSafetySwitchesAreMissing` 测试）

即使攻击者控制了两层（例如同时控制请求对象和环境变量），`SupportsRealBuild => false` 确保 V1.0-A 中绝不执行真实建模命令。

### 12.2 COM late binding 是否安全？

**✅ 安全。** `LateBoundSolidWorksComActivator` 通过 `Type.GetTypeFromProgID` + `Activator.CreateInstance` + `InvokeMember` 进行 late binding，避免了编译期 Interop 依赖。关键安全措施：

- `CreateApplication` 在 ProgID 不存在时抛出 `InvalidOperationException`（而非静默返回 null）
- `SetVisible` 的异常被静默吞掉是**有意的设计选择**（部分 COM 环境限制 Visible 属性，不应阻塞连接）
- `ReadVersion` 的异常静默返回 null 也是**有意的**（版本号是诊断信息，非关键路径）
- `Release` 使用 `Marshal.FinalReleaseComObject`（而非 `ReleaseComObject`）确保引用计数一次性归零
- 所有 COM 调用包装在 `cancellationToken.ThrowIfCancellationRequested()` 守卫中

### 12.3 架构是否被破坏？

**✅ 未被破坏。** 新增的 `RealSolidWorksWorker`、`SolidWorksSessionManager`、`SolidWorksEnvironmentValidator` 严格遵循现有分层：

- Worker 层 ↔ SessionManager 层 ↔ COM Activator 层（三层分离，均可独立测试）
- Validator 层通过 `SolidWorksPreflightEvaluator` 共享 preflight 逻辑
- Gateway ↔ Agent Registry 隔离由测试验证
- self-check 新增 13 个字段，全部有 `[JsonPropertyName]`，命名风格一致

### 12.4 V1.0-B 是否可以开始？

**✅ 可以。** V1.0-A 的真实执行安全边界设计正确且经过良好测试。V1.0-B 的"最小真实建模能力"（README 中提及）可以在当前架构上构建：
- 在 `RealSolidWorksWorker` 中增加 `RealBuild` 执行模式
- 将 `SupportsRealBuild` 改为 `true`（或通过 `SolidWorksRuntimeOptions` 控制）
- 在 `SolidWorksSessionManager` 中增加建模命令执行方法

当前所有 MEDIUM/LOW 问题均可作为 V1.0-B 开发的一部分处理，不阻塞开始。
