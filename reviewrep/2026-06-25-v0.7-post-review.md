## 4. 高优先级问题

### HIGH-001: ExponentialBackoff Retry 延迟从未实际等待 (I7 遗留)

**位置**: `src/PlatformCore/WorkflowEngine/SequentialWorkflowEngine.cs:64-71` — `case GateDecisionResult.Rejected when _retryPolicy.ShouldRetry(...)` 分支

**问题**: 代码在第 68 行计算 `retryDelay`，第 69 行记录审计日志（日志中甚至写了 `"will run after calculated delay {retryDelay.TotalMilliseconds:0}ms"`），然后第 70-71 行执行 `retryCount++; continue;`——直接跳回 `while (true)` 重新执行步骤。缺少 `await Task.Delay(retryDelay)`。

**实际代码**（第 64-71 行）:
```csharp
case GateDecisionResult.Rejected when _retryPolicy.ShouldRetry(decision, retryCount, typedIssues):
{
    var retrying = Normalize(rawResult, step, WorkflowStepStatus.Retrying, decision, retryCount, maxRetries, step.StepId ?? step.Name);
    results.Add(retrying);
    var retryDelay = _retryPolicy.GetDelay(retryCount);
    _auditLog.Record("workflow", retrying.StepId, "workflow_step_retrying", $"Workflow step '{retrying.StepId}' rejected; retry {retryCount + 1} of {maxRetries} will run after calculated delay {retryDelay.TotalMilliseconds:0}ms.");
    retryCount++;
    continue;  // ← 缺少 await Task.Delay(retryDelay)
}
```

**风险**:
* `ExponentialBackoffRetryPolicy` 的 `GetDelay()` 返回正确的指数延迟值（100ms → 200ms → 400ms → ... → 5000ms），但这些值从未被使用
* 重试是立即执行的，在高负载或外部服务短暂故障时，立即重试大概率再次失败，浪费 retry 配额
* 审计日志中的 "will run after calculated delay Nms" 信息与实际情况不符——这是假报告
* 在生产环境中，如果外部 Runtime (LLM API) 返回瞬态错误，立即重试会导致 API 速率限制或连接池耗尽

**建议修复**:
在 `continue` 之前添加 `await Task.Delay(retryDelay)`:

```csharp
var retryDelay = _retryPolicy.GetDelay(retryCount);
_auditLog.Record("workflow", retrying.StepId, "workflow_step_retrying",
    $"Workflow step '{retrying.StepId}' rejected; retry {retryCount + 1} of {maxRetries} will run after calculated delay {retryDelay.TotalMilliseconds:0}ms.");
retryCount++;
await Task.Delay(retryDelay);  // ← 添加此行
continue;
```

### HIGH-002: OpenAICompatibleModelClient HttpClient 无超时配置 (I9 遗留)

**位置**: `src/AgentRuntime.Microsoft/OpenAICompatibleModelClient.cs:11-13` — 构造函数 + `GenerateTextAsync` 方法

**问题**: `_httpClient = httpClient ?? new HttpClient()` 创建的默认 `HttpClient` 的 `Timeout` 属性默认为 `100_000ms` (100秒)。`RuntimeConfiguration.TimeoutSeconds` 默认值为 30 秒，但该值从未应用到 `HttpClient.Timeout` 或通过 `CancellationTokenSource` 实现超时。

**实际代码**:
```csharp
// 第 13 行
_httpClient = httpClient ?? new HttpClient();
// TimeoutSeconds 配置从未使用
```

**风险**:
* 如果 LLM API 端点无响应，请求可能悬挂 100 秒（默认超时），远超预期的 30 秒
* 在 WorkflowEngine 中，`MicrosoftRuntimeAgentInvoker` 的异常过滤器会捕获 `TaskCanceledException` 和 `TimeoutException`，但 100 秒的超时与配置声明的 `TimeoutSeconds=30` 不一致
* `RuntimeConfiguration` 的告警与运行时实际行为脱节——这是配置不一致的问题

**建议修复**:

在 `OpenAICompatibleModelClient` 构造函数中应用超时:

```csharp
public OpenAICompatibleModelClient(HttpClient? httpClient = null)
{
    _httpClient = httpClient ?? new HttpClient();
}
```

改为在 `GenerateTextAsync` 中通过 `CancellationTokenSource` 应用超时:

```csharp
public async Task<string> GenerateTextAsync(
    string systemPrompt,
    string userMessage,
    RuntimeConfiguration configuration,
    CancellationToken cancellationToken = default)
{
    using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
    timeoutCts.CancelAfter(TimeSpan.FromSeconds(configuration.TimeoutSeconds));
    // ... rest of method, passing timeoutCts.Token to SendAsync
}
```

## 5. 中优先级问题

### MEDIUM-001: MicrosoftRuntimeAgentInvoker 异常过滤器未覆盖 SocketException/IOException

**位置**: `src/AgentRuntime.Microsoft/MicrosoftRuntimeAgentInvoker.cs:91` — `catch` 子句

**问题**:
```csharp
catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException or TimeoutException or InvalidOperationException or JsonException)
```

此过滤器未覆盖 `System.Net.Sockets.SocketException` 和 `System.IO.IOException`。在 Windows 上，当网络不可达或 DNS 解析失败时，`HttpClient` 可能抛出 `SocketException`（而非 `HttpRequestException`），尤其是在连接建立阶段。

**风险**:
* 网络层异常可能穿透异常过滤器，导致未处理的异常传播到 `MicrosoftAgentAdapter.ExecuteAsync`，破坏 Runtime-then-Workflow 的双阶段保证
* 如果 Runtime 阶段因未捕获异常崩溃，Workflow 阶段（authoritative execution）将完全跳过

**建议修复**:

在异常过滤器中添加 `SocketException` 和 `IOException`:

```csharp
catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException or TimeoutException or InvalidOperationException or JsonException or System.Net.Sockets.SocketException or System.IO.IOException)
```

或者更安全的方式——添加一个通用 fallback:

```csharp
catch (Exception ex)
{
    _auditLog.Record("agent-runtime", manifest.Id, "real_runtime_failed_unexpected", ex.GetType().Name);
    return new AgentOutput(
        AgentOutputStatus.Failed,
        "Chief engineer real runtime failed unexpectedly before platform orchestration.",
        Array.Empty<ArtifactInfo>(),
        new[] { $"runtime_error: {ex.GetType().Name}" },
        new[] { $"Unexpected runtime failure ({ex.GetType().Name}) was converted to structured AgentOutput without exposing credentials." },
        null,
        RuntimeMetadata: RuntimeMetadata.MockMicrosoft(_configuration.Provider, _configuration.Model, ex.GetType().Name));
}
```

### MEDIUM-002: SequentialWorkflowEngine 默认构造函数使用无延迟 RetryPolicy

**位置**: `src/PlatformCore/WorkflowEngine/SequentialWorkflowEngine.cs:12-14` — 默认构造函数

**问题**:
```csharp
public SequentialWorkflowEngine()
    : this(new RetryPolicy(), new InMemoryAuditLog())
{
}
```

`RetryPolicy` 的 `Delay = TimeSpan.Zero`，`BackoffStrategy = BackoffStrategy.None`，`GetDelay()` 继承自 `DefaultRetryPolicy` 返回 `TimeSpan.Zero`。即使 I7 修复后（添加了 `await Task.Delay`），默认构造的引擎也不会产生任何延迟。

**风险**:
* 平台默认配置下，重试之间无任何间隔
* 这是 I7 问题的根因放大——即使修了 I7，默认行为仍然无延迟

**建议修复**:

默认构造函数使用 `DefaultRetryPolicy(maxRetries: 2)` 并添加最小延迟:

```csharp
public SequentialWorkflowEngine()
    : this(new ExponentialBackoffRetryPolicy(maxRetries: 2, baseDelayMs: 500, maxDelayMs: 3000), new InMemoryAuditLog())
{
}
```

或在 `DefaultRetryPolicy` 基类中为 `GetDelay` 提供非零默认值。

### MEDIUM-003: 测试中 hardcoded 临时路径可能造成文件残留

**位置**: 
* `tests/PlatformSelfCheck.Tests/RealRuntimeIntegrationTests.cs:150` — `Path.GetTempPath()` 
* `tests/PlatformSelfCheck.Tests/WorkflowBackedInternalOrchestrationTests.cs:172` — `Path.GetTempPath()`

**问题**: 测试使用 `Path.Combine(Path.GetTempPath(), "ai_me_self_check_v07", Guid.NewGuid().ToString("N"))` 作为 self-check 输出目录。测试结束后未清理这些临时目录。

**风险**: 长期运行后临时目录累积，占用磁盘空间。虽然单个目录很小（JSON 报告），但频繁运行测试可能产生大量残留。

**建议修复**: 在测试类中实现 `IDisposable` 或在测试方法中使用 `try/finally` 清理临时目录。

## 7. 架构评估

* **边界一致性**: ✅ 优秀。`AgentRuntime.Microsoft` 是唯一引用 Microsoft Agent Framework 包的项目。Contracts、PlatformCore、DomainSchemas、QualityGate 均不依赖 Runtime 类型。self-check 通过反射加载 Runtime 程序集，避免 Contracts 层的编译期依赖。

* **接口稳定性**: ✅ 良好。`AgentOutput` 新增 `RuntimeMetadata?` 可选字段，向后兼容。`IRetryPolicy` 接口自 V0.5 以来保持稳定。`IAgent` 接口未变动。

* **耦合风险**: ✅ 低。Runtime-then-Workflow 将 LLM 输出定位为"咨询性质"，平台权威执行路径 (`ChiefEngineerOrchestrator` → `SequentialWorkflowEngine` → `InternalAgentWorkflowStep` → QualityGate) 不受 Runtime 影响。

* **扩展风险**: ✅ 受控。`AgentFactory.CreateRuntimeAwareAgent` 通过白名单（仅 chief-engineer）控制 Runtime 启用范围。未来扩展至其他 Internal Agent 时只需放宽白名单，结构不变。

* **Workflow 兼容性**: ⚠️ 注意 I7 对 WorkflowEngine 重试行为的影响。retry 延迟缺失不影响正确性（重试仍然发生，只是无间隔），但影响生产环境可靠性。

* **五层安全边界**: ✅ 全部验证通过。
  1. 环境变量 (`AI_AGENT_RUNTIME_MODE` 默认 Mock)
  2. Agent 白名单 (`AgentFactory:44-47`)
