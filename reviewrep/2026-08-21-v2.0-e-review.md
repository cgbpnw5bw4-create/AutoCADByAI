## 2. 结论理由

先讲正面成果，因为它是本轮最大收获：**V2.0-E 的架构目标真实达成了。**

- `PartFamilyBuilderRegistry.CreateDefault()` 从 `PartTypeRegistry` 投影生成通用执行器，**四个零件族共用一条建模链路**，无零件专用 Builder 被注册，无 `switch (part_type)`。
- `no_large_part_type_switch = True`、`no_part_specific_logic_in_real_worker = True`，均为行为/反射式判据。
- 测试从 319 增至 **330 项全绿**，编译零警告零错误。
- 夹套被**显式冻结**并写明理由（`PartFamilies.cs:528`，`SupportsRealExecution => false`，注释「不能因 V2.0-E 的通用 Feature Handler 证据而获得真实 CAD 授权」）——诚实的 fail-closed，不是绕过。

不批准的原因是两件事，第二件比第一件严重。

**第一，V2.0-E 打坏了两个既有自检字段，并在此状态下提交。**

逐提交取证：

| 提交 | `flange_artifact_validation_supported` | `shaft_artifact_validation_supported` |
|---|---|---|
| `92ca04d` V2.0-D | True | True |
| `6e055bc` | True | True |
| `4cd7186` | True | True |
| **`97fd9fe` V2.0-E** | **False** | **False** |

根因在 `PlatformSelfCheckRunner.cs:1100-1103`：判据仍绑定 `PartFamilyExecutionModes.FlangeBasic` / `ShaftBasic`——**V2.0-E 亲手废除的旧执行模式**。迁移后所有定义都是 `GenericFeatureGraph`，这两个字段**在构造上永远不可能再为 true**。

**第二（更严重），V2.0-E 用自己的子集给自己打了合格分。**

`PlatformSelfCheckRunner.cs:861`：`V20EFinalStatus = v20EUnifiedFeatureGraphChecks.AllPassed ? "Passed" : "Failed"`。

结果：`v2_0_e_final_status = Passed`，而平台 `final_status = Failed`，失败项里正好包含被 V2.0-E 打坏的那两个字段。

**这是结构性问题**：自检按版本阶段分组，每个阶段维护自己的 `AllPassed`。于是一个阶段可以在**组内全绿**的同时**打坏组外既有字段**，而阶段状态毫无感知。V2.0-E 是第一个被该结构反噬的实例。

这是我从 V1.8 追踪至今的「self-check `Passed` 含金量稀释」模式的**第七次**出现，首次以**分组自评掩盖跨组回归**的形态呈现。

## 3. 阻塞问题

### BLOCKER-001：两个既有自检字段被打成永久 false 并已提交

**位置**：`src/PlatformCore/PlatformSelfCheckRunner.cs:1100-1103`

**问题**：判据断言 `RealExecutionMode == FlangeBasic / ShaftBasic`，而全部定义已迁至 `GenericFeatureGraph`，条件恒不成立。

**风险**：字段名宣称「artifact 校验受支持」。实际上通用分支的校验**比旧分支更严格**（额外要求 `feature_execution_report.json`），能力不但没丢反而增强。**字段在向下撒谎**——报 false 而能力存在。这会误导后续判断「V2.0-E 弄丢了 flange/shaft 产物校验」，属于与假成功相反、但同样有害的**假失败**。

**建议修复**：改为断言 `RealExecutionMode == GenericFeatureGraph` 且该族解析到通用执行器；或删除这两个按族重复的判据，复用已有的 `AllPartFamiliesUseRegistry`。

### BLOCKER-002：阶段自评允许「组内合格 + 组外回归」并存

**位置**：`src/PlatformCore/PlatformSelfCheckRunner.cs:861`，及各阶段 `*SelfCheckResult.AllPassed` 的分组设计

**问题**：`v2_0_e_final_status` 只由本阶段字段组决定，与平台 `final_status` 解耦。

**风险**：这是 BLOCKER-001 得以提交的**结构性使能条件**。只要该机制存在，每个新阶段都可能重复：组内全绿、组外回归、阶段自评通过。协议第 9 节把假成功列为最高风险，而这是假成功在**治理层**的形态。

**建议修复**：`v2_0_e_final_status` 及后续所有阶段状态，在平台 `final_status != "Passed"` 时强制降级；并增加**跨提交回归闸**——保存上次通过的报告，任何字段由 true 变 false 直接判定本阶段不合格。后者能一次性防住所有未来阶段的同类回归。

### ARCH-002（MEDIUM）：定义层 `SupportsRealExecution` 与 Feature 层证据不一致

`IPartFamilyDefinition.SupportsRealExecution` 默认 `true`，仅 `JacketBasicDefinition` 覆写为 `false`。`shaft_basic` 因此在**定义层声明可真实执行**，但其唯一 Feature `revolve_boss` 的 Handler 证据仍为 `Unverified`，会在 Feature 证据门被拒。

**风险**：两层说法不一致。最终结果正确（fail-closed），但排障时会先看到定义层的 true 而误判。

**建议**：让 `SupportsRealExecution` 由该族 FeatureGraph 所需 Feature 的证据状态推导，使定义层、能力矩阵、执行层三者自动一致。

## 9. 下一阶段建议

### 当前版本是否可以进入下一阶段？

**不可以。**

理由不在于架构做得不好——**V2.0-E 的核心目标真实达成了**。四个零件族确实统一到了一条建模链路，这正是我在 V2.1-A 审查中列为「下一阶段最应该优先做」的事，本轮兑现了。测试也从 319 增至 330 全绿。

### 必须先修什么

1. `PlatformSelfCheckRunner.cs:1100-1103` 两个判据（BLOCKER-001）
2. **跨提交回归闸**（BLOCKER-002 + GAP-001，最高价值）
3. 阶段状态不得独立于平台判定
4. `cad_capability_matrix_exists` 接入（一行，文档已就绪）

修完这四项即可进入下一阶段。前三项是同一件事的三个侧面，一起做成本最低。

### 可以延后

Part 3 / Part 5 / 其余 Part 6 字段、死代码清理、`revolve_boss` 证据、HumanApproval、`InternalRoute`。这些都不影响判断当前版本是否安全。

### 下一阶段最应该优先做什么

**把「一处变更、全局校验」做成机制，而不是继续靠人记得同步。**

> **建立自检的回归基线与一致性闸。** 保存上次通过的报告、比对字段退化、阶段状态从属于平台状态、能力声明（定义层 / 能力矩阵 / Feature 证据）三者交叉校验。

做完这件事，之后每个阶段的迁移成本与风险都会显著下降；不做的话，V2.1、V2.2 会继续以新形态重演同一模式——这已经是第七次了。
